Oracle 자체 스케줄러가 만료된 업무를 이어받습니다.

살아 있는 DB의 소유권이 만료된 뒤 수집·규칙·AI 검수·발행을 제한된 동시성으로 재개합니다. 평소 번역·등록 후 관리는 계속합니다. 웹·관리자도 Oracle용 최소 운영 경로를 준비합니다.

  1. 새 작업 유입을 줄이고 번역·제품 연결·발행 후 반영을 우선
  2. 공통 quota와 사람 결정·기존 중단 설정을 그대로 적용
  3. 한 작업씩 인계하고 늦게 돌아온 M3·mini 결과는 차단

DB·작업 장부도 Oracle에 복구 가능해야 함

실측 NoMoreVibe DB 9.03GiB, 전체 DB 합19.79GiB, Oracle 여유 약20GiB입니다. 기존 DB는 x86, Oracle은 ARM이므로 물리 복제본을 그대로 옮기는 방식도 사용할 수 없습니다. NoMoreVibe 전용 논리 복제·백업 복원과 용량을 검증하고, 기존 writer를 차단한 뒤 전환합니다. 현재 미구현입니다.

번역 모델도 M3와 독립된 경로 필요

현재 번역은 abcllm의 OSS 120을 호출합니다. API 주소가 외부여도 실제 모델이 M3에 있으면 함께 멈춥니다. 독립된 제공 경로·품질·예산을 검증하고 장애용 자격 증명을 준비해야 모델 장애에도 번역이 계속됩니다. 번역 실패를 완료로 바꾸지 않습니다.

1 CPU의 비상 모드는 처리량을 낮춰 서비스를 이어가는 목적입니다. 정상 상태의 2배 목표와 별도로 측정합니다. DB 복원 지연·데이터 손실 허용치(RTO/RPO), 모델 대체 품질·비용, 실제 장애·복귀 시험이 필요합니다. DB가 전환되어도 기존 외부 호출이 끝났는지 확인한 뒤 공통 슬롯을 다시 엽니다.

승인 또는 거절이 확정된 후보를 비교 구간당 최대 한 번만 셉니다. 2차가 필요한 승인 후보는 2차까지 완료해야 합니다. 규칙만 완료·사람 인계·1차만 완료·캐시 재사용·발행 수는 따로 집계합니다.

같은 입력 분포·모델·프롬프트·기준 시각과 동등한 초기 DB·캐시 조건을 맞춥니다. warm/cold cache는 구분하고, 실제 모델 호출 실험도 예산 안에서 진행합니다.

함께 통과해야 하는 조건

  • 검수 대기를 유지한 30분 구간을 양쪽에서 측정
  • 전체 처리 지연 p95 악화 없음
  • 기술 실패율은 기준 +1%p 이하
  • 잘못된 승인·거절 증가 없음
  • 사람 결정 덮어쓰기·필수 심사 누락·이중 발행 0건
기존 기준 측정→격리된 동일 입력 비교→30분 운영 canary→24시간 관측
모델 서버가 이미 포화라면 처리기를 늘려도 2배가 되지 않습니다. 그때는 추가 실행 분리보다 모델 제공 용량과 비용안을 먼저 검토합니다. 대기열이 비어 버린 측정도 최대 용량의 증거로 사용하지 않습니다.

실행 순서

격리 구현·검증 후 각 운영 전환 직전에 PR·CI·migration·canary 적용

  1. 1.
    기준 측정 준비

    동일 입력·고유 완료량·대기 시간 계측. 기존 운영 중단과 근거 회복 작업 유지.

  2. 2.
    공통 한도·소유권 선행

    모델 슬롯, 개별 lease, 출처 분리·결과 검증. DB 생존 경로와 Oracle 3순위 인계 계약 검증.

  3. 3.
    검수의 지속 처리

    AI1·AI2·배경 실행 분리. 준비된 후보와 빈 슬롯이 있을 때 즉시 이어 처리.

  4. 4.
    Oracle 상시 업무 활성화

    번역·사이트 근거부터 실제 저장 확인. 연결 확인은 지역 비교·중복 관측 방지 후 판정 권한 이전.

  5. 5.
    최종 장애·복귀 시험

    M3·mini 동시 중단, DB 복구, 독립 모델 번역, 이전 writer 차단, Oracle 최소 웹 경로 확인.

  6. 6.
    수집 분담·원본 공급

    검색 구간 분할과 버퍼 제어. 원본 동시 3부터, 실제 검수 공급 부족 시 증설 비교.

  7. 7.
    관리자에서 확인

    실행 host·최종 장애 인계 상태, 단계별 대기·모델 슬롯·실제 완료량·보류 이유 표시.

  8. 8.
    단계 배포·실측

    PR·CI·migration, 세 서버 순차 배포와 canary. 정상 2배·비상 유지 처리량을 각각 보고.

이 페이지는 설계 비교용입니다. 파이프라인 변경 구현·운영 배포·2배 실측 성공을 의미하지 않습니다.
