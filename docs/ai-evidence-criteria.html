‘AI로 만들었다’를 어디까지 확신할 수 있나

상세 페이지의 ‘무엇으로 만들었나’가 무엇을 근거로 말하는지, 각 근거가 무엇을 증명하고 무엇은 증명하지 못하는지 정리했습니다. 2026-10-10 이 기준으로 1·2·3단계 판정을 만들어 운영에 적용했습니다(#339·#340) — 무엇을 모으는지, 공개분 표본의 실측과 남은 한계를 함께 적었습니다.

결론

공개된 저장소만 보고 “이 제품 전체를 AI로 만들었다”를 100% 확정할 수 있는 경우는 없습니다. 커밋의 작성자 이름·이메일, 커밋 메시지 끝의 서명 줄, 설정 파일은 모두 사람이 직접 쓰거나 복사할 수 있습니다. GitHub 가 ‘Verified’로 표시한 커밋도 API 로 만들면 작성자를 마음대로 적을 수 있습니다.

확정에 가장 가까운 것은 AI 에이전트 서비스의 GitHub 앱 계정(봇)이 연 PR 이 기본 브랜치에 병합된 경우입니다. 그 계정으로 PR 을 여는 것은 그 앱만 할 수 있으므로, “이 변경은 AI 에이전트가 만들었다”는 것까지는 사실상 확정입니다. 다만 그것도 그 PR 의 변경에 대한 사실이지, 제품 전체에 대한 사실은 아닙니다. 2026-10-10부터 이 신호를 모읍니다.

그래서 화면은 “AI로 만들었다”가 아니라 어떤 근거가 있는지를 단계별로 말해야 합니다. 지금 코드도 같은 원칙을 지키고 있어 모든 판정에 ‘실행 검증 안 됨’(executionVerified: false)이 고정돼 있습니다.

근거의 단계

위에서 아래로 갈수록 약합니다. 한 제품에 여러 근거가 있으면 가장 높은 단계로 말합니다.

1단계사실상 확정

AI 에이전트 봇 계정이 연 PR 이 병합됨 모음 · 10-10

예
GitHub Copilot 코딩 에이전트, Devin, Jules 같은 서비스가 자기 GitHub 앱 계정으로 PR 을 열고, 그 PR 이 기본 브랜치에 병합됨. 서비스마다 PR 을 여는 계정이 달라서, 계정 목록은 실제 PR 로 확인해 가며 유지해야 합니다.
증명하는 것
그 PR 의 변경을 AI 에이전트 서비스가 만들었다. PR 을 연 계정은 GitHub 가 보증하고, 그 앱의 설치 토큰 없이는 그 계정으로 PR 을 열 수 없습니다.
증명 못 하는 것
제품의 나머지 코드, 병합 뒤 사람이 고친 부분.
위조
매우 어려움. 앱 권한을 탈취하지 않는 한 불가능합니다.
지금 코드
기본 브랜치의 최근 병합 PR 30개에서 PR 을 연 계정이 서비스가 토큰을 쥔 에이전트 앱(copilot-swe-agent·devin-ai-integration·google-labs-jules·cursor·kiro-agent·codegen-sh·amazon-q-developer·factory-droid·arena-ai-coding-agent)이고, PR 이 코드 파일을 바꿨으면 1단계. PR 안 커밋 작성자는 보지 않습니다 — Devin·Arena·Cursor 는 사용자 이름으로 커밋합니다(실측). claude[bot]은 저장소 주인의 워크플로가 토큰을 받아 쓰므로 2단계입니다.
2단계강함

AI 도구 서명이 붙은 ‘개발’ 커밋이 기본 브랜치에 있음 모음 · 10-10

예
커밋 메시지 끝에 Co-authored-by: Claude <noreply@anthropic.com>, Co-authored-by: Codex 같은 줄이 있고, 그 커밋이 테스트·문서가 아닌 실제 코드 파일을 바꿨다.
증명하는 것
그 도구를 쓴 작업 흐름에서 이 커밋이 만들어졌다고 저장소가 스스로 밝혔다. 도구가 자동으로 붙이는 줄이라 정상적인 경우 강한 신호입니다.
증명 못 하는 것
실제로 도구가 코드를 썼는지. 이 줄은 사람이 손으로 써 넣을 수 있습니다.
위조
쉬움. 의도적으로 꾸미면 막을 방법이 없습니다.
지금 코드
기본 브랜치의 최근 커밋 30개를 직접 봅니다(병합 커밋 제외). Co-authored-by 표기(모델 이름 뒤 괄호·Fable 포함), 작성자 자체가 도구인 커밋(Claude <noreply@anthropic.com>·Cursor Agent·Copilot·Codex), 도구가 붙이는 꼬리 줄을 읽고, 그 커밋이 코드 파일을 바꿨는지 하나씩 확인합니다. 사람 이름이기도 한 표기(Claude·Devin·Jules)는 메일 주소까지 맞아야 합니다. 기존 수집이 찾은 개발 커밋 표기도 2단계로 셉니다. 포크는 커밋 표기를 보지 않습니다.
3단계보통

특정 AI 도구 전용 설정·규칙 파일이 있음 모음

예
.claude/settings.json, .claude/rules/*.md, .codex/config.toml, .cursor/rules/*.mdc, .github/copilot-instructions.md, .windsurfrules, .clinerules, .aider.conf.yml
증명하는 것
누군가 이 저장소에서 그 도구를 쓰도록 설정했다. 의도와 환경까지입니다.
증명 못 하는 것
그 도구가 실제로 코드를 썼는지. 설정만 복사해 둔 저장소도 있습니다.
위조
쉬움. 파일 하나를 추가하면 됩니다.
지금 코드
루트와 에이전트 폴더(.claude·.cursor·.github 등) 두 겹을 보고, 도구가 정해진 규칙(agents/catalog.ts)에 맞는 파일이 있으면 3단계.
4단계약함

도구를 특정할 수 없는 지침 파일, 메이커의 자기 신고 모음 · 도구 미상

예
CLAUDE.md, AGENTS.md, GEMINI.md, 스킬 폴더의 SKILL.md는 여러 도구가 같이 읽는 형식이라 어느 도구인지 정할 수 없습니다. /nomorevibe로 등록할 때 AI 가 스스로 적어 넣는 ‘제작 도구’(builder)와 README 의 “built with …”도 여기에 속합니다.
증명하는 것
AI 도구와 함께 일할 준비를 했거나, 그렇게 주장한다.
증명 못 하는 것
어느 도구인지, 실제로 썼는지.
지금 코드
CLAUDE.md·AGENTS.md는 관찰은 하지만 이름 있는 도구로 세지 않습니다(client: null). 메이커 신고는 화면에 ‘메이커 신고 · 검증할 방법 없음’으로만 보입니다.
근거 아님

판단에 쓰지 않는 것

예
GitHub 토픽(vibe-coding 등), 페이지나 README 의 ‘AI’ 단어, 제품이 AI 기능을 가진 것, 커미터만 도구 이름인 커밋, 포크로 물려받은 커밋, 예제·템플릿 폴더 안의 설정 파일.
흔적 없음
흔적을 못 찾았다고 해서 AI 없이 만들었다는 뜻은 아닙니다. 검사 범위 밖에 있거나, 흔적을 남기지 않는 방식으로 썼을 수 있습니다.

화면에서 쓰는 말 (2026-10-10 적용)

단계마다 말할 수 있는 만큼만 말합니다. ‘AI 제작 검증 완료’ 같은 배지는 어느 단계에서도 쓰지 않습니다. 공개 여부는 단계와 상관없이 지금처럼 정합니다 — 단계는 분류에만 씁니다.

자리보이는 것
홈 필터‘만든 방식’의 AI로 제작 칩 하나 — 1·2·3단계 모두. 분야·검색·순위와 함께 걸립니다(?ai=made).
카드표시 없음(일단 필터로만 가립니다).
상세“AI 제작 근거 N단계 · 단계 이름”과 한 줄 설명만. PR·커밋·파일 링크와 도구 이름은 내지 않습니다.
근거 없음“검사에서 AI 코딩 도구 흔적을 찾지 못했습니다 — AI 없이 만들었다는 뜻은 아닙니다.”
검사 전“AI 흔적 검사 대기 중 …”
기준 설명푸터 ‘데이터와 집계 기준’의 ‘만든 방식’ — 단계 뜻·한계·단계별 공개 수.

판정 코드와 다른 길(GitHub REST)로 다시 확인: 1단계 30/30, 새 규칙의 2단계 25/25, 3단계 20/20 정확. 2단계가 이전 수집의 최고 단계(31%)보다 많은 것은 이전 수집이 저장소마다 검색으로 찾은 커밋을 최대 5개만 봤기 때문입니다. 도구는 Claude Code 가 가장 많습니다(1·2단계의 97%).

‘AI 흔적 검사 대기 중’이 보이는 때

  1. 판정 잡(ai-level-refresh)이 아직 그 저장소를 보지 않았을 때. 새 후보 → 아직 안 본 공개 제품(최신부터) → 사흘 지난 것 차례로, 1분마다 60개 남짓 봅니다. 크롤러가 올리는 새 제품은 후보 때 이미 판정돼 발행과 함께 단계가 붙습니다.
  2. 묻다 실패해 한 번도 판정하지 못했을 때(GitHub 시간 초과 등) — 한 시간 뒤 다시 봅니다. 한 번 판정한 저장소는 실패해도 지난 단계를 그대로 둡니다.

고친 것과 남은 것

  1. 고침 — 1단계를 모읍니다. 병합 PR 을 연 계정을 읽어 에이전트 앱이면 1단계(#339).
  2. 고침 — 기본 브랜치 최근 커밋 30개를 직접 봅니다. 발견 검색으로 찾은 커밋만 보던 한계가 없어졌습니다.
  3. 고침 — 근거가 있는데 “찾지 못했습니다”가 나오던 상세 문구. 단계 이름을 보이고, 근거가 없을 때만 그 말을 씁니다.
  4. 고침 — 서명 표기의 변형. 모델 이름 뒤 괄호·Fable·Cursor Agent·작성자 표기·꼬리 줄을 읽습니다. 기존 수집기의 규칙(commit-attribution.ts)은 판정 판을 올리면 모든 제품이 ‘대기 중’이 되므로 그대로 두었습니다.
  5. 남음 — 최근 병합 PR 30개·커밋 30개 밖은 보지 않습니다. 오래 활발한 저장소는 그 밖의 근거를 놓칠 수 있습니다(단계를 낮게 볼 수는 있어도 높게 보지는 않습니다). 처음 확인한 표기 커밋이 문서만 바꿨으면 다음 차례에 3개씩 더 봅니다.
  6. 남음 — 하위 폴더의 지침 파일은 보지 않습니다. apps/web/CLAUDE.md처럼 모노레포 안쪽의 파일. 공유 형식이라 단계에는 들지 않습니다.
  7. 남음 — 검색엔진 노출 규칙. lib/domain/products/indexing.ts는 아직 이전 수집기의 흔적을 봅니다. 새 단계로 바꿀지 정해야 합니다.
  8. 남음 — 우리가 직접 기록하는 길. 메이커가 /nomorevibe로 개발 과정을 남기게 하면 ‘우리가 확인한 AI 제작’ 단계를 만들 수 있습니다(nomorevibe_recorded, 아직 쓰는 곳 없음).
