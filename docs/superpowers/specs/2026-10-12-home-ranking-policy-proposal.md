# 신규 목록 수정과 8시간 스타 상승 집계 제안

상태: 사용자에게 제시하는 기준·PR 범위다. **8시간 갱신과 발굴에서 독립된 관측 작업은 사용자 지정**이다. 스타 구간·최소 증가량 등 나머지 정책은 아래 추천안이며 앱 코드·DB·운영 기준은 아직 변경하지 않았다.

근거: [홈 목록 운영 검토](../../operations/2026-10-12-home-criteria-audit.md). 신규 목록이 서비스 등재일을 사용하고, 기존 급상승은 마지막 두 관측의 일평균이며 정상 재조회는20시간이다. 기존 컬럼만으로 전날 같은 시간대 비교나 과거 회차 결과를 보존할 수 없다.

## 추천 정책

‘지금 뜨는 프로젝트’ 대신 **‘전일 대비 스타 급상승’**으로 표기한다. 발굴·신규와 구별되는 관심 증가 목록이다. 오래된 프로젝트도 최근 스타가 증가하면 포함할 수 있다.

| 항목 | 추천 기준 |
|---|---|
| 대상 | NoMoreVibe에 공개된 verified/seeded 프로젝트 중 정상 공개 GitHub 저장소 |
| 스타 구간 | 해당 집계에서 확인한 스타 **50개 이상, 2,000개 미만(50~1,999개)** |
| 비교 | **전날 같은 집계 시간대**의 성공 관측과 비교, 명목상24시간 간격 |
| 수집·갱신 | KST **00시·08시·16시** 회차, 하루3회 |
| 관측 오차 | 각 회차 직전1시간 안에 확인한 값만 사용. 실제 두 관측 간격은23~25시간이며 실제 시각을 공개 |
| 최소 증가 | 두 회차 관측 사이 스타 **순증가10개 이상** |
| 순위 | 순증가 내림차순 → 해당 회차 스타 내림차순 → slug 오름차순 |

| 신규 발굴분 | 다음 관측 회차부터 대상.24시간 전 비교 관측이 확보된 뒤 상승 순위 진입 |

50은 관심 신호가 거의 없는 저장소의 작은 변동이 순위에 섞이는 것을 줄이는 시작선이다.2,000은 기존 ‘많이 쓰이는’ 스타 구간의 시작선과 맞춘다. 최소+10과 스타50은 추천 초기 정책값이며 이미 합의되거나 데이터로 최적화된 값은 아니다. 증가율만으로 정렬하면 작은 분모가 순위를 크게 움직이므로 절대 순증가로 정한다. 방문·서비스 내부 스타·AI 심사는 점수에 섞지 않는다.

정확한 GitHub의 모든 스타 이벤트 시각을 확보한24시간 집계가 아니다. **전일 동시간대의 관측값 비교**임을 표기한다.8시간 관측을 시간별 관측으로 가장하거나, 보간으로 정밀한 실제 스타 이력을 만들어내지 않는다. 화면에 ‘정확히 최근24시간+N’이라는 문구는 쓰지 않는다.

정해진 회차에서 다시 계산해도 상위5개가 그대로일 수 있다. 순위 변화 자체를 목표로 삼거나 임의 순환하지 않는다.

## 발굴에서 독립된 관측 흐름

1. 다음 회차 T의 직전1시간에 관측을 시작한다. 예를 들어08시 집계는07~08시에 수집한다.
2. 시작 시점에 공개·저장소·현재 알려진 스타 구간에 맞는 **대상 목록과 저장소 연결을 고정**한다. 수집 중 새로 발행된 제품은 이 회차 대상에 추가하지 않는다.
3. 기존 GraphQL 묶음 조회와 collector 인증·quota 처리를 재사용해 대상 저장소를 관측한다. 성공/실패와 실제 관측 시각을 관측 전용 표에 기록한다.
4. T에 회차를 닫는다. 마감 후 늦게 도착한 응답은 닫힌 회차를 수정하지 못한다. 실패·누락 표본은 이전 값을 성공으로 복사하지 않는다.
5. T 회차와 T−24시간 회차의 **같은 제품·같은 저장소 연결**의 성공 관측을 비교한다. 관측 간격23~25시간 조건을 다시 확인하고+10 이상·스타 구간 등을 적용한다.
6. 공개 읽기는 닫힌 회차 ID와 고정된 정책으로만 조회한다. 새로운 발굴·현재 products.stars 변화·관리자 정책 변경은 이미 닫힌 회차의 계산에 소급 적용하지 않는다.
7. 차단·삭제·공개 범위 변경 제품은 기존 공개 안전 조건에 따라 즉시 숨긴다. 이 예외를 제외한 순위는 다음 회차 전까지 고정한다.

관측 job을 기존 scheduler에 별도 등록하고 crawler의 별도 `stars` lane으로 처리한다. 기존 M3 주/mini 예비의 역할 lease·job lease를 재사용한다. 추가 서버·worker 앱을 전제로 하지 않는다. 발굴/본문 수집/심사/발행 job을 호출하거나 새 제품을 발행하지 않는다.

관측 job의 짧은 재개 확인과 묶음 처리는 수집 창 안에서만 GitHub 요청을 한다. 창 밖에서는 관측 대상 GitHub 요청을 하지 않는다. 한 번에50개, 제한된 작업 시간, quota 대기와 마감 시간을 지킨다. 역할 전환 시 같은 회차를 이어받고 중복 행은 만들지 않는다. 실제 수집 예산·재개 간격은 PR02에서 기존 job 엔진의 continuation/대기 규칙과 맞추며8시간 회차를 시간별 수집으로 바꾸지 않는다.

기존 `product-stars-refresh`의20시간 조회와 products의 현재/직전 스타 컬럼은 기존 화면에 계속 사용한다. 새 관측 job은 관측 전용 이력에 기록한다. 기존 writer를 단순히8시간으로 당기면 `stars_at`이 계속 새로워져20시간 baseline 이동 조건이 성립하지 않는 문제가 있으므로, 해당 writer의 주기를 무작정 변경하지 않는다. 새 급상승 카드는 회차 관측값을 사용한다.

## 필요한 DB 스키마: 우선2개 표

| 표 | 책임과 필수 내용 |
|---|---|
| `product_star_observation_runs` | 회차 ID/예정 집계 T/수집 시작·마감/상태/대상·성공·실패 수/고정 정책 버전·내용. 예정 집계 시각 unique. 상태는 preparing → collecting → closed 또는 failed |
| `product_star_observations` | 회차 ID+제품 ID를 고유키로 고정 대상 행 생성. 저장소 식별자/관측 스타/실제 관측 시각/ok·missing·blocked 등 상태/archived/오류 분류. 회차와 제품 조회에 필요한 인덱스 |

대상은 관측 행의 pending 상태로 미리 고정할 수 있어 별도 대상 표는 필요 없다. 기록은 유효한 job/role lease와 대상 제품·저장소 연결을 확인한 트랜잭션으로 저장한다. 성공 행은 기존 products의 인증·편집 정보와 분리한다.

회차가 닫힌 뒤 정책과 관측이 불변이면 두 회차에서 순위를 재현할 수 있다. **초기에는 별도 순위 결과 표 없이2개 표로 시작**하고, 홈·모두 보기 읽기의 회차 ID를 캐시 키에 포함한다. 관측·회차는7일 보관하며 먼저 닫힌 오래된 회차를 기존 maintenance에서 제한된 묶음으로 정리한다.7일은3회×7일의 비교·문제 조사에 필요한 초기 범위다.

관측 실패가 많으면 성공/대상 수와 집계 지연을 표시한다. 해당 회차에 비교 가능한 결과가 없으면 자료 부족을 보여준다. 이전 회차를 현재 회차의 결과로 표시하거나 관측 실패 값을0으로 취급하지 않는다.

GitHub는 인증 방식과 질의 비용에 따라 API 한도를 적용하며 응답의 remaining/reset 정보를 사용하도록 안내한다. 새 job도 기존 quota 처리를 재사용한다. [GitHub 공식 API 한도 문서](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)

책임: PR03의 계산 의미를 제목·카드·설명·모두 보기에 일관되게 표시한다. PR02→PR03 이후 전환한다.

- 관련 파일: `app/page.tsx`, `components/home/CompactRow.tsx`, `components/home/CompactCard.tsx`, `components/home/MethodologyDialog.tsx`; 필요하면 전용 `components/home/StarGrowthMetric.tsx`만 추가.
- 제목 **전일 대비 스타 급상승**. 설명 **스타50~1,999개 · 전날 같은 시간대보다10개 이상 증가 ·8시간마다 갱신**.
- 집계 기준 **10월12일08시 · 다음16시**. 카드 **★947 · 전일 대비+135**는 표기 예시이며 실제8시간 회차 자료가 아니다. 실제 측정시각과 명목24시간/실측23~25시간 조건은 펼친 집계 설명에 표시한다.
- 자료 부족/집계 지연/관측 성공률을 숨기지 않는다. 과거 결과를 현재 회차로 가장하지 않는다. 상위5개와 모두 보기의 정책이 같다.
- 전체 카드의 기존 `StarMetric` 의미를 바꾸지 않고 새 상승 카드에 필요한 표기만 추가한다.

## 실행·검토 순서

PR01은 독립 진행 가능하다. PR02를 먼저 배포해 이력을 쌓고, PR03 및 PR04는 순서대로 연결한다. PR01/PR04가 함께 건드리는 `app/page.tsx`와 `CompactCard.tsx`는 오케스트레이터가 순차 통합해야 한다. 공개 UI를 자료 축적 전에 전환하지 않는다.

사용자가 기능 테스트를 직접 한다. 새 테스트 작성·로컬 테스트/빌드/E2E를 계획에 추가하지 않는다. 기존 기대가 의미 변경으로 달라지면 필요한 최소 수정만 하고, 저장소의 최신-base 필수 원격 CI는 유지한다. 코드 리뷰·diff 검사·마이그레이션 적용 상태·운영 읽기 확인과 사용자 확인을 구별해 기록한다.

## 검토한 대안

- 기존 두 관측을 유지하고 설명만 수정: 코드가 가장 적지만 전일 같은 시간대와8시간 고정 회차를 만들지 못한다.
- 매시간 이력과24시간 추정치: 더 자주 바뀌지만 후보3,556개 기준 하루85,344관측이며 사용자가 자원 대비 효용을 이유로8시간을 지정했다.
- **8시간 독립 회차의 전일 동시간대 비교(추천)**: 후보·기준·결과가 고정되고 이력2개 표로 재현 가능하다. 정확한 이벤트 기반24시간 총계와는 관측 오차를 구별해야 한다.
