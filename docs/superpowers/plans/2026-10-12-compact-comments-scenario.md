## 목표와 범위

상세페이지의 README·업데이트 아래에서 댓글을 읽고, 약48px의 한 줄 작성 진입을 누르면 필요한 시점에만 작성창을 펼친다. 비로그인은 기존 로그인 화면을 거쳐 같은 프로젝트의 댓글 위치로 돌아온다. 접수 결과에 따라 공개 목록, 내 댓글, 오류 복구 화면으로 이어진다. 기존 흰색·빨간색 스타일과 상세페이지의 다른 영역은 유지한다.

기존 공개 계정·로그인·댓글 API·검토·GitHub outbox를 재사용한다. 새 DB 스키마, 인증 앱, 키 등록, 워커, 실시간 연결은 필요하지 않다. 스타 권한/동작 변경, 답글·좋아요·수정·삭제, 전체 상세페이지 재디자인은 이번 범위에 포함하지 않는다. 현재 GitHub 로그인에 있는 스타 권한 동의는 기존 계약을 유지한다.

현재 확인한 코드에서 공개 목록은 최대50개, 내 댓글은 최대100개다. 공개 개수는 배열 길이가 아니라 동일한 공개 조건으로 집계해야 한다. 공개는 `accepted`이면서 제품이 `banned`가 아닌 경우이며 `held`·`rejected`는 작성자와 관리자에게만 보인다. 제목은 API 필수 필드이므로 입력 UI를 없애더라도 전송 계약을 보존한다.

## PR01 — 댓글 영역 통합·작은 목록·정확한 공개 개수

**결과:** 상세페이지에서 댓글 헤더, 전체/내 댓글, 작은 목록을 한 영역으로 읽을 수 있다.

- 상세페이지에서 폼과 목록의 중복 테두리·제목·간격을 정리한다. `#feedback`은 통합 영역에 한 번만 둔다. 작성창 접힘은 PR02에서 적용한다.
- 공개 목록은 로그인 없이 읽을 수 있다. 기본3개, 본문2줄 미리보기, 글별 펼치기, 목록 더보기를 제공한다. 작성자·분류·작성일·원문 링크는 유지한다.
- 공개 GET 응답에 `total`을 추가한다. 기존 `feedback` 배열과 정렬·조회 제한은 유지하며 집계에도 목록과 같은 공개/제품/작성자 존재 조건을 적용한다. 내 글·검토 중·공개 거절 글을 공개 개수에 더하지 않는다.
- 현재 가져온 목록을 펼치는 기능으로 한정한다. 제한을 넘으면 공개는 `최근 50개`, 내 댓글은 `최근 100개`임을 표시한다. 제한된 목록을 전체 보관함처럼 안내하지 않는다.
- 로딩·빈 목록·조회 실패·다시 불러오기를 구분한다. 오류가 난 상태를 댓글0개로 표시하지 않는다.
- 공통 `FeedbackItem`을 사용하는 접수 원문·관리자 화면의 본문은 계속 전체 표시한다. 상세페이지에서만 축약한다.

**주요 파일:** `app/p/[slug]/page.tsx`, `components/product-detail/FeedbackList.tsx`, `lib/domain/feedback/repository.ts`, `app/api/products/[slug]/feedback/route.ts`. 필요할 때만 작은 `FeedbackSection.tsx`를 추가한다. 공개 GET을 가정한 기존 테스트/fixture는 변경된 응답에 맞춰 보정한다.

**완료 기준:** 0개/3개 초과/50개 초과의 표시가 정확하고, 전체·내 댓글의 공개 권한이 유지되며, 원문·관리자 본문이 잘리지 않는다.

## PR02 — 한 줄 작성 진입·로그인 후 복귀·본문 중심 작성

**결과:** 평소에는 한 줄만 보이고, 작성할 때만 같은 위치에 입력창이 열린다.

- `댓글 남기기…` 진입을 약48px로 만든다. 로그인 상태면 인라인 작성창을 펼치고 본문에 포커스를 둔다. 로그인 상태 조회 실패는 별도 재시도 안내로 표시한다.
- 비로그인은 `returnTo=/p/{slug}#feedback`을 쓰는 기존 로그인으로 이동한다. 현재의 잘못된 `이메일 로그인` 전용 문구를 실제 로그인 진입에 맞게 바꾼다.
- 해당 프로젝트의 작성 진입에서 로그인한 경우에만 작성 의도를 저장·소비하여 복귀 후 한 번 자동으로 펼친다. 일반 로그인, 인증 취소·실패에서는 자동 작성이나 제출이 발생하지 않는다. 기존 sessionStorage 초안과 안전한 returnTo 처리를 재사용한다.
- 별도 제목 입력을 없앤다. 새 초안의 제목은 본문 첫 비어 있지 않은 줄을 공백 정리 후120자 이내로 생성한다. 본문 한도5000자, 질문·오류·제안 분류, 서비스 공개 동의를 유지한다. 로그인으로 공개 동의를 자동 선택하지 않는다.
- 기존 저장 초안의 제목·본문·requestId는 실제 편집 전까지 그대로 유지한다. 편집하면 새 requestId와 파생 제목을 사용한다. 제목 생성이 기존 링크 개수 검토에 주는 영향을 확인하며 검토 정책 변경은 이 PR에 섞지 않는다.
- 취소하면 입력창만 접고 초안은 유지한다. 다시 열면 복원한다. 접수 중에는 폼이 접히거나 중복 제출되지 않게 한다.
- 기존 E2E의 항상 펼쳐진 폼·제목 입력·제출 버튼 선택자를 새 진입 흐름에 맞춰 보정한다. 본문 보존·동일 요청 재시도 검증 의도는 유지한다.

**주요 파일:** `components/product-detail/FeedbackForm.tsx`, PR01의 댓글 영역 연결부, `tests/e2e/product-feedback.spec.ts`. 로그인 페이지/API/OAuth callback은 기존 기능으로 충분하면 변경하지 않는다.

**완료 기준:** 시안의 비로그인→로그인→동일 위치 복귀, 로그인 상태→바로 작성, 취소→재열기 흐름이 연결된다. 작성은 필수 동의·본문이 있어야 가능하다.

## PR03 — 접수 결과·내 댓글·실패 재시도 연결

**결과:** 등록 직후 서버의 실제 접수 상태가 화면에 반영되고 실패 시 작성 내용이 남는다.

- 접수 중 버튼/편집을 잠그고, POST 응답의 실제 댓글을 폼과 목록에 전달한다. 기존 제출 이벤트를 확장하는 등 최소한의 연결을 사용하고 새 전역 상태 시스템은 만들지 않는다.
- `accepted`: 작성창을 접고 공개 완료 안내·최신 댓글·원문 링크를 표시한다. 응답 댓글을 ID로 중복 제거하여 반영하고 공개 개수는 GET으로 재동기화한다.
- `held`: 작성창을 접고 `검토 중` 안내와 내 댓글로 전환한다. 공개 목록·공개 개수에는 넣지 않는다.
- `rejected`: `공개되지 않음`을 명확히 표시한다. 동일 요청 재조회가 rejected를 반환해도 공개 성공으로 안내하지 않는다.
- 네트워크/서버 실패: 작성창·본문·requestId를 보존하고 같은 요청으로 다시 등록한다. 로그인 만료는 초안을 보존한 재로그인으로 연결한다. 내용 변경 때만 새 requestId를 사용한다.
- 이미 접수된 요청을 다시 확인하는 경우 중복 댓글/개수 증가가 없게 한다. 접수 성공 뒤 목록 재조회만 실패하면 접수 성공과 목록 갱신 오류를 따로 표시한다.

**주요 파일:** `FeedbackForm.tsx`, `FeedbackList.tsx`, PR01의 연결부. POST 계약·CSRF·작성자 서버 결정·검토·중복 제출 방지는 유지한다. `/feedback/[id]` 원문과 기존 개인정보 접근 제한도 유지한다.

**완료 기준:** 시안의 공개 완료/검토 중/실패가 실제 서버 응답과 일치하고, 실패·새로고침·재시도에서 초안과 중복 방지 계약이 보존된다.

## PR04 — GitHub 전달 옵션·상태·제작자 설정 축소

**결과:** 서비스 댓글이 기본이고 GitHub 전달은 연결된 프로젝트에서 선택할 때만 추가 공간을 쓴다.

- 제작자가 수신 저장소를 연결한 프로젝트에서만 작성창 안에 접힌 GitHub 전달 옵션을 표시한다. 기본은 전송하지 않음이며 별도 공개 동의가 있어야 선택할 수 있다.
- 미연결 프로젝트에서는 큰 GitHub 사용 불가 안내를 없앤다. 서비스 댓글 접수는 그대로 가능하다.
- `앱 봇의 공개 이슈로 전달`되는 기존 방식을 정확히 설명한다. 작성자 본인 GitHub 계정 명의로 이슈가 생긴다고 안내하지 않는다.
- 일반 서비스 접수/공개 상태와 GitHub 전달 상태를 구분한다. 연결된 글에는 작은 상태 표시와 확인된 이슈 링크를 제공하고 기존 대기·확인 중·재시도·중지·취소 상태를 유지한다. 내부 오류 코드를 상세페이지 기본 본문에 길게 노출하지 않는다.
- 제작자 GitHub 수신 설정 링크는 댓글 헤더의 작은 메뉴로 옮긴다. 수신 설정 페이지의 기존 권한 검증과 outbox/웹훅/워커는 변경하지 않는다.
- 좁은 모바일 화면, 키보드 포커스, 펼침 버튼의 상태 표시, 접수 안내 접근성을 최종 정리한다.

**주요 파일:** `FeedbackForm.tsx`, `FeedbackList.tsx`, `app/p/[slug]/page.tsx` 또는 PR01의 통합 영역. 공통 원문/관리자용 전달 정보는 불필요하게 축소하지 않는다.

**완료 기준:** 연결/미연결 프로젝트 모두 댓글을 작성할 수 있고, GitHub 전달을 선택하지 않으면 전송되지 않는다. 별도 동의·기존 전달 상태·제작자 설정 접근이 유지된다.

## 순서·충돌 관리·검증

기본 병합 순서는 **PR01 → PR02 → PR03 → PR04**다. PR02~04가 같은 폼/목록을 수정하므로 구현을 병렬로 맡기더라도 같은 파일을 동시에 수정하지 않는다. 후속 작업은 앞 PR의 인터페이스가 확정된 뒤 시작한다. 서브에이전트를 요청받으면 모델은 `gpt-6.1-sol`, reasoning effort는 `xhigh`를 사용한다. 이번 계획 작성에서는 서브에이전트를 실행하지 않았다.

사용자가 화면 기능 테스트를 직접 진행한다. 새 자동 테스트 체계는 만들지 않고, 변경으로 깨지는 기존 테스트/fixture는 해당 PR에서 함께 보정한다. 구현 전 설치된 `node_modules/next/dist/docs/`의 해당 가이드를 읽는다. PR별 코드 리뷰와 저장소의 기존 필수 CI `check`는 통과해야 하며, 최신 base 기준으로 병합한다. 계획 작성 단계에서는 테스트·빌드·운영 제출을 실행하지 않았다.

사용자 확인 항목은 비로그인/로그인 작성, 인증 취소·복귀, 취소 후 초안 복원, 공개/검토 중/공개 거절, 접수 실패·동일 요청 재시도, 50개 초과 개수, 내 댓글 접근 제한, GitHub 연결/미연결·별도 동의, 모바일 배치다. 실제 GitHub 전송 성공은 연결된 테스트 프로젝트의 이슈로 확인하며 로컬 시안의 동작을 성공 증거로 쓰지 않는다.

2026-10-13에 네 PR을 순차 병합하고 최종 main의 검증된 같은 이미지로 두 운영 웹을 배포했다. 기존 feature flag·키를 유지하고 실제 컨테이너/공개 health·상세 HTML/API를 확인했다. DB migration·워커 재배포·플래그/키 변경은 없었다. 사용자 화면 작성·인증 복귀·실제 GitHub 전달 확인은 남아 있으며 [배포 기록](../../operations/2026-10-13-comments-production-rollout.md)의 실제 확인 범위를 따른다.
