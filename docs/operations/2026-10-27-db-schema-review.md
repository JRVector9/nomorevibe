# NoMoreVibe DB 개선 공동 검토

2026년10월27일. 성능·운영 호환성 서브에이전트2개와 Claude CLI의 **Claude Fable 5.1 / xhigh**를 함께 사용했습니다. Fable은 실제 모델 ID `claude-fable-5-1`로 응답했고6분43초 걸렸습니다. 결과를 제가 소스 근거와 대조했습니다.

**현재는 SQL 복구가 우선입니다. 스키마를 크게 바꾸거나 커넥션부터 늘리는 것은 권하지 않습니다.**

운영 DB의 예상 실행계획(EXPLAIN, ANALYZE 미실행)에서 후보별로 모델 요청 이력 검색이 반복되는 구조를 확인했습니다. 현재 수정은 종료되지 않은 요청만 한 번 추려 후보를 확인합니다. 후보를 변경하기 직전에는 다시 조회하여 진행 중이거나 종료가 불확실한 요청을 보호합니다. 검토 중 예약 만료의 판단 시각이 달라지는 경계 조건을 찾아 기존 보호 기준을 유지하도록 보완했습니다.

| 순서 | 변경 | 결정 |
|---|---|---|
|1|반복 검색을 제거하는 SQL|PR693 병합·필수 CI 성공·운영 18앱 반영 완료|
|2|필요한 작은 부분 인덱스|기존 활성 요청 인덱스와 겹치는지 확인 후 결정|
|3|후보 ID로 직접 찾는 검색용 매핑|반복 사용 필요가 확인되면 별도 PR로 설계|
|보류|커넥션 확대|커넥션 대기 증거가 확인될 때 검토|
|보류|활성 업무·완료 이력의 물리적 분리|이번 장애보다 변경 범위가 커 지금은 제외|

단순히 원본 요청에 후보 ID 컬럼을 추가하는 안은 주의가 필요합니다. 전체 요청 행으로 만든 감사 해시가 바뀌고, 수정이 금지된 완료 이력의 일괄 채우기도 막힙니다. 또한 fallback의 논리 투표 ID와 실제2차 검수 행 ID는 다를 수 있습니다.

장기적으로는 원본 요청을 그대로 두고 `request_id → candidate_id / root_vote_id / second_review_id`를 연결하는 검색용 매핑을 비교할 가치가 있습니다. 다만 이 매핑이 없거나 원본과 다르면 기존의 보수적인 보호 판정을 유지해야 합니다. 원본 요청의 상태와 예약 시각이 계속 최종 기준입니다. Oracle·재현 작업·복제 권한과 데이터 적용 순서도 별도로 검토해야 합니다.

Claude 제안도 그대로 채택하지 않았습니다. 단일 검색이 몇ms면 끝난다는 추정은 실측이 없어 제외했고, 생성 컬럼을 바로 추가하는 안은 감사 해시와 이력 변경 제한을 고려해 보류했습니다. 추가 UNION 최적화도 현재 수정 후 병목이 남는지 확인한 뒤 판단합니다.

이번 검토에서 스키마·인덱스·과거 데이터는 변경하지 않았습니다. 실제 복구 확인은 기존 대기76건의 정리, 근거 갱신, 새 세대 재등록, 실제 모델 판별 완료를 각각 나누어 확인합니다. 시간당3,000건 수집도 설정 목표와 실제 시간창 측정을 구분합니다.

참고: [PostgreSQL 부분 인덱스](https://www.postgresql.org/docs/current/indexes-partial.html), [Fable5.1 공식 모델 ID](https://platform.claude.com/docs/en/models/fable-5-1/overview), [SQL 복구 PR693](https://github.com/JRVector9/nomorevibe/pull/693).
