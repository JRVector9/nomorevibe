# 탐색의 반복 집계 시간 초과

기준 main `351bbf5e`, 별도 브랜치 `fix/admin-discovery-error-20261113`. 원본 작업 폴더와 기존 탐색 개선 브랜치를 보존했다. 운영 SQL·컨테이너 로그·이미지 정보는 읽기만 했으며 운영 DB·설정·서비스를 변경하지 않았다.

## 확인한 원인

2026-11-13 19:59:02 UTC에는 네 탐색 잡 모두 `last_error=NULL`이었지만 19:59:34에 `crawl-ko-apply`가 다시 실패했다. `last_error`의 SQLSTATE는 **57014**이고 쿼리는 `readReviewBacklogInTransaction`의 저장 대기량 집계였다. 수집이 성공과 실패를 번갈아 기록하므로 한 번의 정상 스냅샷으로 회복을 선언할 수 없다. 화면의 「오류 있음」을 지우는 변경은 하지 않는다.

최근 60분/최대 12,000줄의 M3 crawler 로그 표본에서 같은 집계의 `job.failed`가 일반 탐색 21회, 한국어 적용 5회였다(18:59:58–19:59:34 UTC). 별도 GitHub 검색 요청의 부분 실패와 이 DB 집계 실패를 구분했다. 실행 이미지의 OCI revision은 M3·mini 모두 `351bbf5e`로, 이전 탐색 개선 미배포가 이번 오류의 원인은 아니었다.

운영 `EXPLAIN`(실행 없는 계획 조회)은 문서 약 80만 행과 후보 약 81만 행을 `lower(repo)`로 비교하는 전체 anti join, 최근 5분 발견량에 frontier 약 81만 행의 병렬 전체 스캔을 보였다. 후보의 `lower(repo)` 인덱스와 frontier 발견 시각 인덱스가 없었다. 세부 진단은 `/tmp/nmv-discovery-error-evidence-20261113/{jobs.private.json,events.safe.json,plan.safe.json}`에 있다. 운영에서 대형 `EXPLAIN ANALYZE`를 실행하지 않았다.

검증 이력: 초기 읽기 도구 재사용으로 `/tmp/nmv-models-postdeploy-health-20261112/runtime.safe.json`이 이번 11월 13일 관측으로 갱신됐다. 이 파일을 11월 12일 원본 증거로 사용하면 안 된다. 이전 바이트의 백업이 없어 복원하지 않았으며, 이번 분석에는 위 전용 증거 경로를 사용한다.

## 변경

문서와 후보의 바이트가 같은 저장소를 먼저 제외하고, 남은 대소문자 변형만 기존과 같은 `lower(repo)` 비교로 확인한다. 이 과정에서 대부분의 과거 저장소를 두 번 소문자로 바꿀 필요가 없어진다. 0185는 후보의 대소문자 무시 조회 인덱스와, alias·원본 재수집 신호를 제외한 frontier 발견 시각 인덱스 두 개를 추가한다.

저장소 중복 제거, 미판정 문서 포함, 완료 후보 제외, 진행 중 원본 수집 포함, 미래 발견 제외, 시간당 발견 한도와 기존 3초 기한·읽기 실패 시 신규 적재 금지는 유지한다. 후보 인덱스는 non-unique라 과거 대소문자 변형 데이터를 거부하지 않는다.

## 실제 검증

- Node 24.18.0: 관련 단위 5파일 **75건**, 전용 PostgreSQL 17/pgvector DB 통합 3파일 **31건** 통과. 통합은 일반 탐색 22건, 한국어 탐색 7건, 저장량 집계 2건이며 대소문자 변형·중복 문서·완료/활성 후보 공존·alias·refresh·미래 시각 회귀를 포함한다.
- Next route type 생성, 전체 TypeScript 검사, 변경 TS 3파일 ESLint, diff 공백 검사 통과. 전체 unit/DB·build는 실행하지 않았다.
- 초기 단위 병렬 실행은 공통 설정 import hook 시간 초과 2건/73건 통과였다. `--maxWorkers=1`로 재실행해 75건 통과했고 Node 24에서도 재확인했다. 초기 통합 실행의 샌드박스 subprocess 제한 실패는 승인된 전용 DB 실행으로 해결했다.

전용 DB의 별도 축약 스키마에 후보 800,000행·문서 800,100행·frontier 810,000행을 넣은 비교다. 운영 데이터나 운영 처리율 측정이 아니다. 동일 DB 기준 시각을 고정하고 세 집계값이 같은지 직접 검증했다.

| 집계 시간 | 586.8ms | 568.6ms | 217.3ms |

두 인덱스 생성 합계는 같은 전용 fixture에서 2.29초(별도 ANALYZE 시간 제외)였다. 축약 테이블과 당시 캐시 상태에서 한 번 측정한 참고값이며 운영 잠금·생성 시간을 보장하지 않는다. 결과와 scratch 스크립트는 같은 evidence 폴더의 `benchmark.safe.json`·`benchmark.mjs`에 보존했다.

## 운영 적용 후 남은 확인

0185는 저장소의 표준 트랜잭션 `CREATE INDEX` 경로를 사용하므로 생성 중 대상 표 쓰기 잠금이 있다. 운영 생성 시간은 미측정이다. 정식 migration·필수 CI·배포 후 인덱스 존재와 실행 버전을 확인하고, 자연 실행에서 두 잡의 성공 시각 진행 및 같은 57014 오류 재발 여부를 관측해야 한다. 오류·성공 기록이나 커서를 초기화하지 않는다. GitHub Actions의 계정 결제/사용 한도 차단은 코드 테스트 실패와 구분하며 필수 CI를 우회하지 않는다.
