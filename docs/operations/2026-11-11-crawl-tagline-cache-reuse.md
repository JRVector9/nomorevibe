# 수집 소개 생성의 빈 캐시 반복 선택

## 운영 실측

2026-11-11 12:53:21 UTC에 운영 DB를 명시적인 읽기 전용 트랜잭션으로 조회했다.
문장 제한은 4초였고, 운영 행 수정·잡 실행·모델 호출은 하지 않았다.
조사 당시 운영 및 PR 기준 코드는 `475a77a0265ea8c74b241a0bbacd1a7477ce3df9`다.

| 관측 | 값 |
| --- | ---: |
| 자동 소개 대상인 `no_description` 보류 후보(문서 보유·사람 작성 제외) | 320 |
| 선택 술어를 통과하는 후보 | 224 |
| 원본과 처리 시각이 밀리초 이하에서만 다른 후보 | 136 |
| 선두에서 반복 선택된 후보 | 12 |
| 로그의 `committed / crawl-tagline / reuse` 이벤트 | 12,576 |

로그 구간은 12:48:21.012~12:53:21.716 UTC(약 5분)다. 이벤트는 동일한 후보 ID 12개에서 발생했다.
이 구간에 완료된 5개 회차의 `written`, `empty`, `failed`, `released`는 모두 0이었다.
이 숫자는 모델 호출 횟수가 아니라 **캐시 재사용 저장 이벤트**다.

선두 12개 모두 다음 조건을 만족했다.

- 현재 증거로 다시 계산한 해시가 저장된 `source_hash`와 같다.
- 저장된 소개는 빈 문자열이고 `error_code`는 없다. 시도 횟수는 1이다.
- 페이지 제목·본문·README 증거가 없다.
- 원본 시각을 JS Date로 바꿨다가 기록하면 시각 불일치 조건이 계속 참이다.
- DB 원본 시각을 SQL로 그대로 복사한다고 가정하면 불일치 조건이 거짓이다.

예를 들어 원본 `06:03:45.755064`는 처리 시각 `06:03:45.755000`과 다르다.
원본의 마이크로초가 JS Date를 거치며 사라진다. 재사용 저장을 반복해도 차이가 남는다.
원본 데이터·로그 전체는 커밋하지 않고 로컬 조사 영수증으로 보관한다.

## 원인과 수정

`pendingTaglinePredicate`는 `document_at IS DISTINCT FROM fetched_at`이면 다시 선택한다.
`recordTaglineResult`의 일반 저장 경로는 JS Date인 `document.fetchedAt`을 기록했다.
빈 캐시 재사용 시 후보 상태·정렬에 쓰는 후보 시각·attempts가 그대로이므로 선두가 유지된다.
잡의 반복문은 캐시를 재사용한 후보를 제외하지 않아 같은 회차에서 계속 집었다.

1. 이미 `FOR SHARE`로 잠근 문서의 `fetched_at`을 SQL 하위 쿼리로 직접 복사한다.
   일반 성공·실패·재사용 모두에 적용한다. 기존의 잘린 빈 캐시는 다음 재사용에서 바로잡힌다.
   별도 데이터 보정이나 마이그레이션은 필요하지 않다.
2. 회차에서 다룬 모든 후보 ID를 다음 선택에서 제외한다. 계속 선택 가능한 행이 생겨도
   그 후보가 같은 회차의 남은 시간을 독점하지 않게 한다. 모델 순위 대체와 빈 답의 두 번째
   질문은 한 후보 처리 안에 있으므로 그대로 실행된다. 다음 회차의 선택은 정상적으로 허용한다.

비교 술어를 밀리초로 잘라 맞추지 않는다. 같은 밀리초 안에서 실제 원본이 바뀐 경우도
선택해야 한다. 예약된 모델 결과의 별도 저장 경로는 이미 원본 SQL 시각을 보존한다.
기존 잠금·lease·CAS·사람 작성 우선권·발행 검증·재시도 예산은 유지한다.

`product-tagline-ko`의 한국어 소개 번역은 별도 작업이다. 이 결함은 모델 호출 및 용량 장부
처리 전의 빈 캐시 재사용 분기에서 발생하므로 장부의 logical key 집계나 호출 백오프로
설명하거나 막을 수 없다. 한국어 번역의 결과 저장 누락 가능성은 이 PR의 범위에 포함하지 않는다.

## 검증과 적용 후 확인

- 수정 전: 마이크로초를 포함한 첫 성공·실패·기존 캐시 재사용 통합 테스트 3개가 시각 불일치로 실패.
- 수정 전: 반복 선택 방어 단위 테스트가 `repeated_candidate_selection`으로 실패.
- 수정 후: 관련 단위 테스트 2파일 53개 통과.
- 수정 후: 소개 생성·저장 fencing·입력 단계 잠금·용량 dispatch 통합 테스트 4파일 70개 통과.
  빈 캐시 12개 뒤의 재시도 후보가 실제 DB에서 `approved`로 진행하는 회귀 테스트를 포함한다.
  같은 밀리초 안의 실제 원본 변경도 다시 선택되는지 확인한다.
- `next typegen`, `tsc --noEmit`, 변경 파일 ESLint 통과.
  전체 수동 unit·DB·종합 검사는 저장소 정책에 따라 반복하지 않는다.

이 기록은 PR 검증이며 **운영 배포 후 복구 완료 기록이 아니다**. 운영 배포는 하지 않았다.
나중에 배포하면 동일 후보의 연속 재사용 감소, 정확한 시각 일치, 뒤 후보 처리 진행을 확인한다.
소개 생성 후에도 기존 발행 관문을 통과해야 하므로 후보 수를 추가 발행 보장량으로 해석하지 않는다.
