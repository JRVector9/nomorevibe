검수 본문은 두 차례 모두 약 11초, 운영 홈은 2.84~5.46초가 걸렸습니다. 요청함·콘텐츠·설정은 약 0.34~0.37초였습니다. 메뉴·URL 반응과 실제 본문 준비를 구분하고, 느린 화면의 조회 범위와 대기 경계를 먼저 줄이는 접근이 적절합니다.

우선 1 · 조회 범위

필요한 데이터부터 읽기

기본 화면에서 사용하지 않는 대량 이력과 탭 공통 조회를 분리합니다. 검수의 필터별 전수 판정 범위를 줄이고, 실제 시간을 나눠 잽니다.

우선 2 · 대기 경계

핵심 본문부터 사용 가능하게

현재 골격을 유지하고, 전체 흐름·현재 상태와 부가 이력·장비·변경 정보를 독립적으로 보여줍니다.

우선 3 · 갱신 비용

현재 업무에 맞춰 다시 읽기

실시간 화면·과거 이력·설정의 갱신 목적을 구분하고 탐색·수동·자동 갱신의 경합을 제어합니다.

구현 전 검토 · 원인별 시간 기여는 아직 분리하지 않음

기존 loading을 활용하고, 데이터를 기다리는 위치를 조정합니다.

페이지 수준 loading.tsx는 이미 있습니다. 독립된 서버 패널을 각각 Suspense로 감싸면 준비된 부분을 먼저 보여줄 수 있습니다. 같은 구간의 layout 대기는 페이지 loading 경계 밖이므로 별도 확인이 필요합니다. layout과 page의 조회 시간을 직렬로 더해 계산하지 않습니다. Next 공식 loading 문서 ↗

공통 관측 reader는 완료 이력을 최대 50,001행까지 읽고 처리량을 계산합니다. 기본 LLM 시안과 운영 홈 desk는 이 처리량을 쓰지 않습니다. 핵심 스냅숏의 일관성을 유지하면서 고급 차트용 이력만 선택적으로 읽는 안이 우선입니다.

요청함 · 0.35~0.37초개인 원문과 처리 상태의 최신성 유지

현 대표 표본은 빠릅니다. 선택 id 변경 때 같은 목록·count를 다시 읽는 범위는 별도 정리할 수 있습니다. 목록 key와 선택 key를 구분하고, 문의 상세·처리 version은 요청 범위에서 재사용하며 제출 시 최신 CAS를 유지합니다.

SNS는 반환 summary를 쓰지 않아도 전역 summary를 계산하고, 새 랭킹은 쓰지 않는 readiness·preview를 기다립니다. 기존 전체 reader를 보존한 채 얇은 reader·옵션을 검토합니다. 랭킹 지연은 별도 실측하지 않았습니다.

캐시는 표시용 데이터와 조치의 경계를 먼저 정합니다

아래 신규 주기는 검토값 · 적용·효과 검증 전

기존 conveyor·desk 15초, overview·inbox 30초, hourly·신호 60초를 우선 재사용합니다. 검수 membership의 결정 직후 일치 계약은 별도로 유지합니다. 개인 away·세션·키·CSRF·현재 제어 판정은 새 공유 캐시 대상에 넣지 않습니다.

현재 sharedLoader는 TTL이 만료되면 새 조회가 끝나기를 기다립니다. 지난 값을 먼저 반환하는 sharedStale과 동작이 다릅니다. 표시 집계에 SWR을 적용하려면 원본 관측 시각·오래된 값·실패를 구분하고, 조치에 쓰는 최신 원본은 별도로 확인해야 합니다.

대상기준조건·보존할 동작
전체 흐름·공유 desk기존 15초 재사용안쪽의 30·60초 원본 기준 시각도 함께 표시. 모든 항목이 15초 이내 최신이라는 의미로 쓰지 않음.
LLM 표시용 관측필요 시 5~10초 검토불필요한 이력 제거가 우선. 현재 제어 가능 상태·epoch·revision은 조치 서버가 다시 확인.

실패·시각
조회 실패를 성공한 0으로 저장하지 않습니다. replica의 기존 hold 정책과 마지막 성공 기준을 보존합니다. 화면 갱신 시각을 원본 관측 시각으로 대신하지 않습니다.

저장 후 반영
현재 공유 저장소는 get/set 기반입니다. router.refresh()나 revalidatePath()가 이 Map·Valkey 키를 직접 지운다고 가정하지 않습니다.

후속 PR은 3단계로 나눕니다

각 PR의 회귀 범위 확인 후 마지막 단계에서 통합 검증

PR 01 · 조회 범위 축소

현재 화면에 필요한 읽기만 남기기

  • 미사용 처리량·랭킹 preview·SNS summary 분리
  • 검수 필터 선조회·갈래 배열 복사 제거
  • flow 탭·프로젝트 상세 section별 reader 선별

완료 기준
동일 목록·CSV·정렬·판정과 고급 차트를 보존하고 reader별 시간·조회 수·행 수를 전후 확인합니다.

PR 02 · 독립 스트리밍

준비된 업무 패널부터 보여주기

  • 주요 흐름·목록과 보조·개인·고급 패널 분리
  • LLM bootstrap을 실제 Suspense 경계 안으로 이동
  • 한 요청의 같은 Promise·snapshot 재사용

완료 기준
느린 부가 조회 중에도 준비된 핵심 화면이 사용 가능하며, 부분 실패를 정상으로 표시하지 않습니다.

PR 03 · 갱신·재측정

탐색과 자동 읽기의 경합 제어

  • 표시용 캐시·명시적 무효화·원본 시각 계약
  • query별 갱신 주기·탐색 pending 조정
  • TTL 만료·장애·복제지연·다른 웹 변경 검증

완료 기준
저장 직후 일치와 입력·dirty·확인창·숨김 탭 규칙을 유지하며, 오래된 표시 값이 최신 제어 판정으로 쓰이지 않음을 확인합니다.

PR별 범위 회귀·정적 검사 후 마지막 통합 단계에서 전체 unit·DB 검사와 production build의 동일 조건 비교를 수행합니다. 현재 대부분의 자동 갱신은 router.refresh()를 사용합니다. 진행 중 중복 차단은 이미 있으며, 수동 갱신·탐색까지 함께 보는 개선안을 검토합니다. 갱신 구현 ↗

아직 측정하지 않은 것
  • 개발 컴파일·서버 렌더·DB 실행·DB pool wait·네트워크별 ms 기여를 분리하지 못했습니다. 개발 로그에도 route별 compile/render timing이 없었습니다.
  • 동일 호스트의 브라우저가 Tailscale 주소를 사용했습니다. 실제 원격 사용자의 네트워크 왕복 표본이 아닙니다.
  • 본문 확인 후 다음 메뉴로 이동하면서 RSC stream 7건의 tail이 취소됐습니다. 해당 최종 종료 시간은 미측정으로 처리했습니다.
  • RSC 헤더 시간은 Node 측정 시작 기준이고 본문 시간은 브라우저 click 기준입니다. 둘을 빼서 기여 시간으로 계산하지 않았습니다.
  • 2회차도 캐시 TTL을 지났을 수 있습니다. cache hit, cold/warm, p95, 운영 응답 시간으로 해석하지 않습니다.
  • 미리보기에 embedding/rerank health 주소가 없고 고급 probe도 제외했습니다. 관련 연결이 설정된 운영 화면의 추가 비용은 이번 측정에 포함되지 않았습니다.
  • production build·운영 배포·개선 코드 실행은 하지 않았습니다. 예상 개선율·가상 성능 수치는 제시하지 않습니다.
