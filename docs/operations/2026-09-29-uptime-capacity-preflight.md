# 2026-09-29 maintenance 점검 용량 사전 검증

운영 DB의 읽기 전용 표본: 공개 웹사이트 19,365곳, 최근 6시간 미점검 13,976곳,
최근 1시간 점검 905건. 최근 900건의 성공 응답 지연은 중앙값 717ms,
95백분위 2,471ms, 최대 6,091ms였다. 마지막 15건 점검 tick은 5,626ms였다.
기존 한 틱 15건·1분 주기의 산술 상한은 시간당 900건 수준이다. 6시간에 전체를
점검하려면 시간당 3,228건, 분당 약 54건이 필요하다.

기본값 15/3을 유지하면서 maintenance 역할에만 `UPTIME_BATCH_SIZE`(최대 60),
`UPTIME_CONCURRENCY`(최대 6)를 설정할 수 있게 했다. 동일 origin 단일 요청,
한 번에 한 DB 기록, 25초 tick 예산은 유지된다. 전용 DB 통합 시험에서 6개 origin
병렬과 같은 origin 직렬, DB 기록 직렬을 확인했다. 이 수치로 실제 운영 처리량을
보장하지 않는다. 30/4 → 60/6 순서로 배포·관측한 뒤 6시간 backlog가 줄어드는지
확인해야 한다.

로컬 검증: `npx next typegen`, `npx tsc --noEmit`, `npm test`(155파일/1,229건),
`npm run test:integration`(96파일/923건 통과·TODO1), `npm run lint`(오류0,
기존 vendor 경고1), `npm run build`, `git diff --check`가 통과했다. 증량 기능의
단위 시험은 구현 전 7건 실패, 구현 후 7건 통과했다. 통합 시험은 동시 3개 대신
6개를 기대해 먼저 실패했고 구현 뒤 24건 모두 통과했다.
