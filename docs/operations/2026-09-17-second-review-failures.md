## 재현한 직접 원인

1. **Gemma 응답이 심사 JSON 계약을 지키지 않는다.** 운영과 같은 함수·입력·설정으로 현재 실패 행 10개를 선택했고, 입력이 바뀐 1개를 제외한 9개를 직렬 재호출했다. Gemma 26B 6회는 형식 오류 5회/시간 초과 1회, Gemma 31B 3회는 형식 오류 1회/시간 초과 1회/유효 응답 1회였다. 실패 표본을 의도적으로 고른 것이므로 전체 모델 오류율로 일반화할 수 없다.
   - 행 59654(26B), 59655(31B): HTTP 200, finish_reason=stop이지만 content가 `yes`뿐이었다.
   - 행 56165·58994·59909·59474(26B): 서로 다른 승인·거부 JSON 두 개와 설명이 한 응답에 들어왔다. 현재 파서는 첫 `{`부터 마지막 `}`까지 단일 JSON으로 읽으므로 실패한다. 상충하는 결론 중 하나를 임의로 골라 통과시키는 것은 적절한 수정이 아니다.
   - 요청은 이미 `response_format: json_schema`, `temperature: 0`, `enable_thinking: false`를 보낸다. 실제 응답은 이 요청에도 단일 JSON을 보장하지 않는다. 게이트웨이의 옵션 전달/구조화 출력 강제 여부와 모델 자체 문제는 게이트웨이 서버 측 추가 조사가 필요하다.
2. **60초 내 응답이 오지 않는 요청이 있다.** 행 58589·59820 재호출이 각각 60,005ms·60,001ms에서 timeout으로 끝났다(응답 헤더도 확보하지 못함). 다른 이전 timeout 행은 15초에 성공하기도 했다. 응답 지연은 재현했으나 서버 자원 부족·내부 큐 적체 등 더 아래 원인은 이번 증거로 확정할 수 없다.
3. **내용 이해도 문제가 함께 관찰됐다.** 56165 입력에는 제품 URL, 페이지 본문 1,785자, README 2,999자가 있는데 26B 응답은 URL이 없다고 주장하며 상충된 판정을 만들었다. 동일 스냅샷을 GPT-OSS 120B에 보낸 대조 호출은 6,662ms에 유효 JSON을 반환하고 실제 URL/브라우저 게임을 인용했다. 단일 대조 사례이지 모델 전체 정확도 검증은 아니다.
4. 현재 출력 상한 오류 2행도 남아 있다. 클라이언트는 3,000 출력 토큰으로 요청하며 `finish_reason=length` 또는 128KiB 본문 초과를 같은 코드로 처리한다. 원래 실패 응답은 저장되지 않아 이 2행의 정확한 분기는 확정할 수 없다. 재호출은 형식 오류/시간 초과로 바뀌었다.

## 문제를 지속·과장하는 애플리케이션 동작

- `lib/crawl/second-review.ts:384`: timeout 등은 5분, invalid_output 등은 1시간 뒤 재시도한다. 2차 심사에는 횟수 상한이 없어 입력이 유효한 동안 실패 모델을 반복 호출한다. 오류 행을 같은 곳에 덮어쓰므로 DB 행 수만으로 총 실패 시도 횟수를 계산할 수도 없다.
- `lib/crawl/jobs/second-review.ts`: 동시 호출 8개, 작업 예산 108초. 남은 시간이 62초 미만이면 새 호출을 미룬다. 느린 호출과 재시도가 처리량을 떨어뜨리는 구조이며 로그에서도 회차당 35–39개 연기가 관찰됐다. 동시 호출 8개가 서버 지연의 직접 원인인지는 별도 부하 비교가 필요하다.
- 실패/대기 표가 남은 후보는 최종 합의 집계에서 계속 대기한다. 오류를 승인으로 받아 발행하지 않는 보호는 유지된다.
- `recentSecondReviewFailures`는 현재 status를 필터링하지 않는다. 09:48 스냅샷에서 최근 오류 표시 대상 117행 중 **65행은 이미 resolved/superseded**, 실제 failed는 52행이었다. 관리 화면의 “2차 심사가 실패하고 있습니다” 숫자는 현재 실패와 지난 기록이 섞여 있다.
- `invalid_output`은 잘못된 JSON, 필드 오류, 근거 ID 오류 등을 하나로 저장한다. 세부 검증 사유, 요청 시간, finish_reason, 시도 이력이 없어 원래 실패의 상세 추적이 어렵다.

## 권장 보완 순서

1. 현재 실패/재시도 중/종료된 과거 오류를 분리 표시하고, 비밀값과 원문 전체를 제외한 세부 오류·시간·시도 이력을 기록한다.
2. 실패 횟수 제한과 모델별 연속 실패 차단을 추가한다. 상한에 도달하면 사람 검토로 넘겨 대기 반복을 끝내고, 판단 없는 실패를 찬성표로 만들지 않는다.
3. 게이트웨이의 Gemma 구조화 출력 적용 여부를 확인하고 실제 실패 입력으로 재평가한다. Gemma 26B의 임시 제외/교체를 우선 검토하되, 대체 모델 정확도와 독립성 검증 후 적용한다. GPT-OSS 하나를 이름만 달리해 여러 표로 세면 안 된다.
4. 지연 분포와 서버 대기열을 확인한 뒤 동시성/모델별 타임아웃을 조정한다. 타임아웃만 늘리면 작업 예산과 대기열 지연을 함께 악화시킬 수 있다.
