따라서 **그 시간대의 감소는 후속 검수 적체에 연동한 수집 제한이 직접 원인**이다. 토큰 부족이나 최신 탐색의 1시간 휴지를 원인으로 단정할 근거는 없다. 이 원인 판정은 기존 관측의 시점에 한정한다. 최신 [handoff](../CODEX_HANDOFF.md)의 후속 복구 후 현재 상태로 확대하지 않는다.

## 이번에 고친 별도 계측 결함

`seedSearchCycle`은 검색 결과 일부를 정상 삽입한 뒤 5분 상한 또는 worker 예산으로 미완 페이지를 보존할 때, 조기 반환에서 `crawl.seeded` 결과 요약을 누락했다. 그 결과 관리자 수집 활동 누적에는 실제 정상 삽입량 일부가 반영되지 않을 수 있었다. 이 결함은 DB에서 직접 읽은 위 감소 원인과는 별개다.

- 조기 반환에서도 이미 삽입한 신규 수를 정확히 한 번 요약한다. 최신 탐색은 `crawl.seed_latest_scanned`, 전체 탐색은 `crawl.seeded`에 남긴다.
- 검색 요청 수(`searchRequests`), 성공적으로 enqueue까지 처리한 항목 수(`examined`), 그중 기존·중복으로 신규 삽입되지 않은 수(`existing`)를 함께 기록한다. 재개한 저장 페이지는 새 검색을 하지 않았으면 검색 요청을 0으로 기록한다.
- 관리자 수집 활동에 설정/적용 페이지, 신규 허용량, 시간당 상한 대기, 수용 측정 미확인을 표시한다. 설정 페이지와 허용량은 순간값이므로 시간 누적 표시에서 제외한다.
- 원본 검색 결과·커밋 내용·자격 정보는 새 지표에 포함하지 않는다. 기존 페이지/구간 커서, 중복 방지, lease 검증과 정상 저장 순서를 유지한다.

## 3,000건 목표와 선택한 방침

기존 구현은 검색 60초 주기/별도 discovery 줄, fetch 별도 줄·동시성 12, `discover.maxNewPerHour=3000` 기본값/5분당 최대 250건을 이미 지원한다. 저장된 설정이 기본값을 덮으므로 코드 기본값만으로 운영 설정 적용을 주장할 수 없다. 기존 운영 기록의 페이지 10 적용도 이번 세션에서 재확인하지 않았다.

**선택: 기존 적체·쿼터 보호를 유지하고 누락된 계측을 보완한다.** 감소를 막기 위해 검수 대기 500건/5분, 1,000건 강한 압력 기준이나 공급자 cooldown을 해제하면 실제 검수 처리보다 유입만 늘어날 수 있다. 설정/모델 전환과 후속 검수 처리율 검증을 함께 본 뒤 이 기준을 다시 평가하는 것이 가장 영향이 작다. 새로운 PAT·App을 추가하거나 같은 사용자의 토큰을 독립 쿼터로 세지 않았다.

상한 3,000은 달성률 보장이 아니다. 검색 결과의 신규 수율, 원본 HTTP 지연, core 쿼터를 함께 쓰는 다른 작업, 1차·2차 검수 처리율이 모두 조건이다. 검수 모델 전환이 처리량을 자동으로 높인다고 가정하지 않는다.

## 운영 확인의 남은 조건

승인된 릴리스 절차로 이 변경과 검수 경로 변경을 적용한 뒤 완전한 60분 창에서 새 고유 frontier 삽입과 실제 원본 확보를 각각 측정해야 한다. 정시/10분 묶음의 관리자 누적은 정확한 rolling 60분과 다를 수 있으며 신규 원본 행이 유효 본문 수집 성공을 보장하지 않는다. 같은 창의 AI1/AI2 완료·대기량, admission 제한 횟수, 신규 수율, 공급자 rate/auth 대기와 원본 지연을 대조한다. 목표 미달 시 어느 구간이 제한했는지 근거를 보존한다. 운영 적용과 지속 3,000건/시 검증은 남아 있다.
