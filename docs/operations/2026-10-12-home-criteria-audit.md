# 홈 신규·급상승 목록 기준 검토

사용자 요청: 상세 화면 작업 뒤 ‘이번 주 새로 나온 프로젝트’에 오래된 프로젝트가 나오고 ‘지금 뜨는 프로젝트’ 변화가 적은 원인을 검토한다. 이 단계는 읽기 전용 조사이며 순위 기준이나 운영 설정을 변경하지 않았다.

## 결론

- **신규 목록은 이름과 구현이 다르다.** 저장소 생성일 대신 NoMoreVibe 등재·인증일을 사용한다. 운영 상위5개 모두 집계 기간보다 오래된 저장소이고, 조건에 맞는1,307개 중1,289개(98.62%)가 기간 이전에 생성됐다.
- **급상승 수집 정체는 이번 표본에서 확인되지 않았다.** 정상 공개 저장소36,262개 모두 최근24시간 안에 숫자를 갱신했고, 작업 성공·복제본 반영도 확인했다. 현재 순위는 약20시간 간격의 두 관측에서 계산한 일평균 증가량의 고정 상위5개다. 새로고침마다 다른 프로젝트를 보여주는 기준은 없다.
- 급상승의 집계 설명에는 이전의 ‘1일 바닥·2~3일 확인’ 문구가 남아 있다. 실제는20시간 바닥·정상 재조회20시간이다. 최근24시간 공통 시간창의 순위는 아니다.

## 조사 범위와 근거

- 코드 기준: main298eb926(문서 변경), 실제 웹 runtime a91eecf2. 앞선 상세 화면 PR363/364/365와 기록 PR366은 병합됐다. 두 운영 웹에 같은 a91eecf2 이미지가 배포됐다.
- gpt-6.1-sol/xhigh 두 서브에이전트가 신규·급상승 소스를 독립 조사하고 부모가 운영 데이터와 대조했다.
- 운영 mini 웹의 실행 컨테이너에서 **실제 DATABASE_URL / READ_DATABASE_URL**로 각각 REPEATABLE READ, READ ONLY 트랜잭션을 실행했다. 비밀 접속 문자열은 출력·저장하지 않았다.
- 주 DB 표본: **2026-10-12 00:02:30 KST**. 공개 복제본 표본도 같은 시각이며 주 DB의 `pg_is_in_recovery=false`, 공개 읽기 DB의 `pg_is_in_recovery=true`를 확인했다. 복제본 마지막 replay 경과는 약 0.058초이고 두 목록의 주소·순위·숫자가 주 DB와 같았다.
- 공개 홈 HTTP 응답도00:03:13 KST에 읽었다. 급상승5개가 DB 순서·스타·증가량과 일치했고, 신규 영역에서 vm2api/Yielded Auth/Aptos Explorer와 ‘10월11일’ 등재 표시를 확인했다. 이 응답은 `CF-Cache-Status: DYNAMIC`, `Cache-Control: private, no-cache, no-store…`였다. 이번 응답에서 CDN 고정 캐시는 원인으로 보이지 않는다.
- 새 테스트·로컬 테스트·빌드·브라우저 기능 테스트는 실행하지 않았다. 기능 테스트는 사용자 담당이다. PR의 필수 원격 CI는 유지한다.

## 1. 이번 주 새로 나온 프로젝트

### 실제 조건

`app/page.tsx:426` → `getNewThisWeek(5, completedWindows(now).weekStart)` → `lib/domain/products/view.ts:221` → `repository.ts`의 일반 최신 목록.

- 공개 상태 verified/seeded, 기본 공개 범위, 연속 생존 확인 실패 제외.
- 스타50 이상. 정상 GitHub 저장소는 저장소 확인 상태ok가 필요하다.
- `coalesce(verified_at, created_at) >= weekStart`로 거른다. `products.created_at`은 서비스 DB 등록 시각, `verified_at`은 인증 시각이다.
- verified 먼저, 그 안에서 등재 시각 내림차순, 최대5개. 저장소 생성일 정렬이 아니다.
- **종료 경계가 없다.** 완료7일을 쓰는 다른 홈 집계와 달리 오늘 등재된 제품도 들어올 수 있다. 이번 표본에서는 오늘 등재분0개였다.
- 카드 날짜도 `listedAt`을 ‘등록한 날’로 표시한다. 모두 보기 링크는 일반 최신순이다.

`completedWindows`는 한국 시간 오늘00시를 끝으로 직전7일을 계산한다. 월요일부터 시작하는 달력상의 이번 주가 아니다. 이번 표본의 완료 창은 **10월5일00시 이상~10월12일00시 미만 KST**다. 신규 목록은 시작 경계만 적용한다.

## 2. 지금 뜨는 프로젝트

### 실제 조건과 주기

`app/page.tsx:425` → `getPublicList(5, { sort: 'rising', rising: true })` → `repository.ts:164,237,266`.

```text
하루 평균 증가량 = (현재 스타 - 직전 스타)
                  / max(두 관측 사이 일수, 20/24)
```

- 증가량 양수, 현재 스타2,000 미만, 공개 범위·생존 조건 적용, 사라짐 확정 저장소 제외.
- 최신 숫자 관측이 설정된 freshness 기간 이내여야 한다. **운영 설정은7일**이다.
- 일평균 증가량 → 현재 스타 → 등재 시각 → slug 순, 고정 상위5개. 생성일·새 발행·방문 증가·주간 가속도는 조건에 없다.
- scheduler 요청5분, 정상 저장소 재조회20시간. 없음/빈 저장소/차단24시간, 불명확 실패 재시도 최소1시간. crawler가 GraphQL50개 묶음, 최대8묶음, 시작28초·작업40초 예산으로 처리한다.
- 카드의 `+N`은 **두 관측 사이 전체 증가량**이다. 순위를 정하는 하루 환산값과 다를 수 있고 관측 시각은 hover 설명에 있다.
- 조회 실패 시 기존 숫자·증가량을 보존하므로 다음 성공 또는7일 만료까지 과거 상승치가 남을 수 있다. 이번 상위5개는 모두ok, archived=false이며 성공 관측이14.38~19.97시간 전이었다.

### 수집·반영 상태

- 공개 저장소 제품37,479개 중 숫자 관측24시간 내36,269개. 정상ok36,262개는 **전부24시간 내**다. 저장소 확정 답(`repo_checked_at`)은37,479개 모두24시간 내다.
- 숫자가48시간보다 오래된1,165개도 있다. 정상ok의 최신 숫자와 구별해야 한다. 실패/없음/차단 답은 숫자를 갱신하지 않을 수 있으므로 전체 숫자 신선도만으로 정상 수집 실패를 단정하지 않는다.
- `product-stars-refresh`: requested=processed=8,332, pending lock/cooldown 없음, 오류 없음. 마지막 성공10/11 23:59:28 KST, 다음 예정10/12 00:04:18 KST.
- 해당 관측: examined35, updated15, ok15, missing20, unknown0, duration1,960ms, done=true. 마지막 숫자 갱신도23:59:28이다. 이것은 한 작업의 관측이며 하루 처리량 전체가 아니다.
- 공개 복제본과 주 DB의 두 목록 결과가 일치했고 실제 홈 급상승 응답도 일치했다.

따라서 **현재 관측에서는 수집이 멈췄거나 복제본이 오래된 순위를 내놓는 현상은 아니다.** 같은 후보가 계속 우세하면 순위는 유지된다. 이 표본만으로 지난 며칠간 상위5개가 같았는지나 원인 전부를 확정할 수는 없다. 과거 순위 이력을 별도로 저장하지 않으므로 지금 데이터에서 과거 일별 순위를 복원할 수도 없다.

집계 기준 UI(`MethodologyDialog.tsx:222`)의 ‘1일 미만은1일·보통2~3일’은 실제 코드와 불일치한다. 정적 캐시 기본값은 공개 읽기30초/설정60초이며 이번 HTTP 응답은DYNAMIC였다. 열린 화면의 띠는 자동으로 다시 요청하지 않는다.

## 최소 수정안(PR 단위, 미구현)

1. **신규 목록 의미 수정:** 전용 신규 조회에서 기존 저장소 생성일 근거를 재사용하고 완료7일의 시작·종료 경계를 모두 적용한다. 생성일 미상은 등재일로 대체하지 않는다. 스타50·공개/정상 조건은 유지한다. 생성일 정렬·카드 날짜·설명·모두 보기 범위를 함께 맞춘다. 일반 최신순은 계속 서비스 등재순으로 유지한다. 명칭은 ‘최근7일에 생성된 저장소’처럼 실제 근거를 드러내거나, 첫 공개일을 별도로 확보해야 한다. 달력 이번 주로 바꿀지는 별도 제품 결정이다.
2. **급상승 설명 정합성:** 20시간 바닥·약20시간 재조회·두 관측 기반이라는 설명을 고친다. 최신 관측 시각을 쉽게 볼 수 있게 하고 카드의 전체 증가량과 순위의 일평균을 구분한다. 정상 동작 중인 수집 주기를 임의로 줄이거나 목록을 무작위 교체하지 않는다. 기존 hover 설명을 활용하면 추가 코드 범위를 줄일 수 있다.
3. **최근24시간 순위가 필요할 경우 별도 PR:** 관측 이력을 저장하고 모든 프로젝트에 공통24시간 창을 적용해 비교한다. 관측 간격 상한은 오래된 구간을 제한하는 별도 정책일 뿐 공통24시간 증가량을 만들지 않는다. 현재20시간의 두 관측 순위를 이름만 바꿔 ‘24시간 증가’로 표시할 수 없다. 이력/정책 추가는 위 두 정합성 수정과 분리한다.

## 실패 접근과 남은 작업

root .env/.env.local 연결은 현재 운영 제품 스키마 필드가 없고 crawl_settings 갱신이9월9일인 다른/오래된 DB였다. 첫 복잡한 읽기 조회가42703으로 실패했다. 운영 연결이라고 보고하지 않았고 마이그레이션하지 않았다. 실행 중 웹 컨테이너의 실제 연결로 다시 조사해 현재 필드·런타임을 확인했다. 웹 도구의 공개 주소 open은 접근 오류였으나 일반 HTTP 읽기로 콘텐츠를 확인했다.

이번 파일과 handoff만 변경한다. 순위 코드/DB/크롤 설정/소개 검수/운영 인증키는 변경하지 않았다. 원래 요청의 GitHub App 등록 최종 확인 및 Resend 보유·발신 주소 답변은 대기 중이며 스타·댓글 플래그는OFF다.

후속 운영 읽기 명령(임시 도구): `python3 /private/tmp/nomorevibe-home-audit-20261011.py`. 이 도구는 컨테이너 안에서만 DB 접속 정보를 사용하며 read-only 트랜잭션을 연다. 원본 연결 정보나 Dokploy 전체 앱 응답을 기록하지 않는다. 수집 시각이 바뀌면 후보·순위도 달라질 수 있다.
