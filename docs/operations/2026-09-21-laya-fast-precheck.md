# LAYA 실측과 심사 속도 개선 검토 — 재검토 반영

2026-09-21 실측. 운영 DB 기준 시각 11:10 KST, 워커 확인 11:15 KST. 코드 기준 `af50608` / 배포 기능 버전 `678380c`.

**최종 재검토에서 LAYA의 운영 판별·힌트·원문 선택·우선순위 변경 제안을 철회했다.** 잘못된 힌트도 후속 모델의 판단과 처리 순서에 영향을 줄 수 있으므로, 오탐 위험이 있는 부분에는 판별을 맡기지 않는다는 사용자 조건을 충족하지 못한다. 이 문서의 실측 자료는 유효하지만 최초의 운영 적용 제안은 최종안이 아니다.

현재 구현 기준은 [최종 PR 계획 6개](../plans/2026-09-21-review-pipeline-speed/README.md)다. LAYA는 기존 오프라인 평가 자료만 보관하며, 운영 모델 호출을 추가하지 않는다. 확정된 결과의 즉시 전달·제한된 큐 연속 처리·텍스트 저장 보호·발행 작업 분리로 대기를 줄인다.

운영 설정, 심사 결과, 발행 데이터, 앱 코드는 변경하지 않았고 배포하지 않았다.

## 1. 확인한 API와 실제 속도

- API: Laya System One 0.3.4, `POST /v1/systemone`, Bearer 인증.
- `state`와 여러 `questions`를 전달하면 정해진 선택지/점수를 반환한다. 현재 API는 `auto`, `english`, `multilingual`을 지원한다.
- 서버는 RTX 5090 / CUDA에서 영어·다국어 모델을 이미 적재한 상태였다.
- 개발 PC에서 인증된 실제 추론을 실행했다. 운영 reviewer/publisher 컨테이너에서는 `/healthz`가 각각 30ms/29ms, HTTP 200이었다. 컨테이너 내부의 인증된 추론까지 측정한 것은 아니다.
- 운영 컨테이너의 worker/runner/1차/2차/발행 코드 5개씩, 총 10개 해시가 로컬과 일치했다.

| 요청 | 실제 프로젝트 | 중앙값 | p95 | HTTP 성공 |
|---|---:|---:|---:|---:|
| 내용 유형 + 설치·플러그인·스킬 언급 여부 4문항 | 47 | 33ms | 84ms | 47/47 |
| 설치·플러그인·스킬에 관한 이지선다 3문항 | 47 | 32ms | 101ms | 47/47 |
| 동시 요청 4개, 초기 비교 질문 3문항 | 16회 | 55.5ms | 123ms | 16/16 |

동시 요청 실험 16회 전체는 289ms였다. 이는 짧은 부하 실험이며 지속 처리량이나 최대 용량을 보장하지 않는다. 모든 추론 시간은 HTTP·네트워크를 포함한 클라이언트 시간이고, 모델이 이미 적재된 상태의 수치다.

LAYA는 정해진 답을 고르는 모델이므로 사유 번역, 소개 문장, 설치 프롬프트 생성에는 직접 사용할 수 없다. 해당 용도 구분은 [공식 모델 설명](https://huggingface.co/convaiinnovations/laya)에 따른다.

## 2. 단순 판별도 운영 경로에서 제외한 이유

| 검토한 신호 | 간접 영향 | 최종 처리 |
|---|---|---|
| 소프트웨어 / 읽을거리 / 개인 프로필 / 회사 소개 | 모델이 볼 원문·수집 범위가 잘못 선택될 수 있음 | 운영 제외 |
| 설치·사용 안내 | 다른 도구의 설치법을 해당 제품 근거로 취급할 수 있음 | 운영 제외 |
| 플러그인 또는 스킬 | 확정 전 힌트도 분류·검수 판단을 유도할 수 있음 | 운영 제외 |
| 읽을거리 가능성에 따른 우선순위 | 실제 제품이 지연되거나 필요한 증거를 놓칠 수 있음 | 운영 제외 |

별 수, URL, 중복, 파일 존재는 기존 코드/DB로 확인한다. 설치 문구나 파일 이름이 존재한다는 사실만으로 제품 적격성을 확정하는 새 규칙도 추가하지 않는다.

실제 테스트에서는 `grepai`, `raycast/extensions`, 일부 책에 맞는 결과도 나왔으나, `dsh-handbook`은 다른 도구의 설치법 때문에 소프트웨어로 잘못 분류했다. **설치법의 존재와 해당 저장소의 설치 가능한 제품 여부는 다르다.** 긍정 사례만 골라 운영 적용 근거로 쓰지 않는다.

## 3. 정확도를 고려한 적용 범위

단순 판별도 질문과 언어에 따라 달라졌다. 영어·한국어 각 12개, 총 24개의 명시적 예제를 구성해 확인했다.

| 판별 | 기대값과 일치 | 해석 |
|---|---:|---|
| 내용 유형 5분류 | 18/24 | 오탐으로 운영 힌트에서도 제외 |
| 설치·사용 안내 이지선다 | 20/24 | 설치형 적격성으로 연결하지 않고 운영 제외 |
| 플러그인 이지선다 | 11/24 | 자동 카테고리·수집 분기 모두 제외 |
| 스킬 이지선다 | 19/24 | 운영 힌트 제외; 기존 원문 심사 유지 |

이는 작은 구성 예제이며 질문 수정에도 재사용했다. 별도 검증 표본의 일반화 정확도가 아니다. 실제 프로젝트 47건은 API 속도와 동작 확인용이며, 기존 모델 판단이나 현재 카테고리를 정답으로 간주하지 않았다. 예를 들어 현재 `OfficeCLI`의 Skill 분류 자체도 별도의 의미 검토 대상이다.

초기의 단순 `noul` 질문에서는 책을 스킬 관련 내용으로 높게 평가하는 오탐도 있었다. 따라서 **확률이 높다는 이유만으로 검증 단계를 생략하면 안 된다.** 준비 작업도 원문 선택·큐 순서·자원 경합에 영향을 주므로 이번 구현에서는 LAYA 힌트에 연결하지 않는다.

또한 SDK 0.3.4에서 `choice.confidence`는 `1 - H(p)/log(k)`인 분포 집중도다. 기존 2차 심사의 `confidence >= 0.7`과 같은 의미가 아니다. `noul.confidence` 계산도 다르다. 작은 검증 표본이나 임계값 조정만으로 오탐 0을 증명할 수 없으며, 이번 최종안에는 임계값 기반 운영 적용이 없다. [공식 SDK](https://github.com/NandhaKishorM/laya/blob/main/laya/common.py), [확인한 0.3.4 배포본](https://pypi.org/project/laya/0.3.4/).

## 4. 실제로 줄일 대기 시간

새 기준으로 재심사 후 발행된 동일 집단 109건을 DB 이벤트로 연결했다. 최신 1차 성공 기록과 그 기록에 연결된 2차 승인, 실제 발행 전환 이벤트를 사용했다.

| 구간 | 중앙값 | p95 |
|---|---:|---:|
| 재심사 요청 → 수집 완료 | 65.1초 | 165.7초 |
| 수집 완료 → 1차 시작 | **947.9초 (15.8분)** | 3,329.5초 |
| 1차 실행 | 11.4초 | 15.1초 |
| 1차 완료 → 2차 등록 | 25.3초 | 34.3초 |
| 2차 등록 → 2차 완료 | 8.4초 | 38.9초 |
| 2차 완료 → 발행 | 35.2초 | 102.5초 |
| 재심사 요청 → 발행 전체 | 1,094.3초 (18.2분) | 3,489.6초 |

이 집단은 일괄 재심사 시점의 적체를 포함한다. 현재 모든 프로젝트가 15.8분씩 기다린다는 뜻은 아니다. 각 구간의 분위수는 합산할 수 없다. 2차 기록에는 시작 시각이 없어 등록→완료는 **큐 대기 + 실행**이며 순수 모델 시간으로 표기하지 않았다.

최근 24시간 1차 성공 기록 2,589건에는 이전 결과 재사용 190건이 포함됐다. 이를 제외한 새 실행 2,399건은 중앙값 **10.600초**, p95 **14.525초**였다. 실행 시간에는 결과 기록 등 부수 처리도 포함된다. 1차 gateway_error 43건, invalid_output 27건, 취소 4건도 있어 단순히 잡의 마지막 오류가 없다는 이유로 모든 호출이 성공했다고 볼 수 없다.

코드에서 확인한 개선 지점:

1. **다음 단계 깨우기.** 규칙 판정은 보류 후보의 1차 심사를 직접 요청하지 않는다. 1차 승인은 현재 발행만 요청하고 2차를 직접 요청하지 않는다. 2차 완료는 발행을 직접 요청하지 않는다. 결과 저장 트랜잭션에서 다음 작업 요청도 함께 남기면 정기 실행을 기다리는 구간을 줄일 수 있다. 기존 고유 키·lease·최종 발행 검증은 유지한다.
2. **남은 일 이어서 처리하기.** 운영 1차 동시성은 4이고 한 틱에서 외부 호출을 최대 4개만 시작한다. 먼저 끝난 자리를 새 후보로 채우지 않는다. 또한 runner는 `done:false`여도 현재 요청을 처리 완료로 표시한다. 정기 신호만 있는 경우 최대 4개/분 수준이며, 모델만 빨라져도 이 제한은 남는다. 가용 슬롯 재사용과 제한된 연속 실행을 같이 적용해야 한다.
3. **발행과 번역의 실행 분리.** publisher는 작업을 하나씩 실행한다. 최근 컨테이너 로그의 번역 80회는 중앙값 30.3초, p95 38.7초였다. 발행 요청이 와도 진행 중인 번역을 기다릴 수 있다. 번역을 별도 소비자로 분리하거나 더 작은 작업 단위로 양보시키는 것이 효과적이다. LAYA는 번역 자체를 수행할 수 없다.
4. **조기 분류·선택적 입력 준비는 제외.** 현재 분류는 두 심사를 통과한 뒤 발행 잡에서 시작한다. LAYA에 따른 원문 선택이나 조기 분류, 새로운 캐시는 이번 변경에 포함하지 않는다. 기존에 검증된 입력과 재사용 조건을 유지한다.

## 5. 최종 구현 흐름

```text
수집 → 기존 규칙 확인 → 결과 저장과 동시에 1차 작업 요청
     → 기존 1차 심사 → 결과 저장과 동시에 2차 작업 요청
     → 기존 2차 심사 → 승인표 저장과 동시에 발행 작업 요청
     → 기존 분류·최종 관문 확인 → 발행

소개·사유 번역: 별도 worker, 기존 원문·수동 작성·lease 보호 후 저장
LAYA: 운영 경로 연결 없음
```

PR-01 계측/계약 검증 → PR-02 원자적인 작업 연결 → PR-03 제한된 큐 처리 → PR-04 늦은 텍스트 결과 보호 → PR-05 텍스트 worker 분리 → PR-06 전체 회귀/배포 검증으로 나눴다. 상세 범위·완료 조건·테스트·롤백은 [최종 PR 문서](../plans/2026-09-21-review-pipeline-speed/README.md)를 따른다.

속도 개선 목표는 단계 간 대기를 줄이는 것이다. 전체 단축률은 아직 구현·측정하지 않았으므로 제시하지 않는다.

- 초기 API 조사에서는 실제 호출, 운영 읽기 전용 집계, 컨테이너 접근·해시 확인, 산출물 일관성 검사를 수행했다. 이후 최종안 재검토에서는 기존 단위 테스트 14개 파일/132개를 실행해 통과했다. 새 구현의 회귀/통합 테스트는 아직 실행하지 않았다. API 키는 산출물에 포함하지 않았다.
