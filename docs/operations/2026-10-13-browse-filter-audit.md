# 홈 필터·정렬 운영 검토

2026-10-13. 코드 기준 main `3f7233269f7e0d31157106c055b70630ce143c87`, 공개 HTML의 실행 release `de55c8e8182de49ad05cc23018f3c3b4bce4c25a`. UI·DB·설정은 변경하지 않았다. 이 보고서는 현재 결과와 수정 제안을 구분한다.

## 결론

칩 숫자가 항상 ‘누르면 보이는 프로젝트 수’를 뜻하지 않는다. 분야 칩은 전체 공개 프로젝트, AI 칩은 그중 AI 근거 단계1·2·3 프로젝트를 센다. ‘지금 뜨는’과 ‘최신’ 목록은 여기에 별도 자격 조건을 더한다. 따라서 현재 요구인 **칩 숫자와 클릭 결과 수의 일치**는 두 탭에서 충족되지 않는다. ‘관심 많은 순’의 현재 GitHub 스타 대체 목록은 동일 공개 집합을 쓰므로 분야별 수가 맞는다.

조회한 카드582개에서는 현재 DB 분야·AI·정렬 대상 조건 위반이나 주 정렬값의 역전을 찾지 못했다. 19개 분야의 개수 조회와 목록 조회가 서로 다른 필터를 쓰는 누락 오류는 확인되지 않았다. 칩이 목록의 대상 조건을 적용하지 않는 것이 큰 수 차이의 원인이다. 또한 ‘지금 뜨는’ 탭은 홈 상단의 **8시간 스타 급상승**과 다른 기존 집계를 쓰고 있고, 향후 검증 제품 수에 따라 두 탭의 의미가 전환되는 코드가 남아 있다.

## 실제 확인 범위

- 공개 GET66개: 19분야×3정렬=57개, 전체×3개, AI 필터 전체/개발 도구×3정렬=6개. HTML 확인10:17:37~10:22:04 KST. 초기에 같은 범위를 확인한09:27 결과는 최신 집계와 섞지 않았다.
- 66개 각각 기본9개 또는 대상 수가9개 미만이면 그 수만큼 표시, 카드 중복0, 더 보기 대상 URL 확인. 기본 카드582개를 운영 DB의 공개·분야·AI·정렬 자격과 대조했다. 주 정렬값은 증가/스타 내림차순 또는 등록 최신순을 확인했다. 동률의 모든 보조 조건까지 수작업으로 검증한 것은 아니다.
- 추가 GET7개: 전체/개발 도구의 세 정렬에서 `shown=18`은 카드18개·다음27개 링크 정상. 개발 도구 `weekly&shown=207`은 앞9개를 접고 카드198개·다음216개 링크 정상. 198은 전체 접근 가능한 결과 수의 상한이 아닌 한 화면의 카드 상한이다.
- 운영 DB는 read-only repeatable-read transaction으로 분야 집계·현재 시즌·검증 수·582개 멤버십을 읽었다. 최종 snapshot10:22:23 KST.
- 공개37,000개 이상을 모두 브라우저로 순회하거나 분야 분류의 내용 품질을 프로젝트마다 검수한 것은 아니다. DB 분야값과 실제 목록 조건·초기 노출을 확인했다. 실제 사용자 클릭·저장·로그인·댓글 제출 기능 테스트는 실행하지 않았다.

Next의 스트리밍 응답은 카드뿐 아니라 마지막 칩의 숫자도 별도 hidden segment로 보낼 수 있었다. 원시 HTML의 첫 골격이나 nav 일부만 읽으면0장 또는17칩으로 잘못 판정된다. React의 `$RS` 조각 연결을 반영하고 실제 project-grid를 읽어 바로잡았다. 이것은 검토 도구의 파싱 보정이며 서비스의 카드/칩 누락이 아니다.

## AI 필터의 실제 의미와 개수

스크린샷의 ‘AI로 제작’은 선택 전에는 전체 AI 근거 보유 수를 표시하는 선택 가능한 필터다. 그 숫자가 기본 목록 전체에 AI 필터가 적용됐다는 뜻은 아니다. 선택 시 category×ai_level 집계를 사용해 분야 숫자도 AI 집합으로 바뀐다. 그러나 여전히 정렬 자격은 적용하지 않는다.

| 선택 상태 | AI 칩 수 | 지금 뜨는 결과 | 최신 결과 | 관심 많은 순 결과 |
| --- | ---: | ---: | ---: | ---: |
| 전체 · AI로 제작 | 32,503 | 1,368 | 32,186 | 32,503 |
| 개발 도구 · AI로 제작 | 7,713 | 695 | 7,702 | 7,713 |

최종 DB의 AI 전체는32,505/급상승1,370/최신32,188이었다. 일부 AI 분야 칩도1개 차이였다. 큰 차이는 분야와 마찬가지로 정렬 자격을 빼고 센 데서 온다. `ai_level` 단계 확인 결과를 쓰는 필터이며 제품이 실제로 AI로 만들어졌는지 근거 자체를 재심사한 결과가 아니다.

## 상위 세 탭의 현재 차이

현재 활성 시즌은2026-W42, 최소 검증 제품20개, 공개·생존 검증 제품0개다. 따라서 아래 GitHub 대체 목록이 실제로 동작한다.

| 탭 / URL 값 | 지금 쓰는 대상 조건 | 지금 쓰는 순서 | 실제 의미 |
| --- | --- | --- | --- |
| 지금 뜨는 / weekly | 공개·생존, 마지막 두 스타 관측의 증가>0, 총스타<2,000, 마지막 스타 확인이7일 이내, 저장소 소실 확정 아님 | 증가량 ÷ 관측간격(하루 기준, 최소20시간) 내림차순 → 총스타 → 등록시각 → slug | 최근 두 확인 사이 하루 평균 스타 증가. 고정8시간도 고정24시간도 아님 |
| 최신 / recent | 공개·생존, 정상 GitHub URL인 제품은 repo_status=ok. 저장소가 없거나 다른 형식 주소이면 이 확인 조건을 기다리지 않음 | 검증 제품 우선 → coalesce(verifiedAt,createdAt) 최신 → slug | 서비스에서 새로 등록/검증한 순. 오래된 저장소도 최근 수집되면 올라옴 |
| 관심 많은 순 / all-time | 공개·생존 전체. 소실 저장소의 기존 스타는 정렬에서 null 취급 | 총 GitHub 스타 내림차순 → 등록시각 → slug | 누적 GitHub 스타 수. 증가량이나 서비스 관심 이벤트 수가 아님 |

공통 공개 자격은 `seeded/verified`, 상태 확인의 연속 실패3회 이상 제외, 소실 확정 저장소의 설치형 제외, 수집한 미클레임 Profile 제외다. 분야·AI·검색·도구 조건은 그 위에 추가된다. 검색/빌더/관측 도구를 고르면 현재 숫자를 오해하지 않도록 칩 수를 숨기는 정책도 있다.

‘최신’과 별도 홈 ‘이번 주 새로 나온 프로젝트’도 다르다. 후자는 연결된 GitHub 저장소의 실제 생성일·별도 기간/스타 조건을 사용한다. `recent`는 프로젝트 생성일이 아닌 서비스 등록·검증일 기준이다.

### 상단8시간 급상승과 탭이 다른 문제

PR400으로 배포한 홈 상단 띠와 `/rising`은 독립적인 `star-growth.ts` 집계를 사용한다. 같은 저장소·연결 버전의 마감된 T와T−8h 회차, 실제 간격7~9h, 총스타50~1,999, 순증가≥1, 관측10시간 이내, 공개·생존 조건을 사용하고 **8시간 증가량 내림차순**으로 정렬한다. 카드 주 지표는 ‘8시간 +N’이다.

반면 아래 세 탭 중 ‘지금 뜨는’은 `products.stars/stars_previous`의 기존20시간 이상 기준점을 사용한다. 이름이 비슷하지만 조회 함수·대상·관측창·배지가 다르다. 지난8시간에 늘어난 프로젝트를 아래 탭에서도 같은 순서로 본다고 기대하면 맞지 않는다. 수집 스케줄을 더 늘려 해결할 문제가 아니라 읽기 경로와 표시 기준을 맞춰야 한다.

### 검증 수가 늘면 의미가 바뀌는 문제

`verifiedTotal < minimumProducts`가 아니게 되면 대체 목록을 끈다. 현재 설정이면20개에서 전환된다.

- `weekly`는 탭 이름이 ‘추천’으로 바뀌고 활성 시즌의 검증 제품 랭킹을 쓴다. 현재 시즌 정책은 valid_visits이며 순위 노출 상한은 정책의 leaderboard.limit를 따른다.
- `all-time`은 검증·생존 제품의 서비스 방문 이벤트 누적 순위를 쓴다. 코드의 집계 창은3,650일이다. GitHub 총스타 순과 의미가 달라진다.

운영 프로젝트 수만으로 탭의 의미가 조용히 바뀌므로 다국어 문구도 안정적으로 붙일 수 없다. 방문 순위와 GitHub 스타 탐색은 이름·진입점을 고정해서 분리하는 편이 명확하다.

## 수정 제안과 PR 단위

아래는 후속 구현 제안이다. 이번 요청의 확인·설계 단계에서는 적용하지 않았다. 기존 필터 스타일·배치는 유지하고 기준과 개수를 맞추는 범위를 우선한다.

| PR | 수정 | 주요 범위 | 확인할 계약 |
| --- | --- | --- | --- |
| FILTER-01 | 칩을 현재 목록 대상 수로 집계 | 공통 browse 대상 조건, 분야×AI 집계, BrowseFilters, 캐시 키 | 분야 칩=해당 분야로 바꿨을 때 결과 수, AI 칩=현재 분야에서 AI로 좁힌 수. 공개 전체 수는 별도 라벨 |
| FILTER-02 | 세 탭 의미를 고정하고8시간 집계 통일 | app/page.tsx, browse-state, star-growth reader의 분야/AI 조회·count, metadata/집계 설명 | ‘8시간 스타 급상승’ / ‘최근 등록’ / ‘GitHub 스타 많은 순’. 검증 수 증가로 의미 변경 없음, 홈 띠·목록·/rising 동일 회차·순서 |

두 PR은 동일 대상 모델을 바꾸므로 순차 구현한다. FILTER-01에서 기존 실제 모드의 조건부터 공통화하고 FILTER-02에서8시간 모드를 연결한다. 관측 워커·8시간 스케줄·기존 DB 회차 schema는 재작성하지 않는다. 서비스 방문 랭킹은 기존 랭킹 페이지에서 명확한 별도 이름으로 유지한다. `weekly`/`all-time` 등 기존 query는 이전 링크 호환 alias로 처리한다.

칩 집계는 현재 정렬/관측 회차·AI 조건을 유지하되 분야는 각 칩을 눌렀을 때의 대체 분야로 센다. AI 칩은 현재 분야와 정렬을 유지하고 AI 선택 자체는 대체해서 센다. 모든 칩에 현재 선택 분야 조건을 그대로 걸어 다른 분야가0이 되는 구현은 피한다. 검색·도구·빌더 상태에서 숫자를 숨기는 현재 정책은 우선 유지한다. 칩 순서를 전체 공개 수로 안정적으로 유지할 수 있지만 칩 숫자는 실제 정렬 자격으로 표시한다.0건 분야도 위치를 유지해 비활성/0 표시하고 현재 선택은 해제할 수 있게 한다.

FILTER-02에서는 ‘최근 등록’이 서비스 등록순임을 설명하고 ‘최근7일 생성’ 목록은 기존 별도 메뉴를 유지한다. 신규 저장소 목록과 등록순을 섞어 이름만 바꾸지 않는다. 8시간 데이터가 아직 준비되지 않았거나 지연된 경우 그 상태를 표시하며 총스타 순을 대신 ‘급상승’으로 제공하지 않는다. 번역 준비 여부는 필터 자격에 영향을 주지 않는다.

다국어 설계는 [한국어·영어·간체·번체 공개 페이지 설계](../plans/2026-10-13-public-i18n-design.md)의 I18N-01~04로 이어진다. 이 두 필터 PR의 의미 계약을 먼저 확정해 네 언어가 같은 기준을 설명하게 한다.
