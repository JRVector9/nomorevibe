## 우선 구분할 숫자

「발굴」과 「원본 수집」 두 화면 숫자의 차이만으로 수집 손실률을 계산하면 안 된다. 화면의 발굴은 `crawl_frontier.discovered_at`이 최근인 행 수이고, 원본 수집은 마지막 `crawl_documents.fetched_at`이 최근인 저장소 수다. 둘은 같은 발견 집단이 아니며 재수집이 뒤 숫자에 들어간다. [집계 구현](../../lib/operations/pipeline.ts#L50), [시간별 발견 집계](../../lib/operations/dashboard.ts#L193), [원본 처리량의 측정 한계](../../lib/operations/throughput.ts#L17).

홈 흐름 표는 **발굴을 `/시간`, 원본 수집을 `/5분`**으로 표시한다. 예를 들어 1,481/시간과 192/5분을 1,481→192 전환으로 읽으면 관측 창부터 다르다. 5분 수에 12를 곱해도 일정 속도를 가정한 환산일 뿐 실제 같은 시간창의 전환율이 되지는 않는다. 이번 분석은 화면 숫자를 단순 환산하지 않고 같은 발견 코호트와 기준 시각으로 조회했다. [표의 단위 선택](../../lib/operations/console-home-model.ts#L87), [원본 칸의 5분 처리량](../../lib/operations/conveyor-model.ts#L253).

| 수치 | 분모/단위 | 해석 범위 |
|---|---|---|
| 검색 응답 `returned` | API 응답 항목·커밋 | 저장소 고유 수가 아니다. 같은 저장소의 여러 커밋·여러 검색어·최신/과거 구간이 포함된다. |
| seed `filtered` | 응답에서 형식·홈페이지 조건을 통과하지 못한 항목 | 신규 DB 저장소 수와 직접 빼거나 나눌 수 없다. |
| `pageDuplicates` | 같은 페이지의 저장소/커밋SHA/귀속 근거가 동일한 항목 | 저장소가 같아도 SHA가 다르면 이 중복에 해당하지 않는다. |
| `examined` / `existing` | 적재 검사를 완료한 항목 / 그중 이미 저장된 항목 | 기존 frontier·문서·후보 중 어디든 있으면 기존이다. 이미 거절·발행된 저장소도 포함한다. |
| 신규 정본 발굴 코호트 | 비재수집 신호로 처음 삽입된 frontier에서 `alias_of IS NULL`, 소문자 저장소별 구분 | alias는 수집 후 발견될 수 있다. 관측 시점의 정본 여부이며 모든 과거 정체성 변경을 재구성하지 않는다. |
| 코호트의 현재 원본 존재 | 위와 같은 저장소 중 문서가 존재하는 수 | 같은 발견 집단의 도달 여부다. 첫 원본 수집 시각이나 모든 네트워크 시도를 뜻하지 않는다. |
| 신규 규칙 후보 | `crawl_candidates`에 생긴 심사 대상 | frontier 적재와 다르다. 원본 수집·근거 관문 이후의 수치다. |
| 최근 원본 `fetched_at` | 마지막 원본 저장 시각이 창 안인 문서 | 신규 수집과 기존 제품·후보 재수집이 섞인다. 동일 저장소를 여러 번 받아도 마지막 한 행이다. |

`review-source-refresh`, `star-auto-source-refresh`, `admin-evidence-refresh`로 신규 생성한 frontier는 신규 발굴 분모에서 제외한다. 기존 frontier를 재수집 대기로 되돌릴 때는 첫 발견 신호와 발견 시각을 유지하므로, **현재 수집 작업이 재수집인지 신호만으로 가를 수 없다.** 현재 문서 또는 후보 존재 여부도 확인한다. [재수집 재등록](../../lib/crawl/agent-review-repository.ts#L516), [관리자 재수집](../../lib/crawl/admin-review.ts#L207).

## 현재 코드에서 확인한 유입 경로와 차단점

1. 일반 GitHub 탐색은 켜진 검색어를 읽되 한글 repository 검색은 Oracle에 맡긴다. 검색을 하기 전에 저장 대기량과 최근 5분 신규 적재를 확인한다. 신규 몫이 없으면 커서를 보존하고 검색을 미룬다. 설정 기본 상한은 시간당 3,000건을 5분당 250건으로 나눈 값이고, 모델의 동시 호출 수를 뜻하지 않는다. 실제 운영 저장값과 `rate_cap` 관측을 확인하기 전에는 상한이 현재 병목이라고 결론 내릴 수 없다. [seed 입장 확인](../../lib/crawl/jobs/seed.ts#L78), [실제 적재의 재확인](../../lib/crawl/shared-discovery.ts#L117), [한도 계산](../../lib/crawl/review-backlog.ts#L85).
2. repository 검색 응답은 homepage가 없거나 유효한 배포 URL로 정규화되지 않으면 seed 단계에서 제외한다. commit 검색에는 이 homepage 필터가 없다. 뒤의 심사 규칙이 설치형 500스타·패키지 근거 5스타 경로를 지원하더라도 해당 repository 검색 결과가 이 앞 필터를 통과한다는 뜻은 아니다. 이 경계는 코드로 확인되지만 현재 이탈 건수·공개 적격성을 확인하기 전에는 품질 기준 완화나 수율 개선량을 제안하지 않는다. [입구 필터](../../lib/crawl/jobs/seed.ts#L573), [설치형 접근 규칙](../../lib/domain/products/access.ts#L1).
3. 공유 적재는 frontier·문서·후보를 모두 대소문자 무시로 확인하고 실제 처음 삽입한 항목만 신규 한도를 쓴다. 반복 검색에서 `existing`이 많으면 API/근거 저장 비용에 비해 신규 유입은 적을 수 있다. 다만 근거 보강에는 의미가 있을 수 있어 기존 검색을 모두 낭비로 분류하지 않는다. [기등록 판정](../../lib/crawl/shared-discovery.ts#L126), [근거 저장과 신규 적재 순서](../../lib/crawl/jobs/seed.ts#L503).
4. 수집 잡은 `pending/fetching` 중 재시도 시각이 지난 행을 priority 내림차순·다음 시도 시각 오름차순으로 가져온다. 기본 24개 묶음·동시 12개지만 GitHub origin 요청은 잡 안에서 직렬화된다. 홈페이지 대기는 다른 origin과 겹칠 수 있다. 따라서 동시성 12를 GitHub 초당 12요청이나 시간당 공개량으로 바꿔 계산하지 않는다. [큐 선택](../../lib/crawl/repository.ts#L150), [묶음과 동시성](../../lib/crawl/jobs/fetch.ts#L33), [직렬 origin](../../lib/crawl/jobs/fetch.ts#L407).
5. source buffer는 설정 기본값이 꺼짐이다. 켜져 있으면 후속 단계의 고유 대기 저장소 수가 `maxReviewBacklog`에 도달했거나 측정을 못 했을 때 새 저장소 수집을 제한한다. 이때도 이미 문서/후보가 있는 원본 재수집은 통과시킨다. 발견 큐까지 포함하는 seed 저장 상한과 수집의 후속 단계 상한은 분자가 다르다. [source buffer](../../lib/crawl/source-buffer.ts#L15), [재수집 예외](../../lib/crawl/source-buffer.ts#L39).
6. 재수집이 항상 더 높은 priority인 것은 아니다. 기존 행의 재등록은 원래 priority를 보존하고, frontier가 없어 재수집 행을 만들 때만 priority 100을 지정하는 경로가 있다. HN/GN의 priority도 별도다. 큐에서 실제로 어느 유형이 앞서는지 측정해야 한다.
7. `fetch` stage가 legacy가 아니면 legacy 잡은 `stage_blocked`로 물러난다. items 모드에서는 소비자·item lease를 함께 확인해야 한다. 잡의 마지막 성공 시각만으로 실제 신규 원본 확보를 인증하지 않는다. 재시도·HTTP origin permit·GitHub core/auth cooldown·잡/역할 lease도 각각 다른 원인이다. [소유권](../../lib/crawl/fetch-ownership.ts#L37), [미룸 분기](../../lib/crawl/jobs/fetch.ts#L83).
8. 원본 수집의 AI 흔적 관문은 메타 원본을 저장하면서 후보를 거절할 수 있다. 따라서 `gated`는 「원본 미수집」과 같지 않다. 404/빈 저장소나 GitHub numeric ID alias는 원본 없이 skipped가 될 수 있다. 홈페이지 부재·차단 도메인·제외 패턴 같은 일반 negative/품질 규칙은 대부분 원본 이후 규칙 심사에서 적용되므로 원본 이전 이탈과 분리한다. [근거 관문 저장](../../lib/crawl/repository.ts#L654), [alias](../../lib/crawl/repository.ts#L642), [수집 후 규칙](../../lib/crawl/rules.ts#L400).

Show HN은 `crawl.enqueue`로 frontier 중복을 제외하며 공유 신규 적재 입장 확인을 거치지 않는 별도 경로다. GN·일반 검색·Oracle의 공유 적재 정책을 HN에 그대로 대입하지 않는다. Oracle staging은 언어 미판별/yes/no와 applied 상태를 구분해야 하고, `applied`도 기존 저장소 재발견을 포함할 수 있으므로 `outcome.added`와 다르다. [HN](../../lib/crawl/jobs/hn-show.ts#L163), [Oracle 반입](../../lib/crawl/korean-discovery/apply.ts#L24).

## 측정안과 증거 범위

root 전용 제안 SQL: `/tmp/nmv-intake-readonly-proposal-20261114.sql`. 분석 담당은 실행하지 않았다. 각 SELECT는 별도 읽기 전용 repeatable-read 트랜잭션으로 제한한다. 조회가 실패하면 실패 영수증을 보존하며 전체 이력 무제한 재시도·쿼리 제한 해제·운영 변경으로 대체하지 않는다.

| 조회 | 확인할 것 | 제한 |
|---|---|---|
| Q1 | 정확한 최근 1시간·24시간 frontier 생성, 재수집/Oracle/HN/GN/alias/state | 저장소 키 고유 수와 행 수를 별도 표시 |
| Q2 | 같은 신규 비재수집 코호트에서 원본·현재 후보·거절·보류·공개 도달 | 최신 20,000건과 초과 sentinel. 잘렸으면 전체 24시간 전환율로 쓰지 않음 |
| Q3 | 현재 실제 수집 큐의 신규/기존 문서·후보, priority, due, live item, 오류·시도 | 최대 20,000건과 초과 표시. 신호를 현재 재수집 여부로 대체하지 않음 |
| Q4 | 저장 상한/페이지/sourceBuffer, fetch stage, crawler 역할 lease, 잡 시각·커서·최신 관측 | 현재 상태이며 과거 24시간 정상의 증거가 아님 |
| Q5 | 최근 source/lane별 API 응답·기등록·신규·불완전·차단 관측 | 최대 512 source 행·분 bucket. 24시간 자료로 연장하지 않음 |

| Q7 | 일반 탐색·HN/GN·Oracle·fetch의 누적 job-tally와 defer | 최근 정시 24칸은 23~24시간, 10분 7칸은 60~70분. Q1 rolling 창과 혼합 비율을 내지 않음 |

job-tally에는 `filtered`도 남는다. 성공적으로 마친 틱의 요약 합계이며 실패 틱은 `@failed`만, 미룬 틱은 `defer:<job>`에 따로 기록된다. 실제 DB 적재 이후 실패한 틱의 일부 작업이 누적 합계에 빠질 수 있다. 여러 lane의 API 결과와 유입을 합산할 때도 `seeded`와 `seed_latest_scanned`를 구분한 뒤 합친다. snapshot의 최신 `job:<name>` 한 줄을 24시간 처리량으로 간주하지 않는다. [누적 규칙](../../lib/jobs/tally.ts#L7), [이벤트 종류](../../lib/jobs/collector-events.ts#L16).
