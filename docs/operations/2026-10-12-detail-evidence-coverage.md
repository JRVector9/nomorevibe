# 상세 저장소 근거 누락 점검 — 2026-10-12

## 확인한 운영 상태

팀의 2026-10-12 운영 DB 읽기 전용 점검에서, 공개 상태(`seeded`/`verified`)이고 GitHub 저장소 주소가 있는 제품을 **현재 주 저장소 키와 연결된 보이는 링크·GitHub facts**로 대조했다. 저장소가 아닌 다른 출처나 과거 저장소의 facts를 대신 세지 않았다.

| 상태 | 제품 수 |
| --- | ---: |
| 공개 GitHub 제품 | 42,283 |
| 상세에 표시 가능한 현재 저장소 facts | 38,623 |
| 현재 저장소 링크 자체가 없음 | 1,105 |
| 보이는 현재 링크는 있지만 출처 행이 없음 | 2,402 |
| 현재 출처 행은 있지만 facts가 없음 | 153 |
| 숨겨진 현재 저장소 링크 | 0 |

별도 교차 집계에서 48시간을 넘긴 facts는 9,732개, 정상 상태가 아닌 출처는 1,566개였다. 마지막 성공 facts가 남은 실패 출처도 있으므로 이 두 수를 위 누락 수에 더하지 않는다.

`facts` 없는 153개는 잘못된 다른 타입의 데이터가 아니었다. `not_found` 136개, `rate_limited` 10개, `collection_failed` 5개, `http_403` 1개, `invalid_response` 1개로 출처 실패가 기록돼 있었다. 이들은 재시도 시각과 마지막 정상 관측값을 보존하는 기존 경로의 대상이다.

근거 파일은 `/private/tmp/nomorevibe-detail-license-audit-result-20261012.json`, `/private/tmp/nomorevibe-detail-license-audit-extra-20261012.json`이다. 저장소 이름·라이선스 정보 등 공개 메타데이터와 집계 결과이며, 이 구현 작업에서 운영 DB나 제공자에는 쓰지 않았다.

## 원인

1. **최초 수집 요청 누락.** `products.insert`는 저장소 링크를 동기화했지만 제품 근거 요청을 만들지 않았다. `publishCandidate`의 발행 후 요청은 썸네일 작업뿐이었다. 정기 `dueEvidenceProductSlugs`는 최초 출처가 없는 제품과 기존 출처의 재수집을 모두 slug 오름차순으로 훑는다. 새 제품이 커서보다 앞에 들어오면 다음 전체 순회까지 기다리고, 뒤에 들어와도 앞선 재수집량의 영향을 받는다. 점검 시 근거 워커는 살아 있었고 커서는 `agentgateway`였다. 워커 정지로 분류할 근거는 없었다.
2. **과거 제품의 링크 백필 미완료.** 링크가 없는 1,105개는 모두 `crawler`/`seeded`/미클레임 제품이며 메이커 링크 감사 기록이 없었다. 생성 시각은 2026-08-29부터 2026-09-08이었다. `okraPDF`, `unbound`(`home-3`), `lykn`, `Jovie`, `mad.builders` 표본도 저장소 링크와 메이커 링크 감사 기록이 모두 비어 있었다. 저장소 링크 동기화는 `4aed858`에서 제품 생성·수정 경로에 추가됐지만, 기존 제품 복구는 수동 백필 명령에만 있었다. 정기 due 조회는 `product_links`에서 출발하므로 이 제품들은 순서가 늦은 정도가 아니라 저장소 수집 대상에 들어오지 않았다. 현재 코드의 `repo_url` 수정 경로는 동기화를 호출하며, 최근 수정 우회로라는 증거는 발견하지 못했다.

ManimGX는 보이는 현재 링크 `academa-labs/manimgx`가 있지만 출처·요청 이력이 없던 첫 번째 유형이었다. 팀이 기존 강제 갱신 큐로 이 한 제품을 접수한 뒤 완료 버전 1/실패 0과 공개 상세의 저장소 사실 6개를 확인했다. 이는 해당 제품의 복구 결과이며 전체 대기열 완료를 뜻하지 않는다. 원본 크롤 문서의 라이선스 값을 관측 facts인 것처럼 화면에 대입하지 않았다.

## 코드 변경

- `queueProductRefresh`가 기존 제품 트랜잭션을 받을 수 있도록 했다. 별도 호출의 세대 잠금, 요청 버전 병합, active 진행 보존, 강제 요청 제한과 제공자 재시도 시각은 같은 로직을 사용한다. 트랜잭션 안에서 새로 생성한 제품은 포착한 `productId`로 검증한다.
- 새 저장소 링크가 생긴 공개 제품은 생성 트랜잭션에 `force:false` 최초 요청과 job 요청을 함께 기록한다. 발행의 OG 부가 작업이나 프로세스 종료 전에 요청이 보존된다. 미공개 메이커 등록은 이 경로에서 수집하지 않는다. `markVerified`는 보이는 주 저장소 링크가 있고 아직 출처 행이 없는 경우에만 공개 전환과 같은 트랜잭션에서 접수한다. 이미 수집한 크롤러 제품을 클레임할 때 신선한 출처를 강제로 다시 수집하지 않는다.
- `product-evidence-refresh`는 **현재 due 명시적 요청이 없는 회차에만 최대 한 제품**을 복구 접수한다. 일반 GitHub URL 형태의 현재 주 저장소를 가진 공개 제품 중 오래된 제품 ID부터 선택하며, 기존 요청이 진행·대기 중인 제품은 다시 접수하지 않는다. 보이는 링크의 출처가 없는 경우 또는 안전한 과거 링크 누락만 대상이다.
- 과거 링크는 `syncRepositoryLink(mode:"backfill")`를 재사용한다. 미클레임 크롤러 제품·메이커 링크 감사 기록 없음 조건을 그대로 유지한다. 선택 뒤 같은 세대 잠금 안에서 공개 상태·현재 저장소 키·기존 요청을 다시 확인하고 job lease를 검증한다. 숨긴 링크, 삭제 tombstone, 클레임 또는 메이커 변경은 복구로 되살리지 않는다.
- 복구 요청은 새 요청의 접수 시계보다 앞선 회차 시작 시계로 실행하지 않고 후속 회차의 기존 요청 처리 경로에서 소비한다. 정기 수집의 `afterSlug`, 요청/정기 수집의 `requestTurn`, 수집 예산·실패 백오프·제공자 대기는 변경하지 않았다. 초기 복구 접수에는 외부 제공자 호출이 없다.

## 확인 범위와 남은 운영 확인

구현 작업에서는 설치된 Next 가이드와 기존 큐·세대·lease·백필·발행 경로 및 관련 통합 fixture를 소스에서 검토했다. 기존 요청 함수의 단독 호출 형태는 유지했고, 통합 fixture 초기화는 `product_refresh_requests`를 비운다. 테스트를 작성하거나 실행하지 않았다. 타입 검사, lint, build, E2E, UI 자동화, 배포도 실행하지 않았다.

실행한 변경 검사는 `git diff --check -- lib/domain/products/repository.ts lib/domain/evidence/refresh-requests.ts lib/domain/evidence/refresh.ts lib/jobs/products/evidence-refresh.ts`이며 종료 코드 0이었다.

배포 후에는 다음을 읽기 전용으로 대조한다.

- 새 발행의 제품·보이는 주 저장소 링크·`force:false` 요청이 함께 커밋되고 요청이 실제 완료되는지 확인한다.
- `evidence.initial_refresh_queued`가 명시적 요청 없는 회차에 최대 한 번씩 기록되는지, 과거 링크 1,105개와 출처 없는 2,402개가 줄어드는지 확인한다.
- 정기 커서와 실제 출처 저장 시각도 함께 전진하는지 확인한다. 접수 수나 워커 heartbeat만으로 복구 완료를 판단하지 않는다.
- 숨김·메이커 삭제 기록은 유지되는지, 위 실패 출처의 재시도 시각을 당기거나 facts를 지어내지 않는지 확인한다.

복구 접수율은 회차당 최대 1개이며, 명시적 요청이 계속 있으면 복구 접수는 미뤄진다. 일반 수집도 함께 진행하지만 신규 발행량, 제공자 대기와 실제 워커 처리량에 따라 전체 해소 시간은 달라진다. 이번 변경은 신규 최초 요청 누락과 과거 수집 대상 누락의 복구 경로를 마련한 것이며, 전체 누락·오래된 facts가 이미 해소됐다는 기록이 아니다. 소개 검수 중단 상태는 변경하지 않았다.

독립 `gpt-6.1-sol / xhigh` 읽기 전용 소스 리뷰는 actionable finding 없이 완료됐다. 같은 트랜잭션 큐·세대 잠금·예산·lease·백필 보호를 검토했으며, 실제 SQL 실행·동시성·복구 처리량을 실행 검증한 결과는 아니다.
