# 크롤링 yes/no 체크 속도 재검토

2026-09-21 12:00 KST · 코드 기준 `af50608` · **검토·로컬 측정만 완료, 운영 구현·배포 없음.**

## 결론

**체크에 필요한 자료를 준비하고 다음 단계로 넘기는 시간은 개선 여지가 있다. 현재 체크 계산을 LAYA로 교체하는 속도 이점은 확인하지 못했다.** 관리자 화면의 ✓/■ 목록은 항목마다 LLM을 호출한 결과가 아니라 저장된 원본에 코드 규칙을 적용한 결과다. 1차 모델도 이 체크마다 따로 호출되는 것이 아니라 전체 원문과 정책을 받아 한 번 판단한다.

따라서 앞선 답변에서 “속도 개선 근거가 없다”는 범위는 **LAYA 도입 효과**에 한정된다. 크롤링 준비·DB·후속 작업 전달까지 개선할 수 없다는 뜻은 아니다. 작은 모델을 빠른 질문에만 쓰자는 방향은 검토할 수 있지만, 현재 경로에는 별도 느린 LLM 호출로 처리하는 단순 사실 체크가 발견되지 않았다.

## 항목별 검토

| 체크 | 현재 확인 방식 | 속도 개선 및 LAYA 판단 |
|---|---|---|
| 별 500개 이상 / 포크 / 보관됨 / 계정 종류 | GitHub 응답 필드와 설정을 코드로 비교 | 응답 후 계산은 매우 짧음. LAYA 추가 불필요 |
| homepage 값 / URL 형식 / 차단 도메인 / docs 경로 | URL 파싱·목록·패턴 비교 | 원문에서 확정된 사실 유지. 패턴의 제품 판별 정확성과 계산 속도는 별개 |
| URL 응답 여부 / 리다이렉트 후 도착 주소 | 실제 HTTP 요청 결과 | 기다리는 것은 HTTP. LAYA는 URL이 실제 응답했는지 대신 확인할 수 없음 |
| 중복 등재 / 차단 상품 | 저장소·URL 기준 DB 조회 | 쿼리·왕복 계측 대상. 모델로 추측하지 않음. 최종 잠금·재검증 유지 |
| AGENTS.md·CLAUDE.md 등 지원 파일 존재 | commit/tree/blob 수집 후 경로·형식 파싱 | API 자료 수집과 로컬 파싱을 구분. 불완전 탐색은 ‘없음’으로 확정하지 않음 |
| AI 개발 근거 조건 충족 | 스캔 완료·신선도·저장소 관계·commit attribution을 코드로 확인 | 이미 LLM 미사용. 파일 존재가 실행 증명은 아니며 `executionVerified=false` 유지 |
| 문서 생성기로 만든 홈인가, 문서 자체인가 | 코드에서 보류하고 기존 심사로 전달 | yes/no로 물어도 의미 판단. LAYA 오답이 제품 제외로 이어질 수 있음 |
| 설치 명령이 있는가 / 그것이 이 제품 설치법인가 | README 원문과 기존 1·2차 심사 | 문자열 존재와 제품의 설치 가능성은 별개. 책에 나온 다른 도구의 설치법도 있음 |
| 플러그인 / 스킬 / 실제 제품인가 | 기존 1·2차 원문 심사 | 이전 단순 질문 평가에서도 오답. 자동 통과·탈락·수집 생략에 적용하지 않음 |

화면의 정지 표시에는 `needs_review`도 포함된다. `passed=false`를 전부 최종 거절로 취급하면 안 된다. 마찬가지로 미수집·timeout·partial은 false가 아니라 미확정 상태로 유지해야 한다.

[재현 스크립트](evaluations/2026-09-21-crawl-checks/benchmark.ts), [결과 JSON](evaluations/2026-09-21-crawl-checks/benchmark.json).

DB, HTTP, HTML 추출, LLM 시간은 제외했다. 이는 체크 계산이 작다는 근거이며 전체 크롤링 지연을 측정한 결과가 아니다. 첫 측정은 단위 테스트와 동시에 실행되어, 테스트 종료 후 벤치마크만 재실행한 최종 결과를 보관했다.

비교 참고로 [이전 LAYA 평가](2026-09-21-laya-fast-precheck.md)의 yes/no 성격 질문 3개는 47개 프로젝트에서 중앙값 32ms / p95 101ms였다. **서로 다른 작업·실행 위치이므로 동일 기능의 배속 비교로 해석하지 않는다.** 다만 이미 짧은 로컬 사실 확인에 원격 추론을 추가할 이유는 발견되지 않았다.

이전 구성 사례 12개×2언어에서 설치/사용 안내 질문은 20/24, 플러그인은 11/24, 스킬은 19/24가 기대 답과 같았다. 프롬프트 탐색에 재사용한 사례라 일반 정확도 수치가 아니다. 설치 안내가 분명한 한국어 플러그인을 ‘없음’, 영어 CLI를 ‘플러그인’으로 답한 사례가 있다. 이번에는 LAYA API를 다시 호출하지 않았다.

## 실제 개선 후보와 적용 순서

1. **준비 시간부터 분리 계측 — 기존 PR-01.** `loadReviewDocument`의 DB 읽기/README HTTP/저장, `loadReviewInput`의 근거 조회, 중복 조회, 순수 규칙, claim/저장을 나눠 잰다. 현재 단순 규칙 시간만 줄여서는 효과가 작다. 순수 계산에 네트워크 시간을 합산해 ‘판별이 느리다’고 해석하지 않는다.
2. **정해진 슬롯 안에서 후보 준비를 병행 — 기존 PR-03.** 현재 `agent-review.ts`의 루프는 각 후보의 README·DB 준비를 `await`한 뒤 모델 호출을 시작한다. 먼저 시작한 모델과 다음 후보 준비는 겹칠 수 있지만, 후보별 준비 자체는 순차다. 느린 README가 뒤 후보의 모델 시작을 지연시킬 여지가 있다. 준비 중인 후보도 슬롯 수에 포함하고, 완성된 동일 원문·최신 상태를 claim 시 재검증한다. 모델 호출 한도·DB 풀·호스트별 요청 제한을 유지해야 한다. README가 이미 저장돼 있으면 이 개선 효과는 작다.
3. **확정된 결과의 다음 단계 요청 — 기존 PR-02.** 체크/심사 결과가 저장되면 다음 작업을 깨운다. 요청과 결과의 원자성, 새 요청 보존, 소비자의 기존 정책 재검증을 유지한다. 이는 체크 종류나 판정 자체를 바꾸지 않는다.
4. **DB 왕복 최적화는 측정 뒤 별도 검토.** 판정 잡은 후보별 순차 처리이며 저장 트랜잭션은 후보·문서·설정 잠금 및 재검증을 한다. 이 보호를 지우거나 서로 다른 의미의 최신 scan 조회를 무조건 합치면 안 된다. 병목으로 확인된 읽기만 같은 선택 조건·원본 일관성·순서를 보존해 개선한다. 이번에 안전한 대체 쿼리를 구현·검증한 것은 아니다.

이 순서는 검토 우선순위다. 실제 구현/병합은 기존 [6개 PR 계획](../plans/2026-09-21-review-pipeline-speed/README.md)의 01→02→03→04→05→06 순서를 따른다. 별도의 LAYA 운영 PR을 추가하지 않는다.

기존에 있는 최적화도 새 개선처럼 계산하지 않는다: 크롤링 페이지는 이미 최대 3개 병행, 같은 origin은 순차 처리, README는 저장된 sample/version 재사용, AI 근거 수집은 동일 repository ID/commit의 완료 스캔을 재사용한다. 이것만으로 더 줄어드는 시간을 주장할 수 없다.

fork/archive/별 수를 먼저 읽었다는 이유로 홈페이지를 생략하는 조기 탈락은 이번 권장 범위에 넣지 않았다. 사실값이 정확해도 수집 원문·현재 규칙의 정지 사유·설치형 예외·관리자 재검토 흐름까지 달라질 수 있다. 기존 결과와 같은지 별도 증명 없이 순서를 바꾸지 않는다.
