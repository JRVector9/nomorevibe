## 현재 구현에서 확인한 범위와 빈틈

- `lib/domain/evidence/agents/catalog.ts`: Claude, Codex, Cursor, Copilot, Aider, Gemini, OpenCode 등 설정·지침 규칙이 이미 있다. AGENTS.md/CLAUDE.md 같은 공유 지침은 특정 도구로 단정하지 않는다. 단순 파일 확장은 일부 개선일 뿐이다.
- `collect.ts`: 기본 브랜치 SHA에 고정해 공개 저장소를 검사한다. 심볼릭 링크·서브모듈·예제/벤더 경로를 제외하며 API 요청 12회/회차, 20초, 파일 32개, 64KiB/파일, 512KiB/회차 예산과 재개 커서를 갖고 있다.
- 트리 탐색은 기본적으로 루트와 지정 에이전트 폴더만 내려간다. `apps/web/.cursor/rules` 같은 일반 하위 폴더는 별도 scope가 없으면 놓칠 수 있다. 경로 매처 자체가 중첩 경로를 지원하는 것과 실제 수집 범위는 다르다.
- 커밋은 검색에서 발견한 SHA 최대 5개를 검사한다. 모든 발행 저장소의 최근 커밋을 정기 순회하지 않는다. 최종 트레일러의 Co-authored-by만 읽고, 부모 1개인 커밋과 기본 브랜치 포함 여부를 검사한다. 초기 커밋·병합 커밋 표기는 제외된다.
- Aider의 author/committer `(aider)` 표기, PR 생성 주체, 실제 Actions 실행 기록은 현재 관측 종류에 없다.
- `summary.ts`는 모델 설정 또는 커밋 표기가 있고 관계·완료 조건이 충족되면 지원 근거로 인정하지만 `executionVerified=false`를 유지한다. 모델 설정은 실행 사실이 아니므로 새 사용 도구 지표에서는 더 세분화해야 한다.

## 공식 자료에서 확인한 활용 가능한 신호

1. **공유 지침은 도구 식별력이 낮다.** Cursor도 AGENTS.md를 지원하며, 전용 프로젝트 규칙은 `.cursor/rules/*.mdc`다. 따라서 AGENTS.md 하나로 Codex라고 분류하면 오탐이다. [Cursor Rules](https://cursor.com/docs/rules)
2. **Aider의 작성과 단순 커밋을 구분할 수 있다.** 공식 문서는 코드 작성 시 author/committer에 `(aider)`, 기존 변경을 커밋만 했을 때 committer에만 표기한다고 설명한다. 이 메타데이터와 Co-authored-by를 함께 읽어 `코드 작성 표기`와 `커밋 도구 표기`를 분리할 수 있다. 표기는 끌 수 있고 위조도 가능하므로 불변의 실행 증명은 아니다. [Aider Git integration](https://aider.chat/docs/git.html#commit-attribution)
3. **PR과 실행 이력은 설정 파일보다 구체적인 단서다.** Copilot cloud agent는 브랜치에서 변경하고 PR을 만들며 GitHub Actions 환경에서 작업한다. API의 작성자·커밋·병합 상태를 연결해 수집할 수 있다. 단순 `@copilot` 요청 댓글은 실행 사실이 아니다. [Copilot cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent), [Pull requests API](https://docs.github.com/en/rest/pulls/pulls)
4. **워크플로 정의와 실제 실행을 연결할 수 있다.** 공식 Claude Code Action 같은 도구의 워크플로 경로와 해당 SHA의 실행을 대조한다. GitHub workflow runs API는 head_sha, path, actor, status/conclusion 등을 제공한다. 정의 파일만 있거나 실행 성공만 확인된 경우 코드 작성 완료로 승격하지 않는다. [Claude Code Action](https://github.com/anthropics/claude-code-action), [Workflow runs API](https://docs.github.com/en/rest/actions/workflow-runs)
5. **공개 저장소만으로 완전한 사용률을 알 수 없다.** Claude Code의 사용자 설정은 홈 디렉터리, 로컬 설정은 보통 Git에서 제외된다. 흔적 미발견은 미사용이 아니다. [Claude Code settings](https://code.claude.com/docs/en/settings)

## 추천: 근거를 합쳐 도구별로 분류

파일 종류만 늘리면 빠르지만 설정 템플릿과 실제 사용이 섞인다. 소유자 연동만 요구하면 신뢰도는 높일 수 있어도 미등록 프로젝트를 놓친다. **공개 근거를 단계별로 합치고, 소유자 제공 정보를 보완 경로로 두는 방식**을 권장한다.

| 우선순위 | 개선 | 구현 범위 / 판정 |
|---|---|---|
| 1 | 검사 누락·부분 검사와 최신성 개선 | 발행 미검사 1,715개 우선 대기열, 부분 검사의 실패 사유·예산 소진 분리, 기본 브랜치 변경 시 증분 검사, 동일 SHA는 기존 결과 재사용. 실패를 미발견으로 저장하지 않음 |
| 1 | 최근 커밋 자체 순회 | 최초 최근 90일·최대 100개를 제안 범위로 삼아 커서 수집, 이후 마지막 SHA부터 증분. 발견용 검색과 분리. 트레일러 + author/committer + 변경 파일을 함께 저장. API 비용은 파일럿에서 실측 |
| 1 | 도구 이름·근거 등급 정규화 | 도구(client) / 모델(model) / API 제공자(gateway) / 역할(작성·리뷰·커밋)을 분리. `claude-code`, `github-copilot` 같은 ID를 통일하고 다중 도구 허용 |
| 2 | 하위 프로젝트·포크 처리 | 제한된 재귀 트리 또는 패키지 경로 탐색. 제품 디렉터리 scope를 유지하고 상위 지침 상속을 표현. 템플릿·포크 상속은 독립적 사용 근거로 세지 않고 이후 원본 변경을 확인 |
| 2 | PR + Actions 교차 확인 | 도구 계정/App 식별, PR 변경 파일·SHA·병합 관계와 실행 기록 연결. 문서 작성/리뷰 전용 봇 활동은 개발 도구 작성 지표에서 분리. Git 메타데이터 서명만으로 AI 사용을 인증했다고 주장하지 않음 |
| 3 | 제작자 확인 보완 | 소유자가 도구·기간·역할을 직접 신고하거나 opt-in 연동으로 최소 실행 메타데이터 제공. 본인 신고/관측을 분리하고 원문 대화나 비밀 설정은 수집하지 않음 |

### 지표 연결 규칙 제안

- `활동 기록 관측`: 제품 scope에 연결된 커밋/PR/실행 기록에서 도구와 역할을 확인. 공개 지표 문구도 ‘관측’으로 표현한다.
- `설정만 발견`: 전용 설정·모델 설정은 존재하지만 활동 근거 부족. 활동 지표의 분자에서 제외한다.
- `제작자 신고`: 저장소 관측과 별도 출처로 유지한다.
- `미확인`: 미검사/부분 검사/미발견은 내부 상태를 구분하고, AI 미사용으로 계산하지 않는다.
- 동일 프로젝트의 Claude+Cursor 사용은 둘 다 표현하되 전체 프로젝트 수는 중복 제거한다. 도구별 비율 합이 100%를 넘을 수 있음을 지표 정의에 명시한다.
- 최신 사용과 과거 사용을 구분한다. 활동 90일 창 밖 근거는 이력으로 보존하며, 단순 날짜 만료로 역사 자체를 삭제하지 않는다.
- 기존 `products.builder`를 관측값으로 덮어쓰지 않는다. 관측에서 파생한 별도 도구 요약을 목록·필터·통계가 함께 사용하고 신고 출처도 유지한다.

### 작은 비교 실험부터

발행 항목 중 미검사 100개, 설정만 발견 100개, 커밋 근거 보유 100개를 층별 추출해 동일한 시점/저장소 SHA에서 기존 탐지와 개선 탐지를 비교한다. 각 층 결과를 별도 보고하고 전체 모집단 비중으로 보정한다. 편의 표본의 단순 평균을 전체 탐지율로 발표하지 않는다.

측정: 새로 식별한 프로젝트·도구 수, 수동 판독 정밀도, 템플릿/포크 오탐, 미검사·부분검사 비율, API 요청/프로젝트, 처리 시간. 소유자 정보 등 정답 집합이 없으므로 ‘실제 사용 전체에 대한 재현율’은 주장하지 않는다. 판정 기준을 먼저 고정하고 관찰 모드로 비교한 뒤 지표 연결 여부를 정한다. 현재 보고서에는 탐지 개선 효과에 대한 예측 수치를 넣지 않았다.
