# 공유 모델 한도와 단계별 처리량

## 설정과 실행의 구분

관리자 `작업 ↔ AI 모델`에서 대체 실행은 한 작업에 실패 시 다음 순위를 사용한다. 작업 분산은 서로 다른 작업을 구성원 중 한 모델에 배정한다. 같은 입력을 모든 구성원에게 보내는 합의 심사가 아니다. 구성원은 최대 4개이며 실제 병렬도는 각 작업의 동시 실행 설정과 공유 엔진 한도에도 제한된다.

1차와 2차에 같은 연결·모델을 선택할 수 있다. 같은 후보를 두 단계에서 처리할 수도 있지만, 2차의 별도 실제 호출과 유효한 결과는 여전히 필수다. 2차 내부에서 같은 canonical 모델을 여러 투표자로 세는 제한, 세대·원문·정책·공개 CAS는 유지한다.

관리자 `장비·용량`의 공유 한도는 등록된 연결과 실제 정책의 장비 그룹을 표시한다. `공유 최대 동시 실행` 하나로 운영 한도와 물리 엔진 최대치를 함께 저장한다. 여러 단계에서 사용하는 예약·실행을 합산하는 한도다. 기존 역할 우선순위와 유휴 정책은 고급 설정에서 유지하며, 새 한도를 초과하는 보조 상한·예약 여유만 줄인다. 저장 시 정책 hash와 장비 버전을 검사한다. 진행 중 호출은 종료시키지 않는다.

2026-11-05 실제 공식 장비 writer로 GPU3090 Qwen은 5, Supa 직접 연결 Qwen은 2로 변경했다. 이 데이터 변경은 소스 배포 및 모델 분산 구성 저장과 별개다. 다른 기존 장비나 은퇴한 정책 그룹은 일괄 변경하지 않았다.

## 병렬화하는 범위

- 발행 분류: API 작업 분산에서 최대 10개 후보씩 서로 다른 묶음을 분류한다. `crawl-publish.classifierConcurrency`는 1~4이며 기본 1이다. 실제 공개·반려·중복 방지·후속 등록은 기존 후보별 CAS 순서로 수행한다. 기존 ConnectAgent CLI 대체 실행은 유지한다.
- 후처리: 제품 번역과 한국어 소개문은 기존 경로 동시 실행 설정으로 서로 다른 묶음을 처리한다. 선택과 중복 제외는 직렬로 확정하고 모델 호출은 병렬로 수행한다. 시작한 호출은 정산까지 기다린다. 검색 프로필·검증 등 기존 병렬 경로는 재작성하지 않는다.
- 모델 구성 저장 자체가 운영 병렬 활성화를 뜻하지 않는다. 모델별 serving 계약, 작업 실행 모드, 작업 동시성, 전역 용량 모드가 모두 실제로 허용해야 호출한다. 설정하지 않은 작업에 임의 모델을 배정하지 않는다.

## 느린 작업과 고아 작업

정상 소유자·리스가 살아 있는 호출은 오래 걸린다는 이유로 해제하지 않는다. 기존 maintenance가 최대 20개씩 공정한 cursor로 실제 단일 인스턴스의 고아 모델 dispatch를 확인한다. 기본 30분의 조용한 기간, 살아 있는 리스 부재, 실제 후속 boot 또는 종료 기록을 기존 판정기로 확인한 경우만 미확정 검토 상태로 옮긴다. 이는 업무 성공이나 native 종료 증거가 아니며 점유를 임의 해제하거나 검토를 자동 완료하지 않는다.

이 배포는 과거 미확정 기록을 일괄 삭제하거나 완료 처리하지 않는다. 종료 증거가 부족한 점유는 기존 용량·운영 검토 규칙을 따른다. 다른 대상의 독립 작업은 가능한 범위에서 계속 처리하고, 전역 DR·작업 소유권·실제 장비 포화는 계속 존중한다.

## 배포 경계

발행 API binding의 append-only 장부 규칙은 0166 migration이다. 공식 DRAINING 및 실제 reserved/dispatched=0 확인 후 별도 한 번 실행 절차로 이전한다. 코드 병합이나 앱 재시작만으로 적용됐다고 기록하지 않는다. 기존 0165 이력과 SQL guard를 보존한다.

로컬 전체 테스트나 수동 모델 기능 검사는 사용자 지시에 따라 실행하지 않는다. 필요한 정적 검사와 저장소 필수 CI를 유지한다. 코드 리뷰는 실제 설치된 OpenCode CLI의 `opencode-go/deepseek-v4.1-flash`, `--variant max`로 독립 범위를 병렬 실행한다. 길이 한도 종료·최종 답변 없음·검토 미완료 응답은 통과로 기록하지 않는다. 리뷰 결과와 배포 완료 여부는 실행 영수증을 기준으로 별도 보고한다.
