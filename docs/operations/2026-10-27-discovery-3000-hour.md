# 수집 시간당 3000 — 2026-10-27

목표는 새 고유 저장소의 발견과 원본 확보다. 승인 제품 3000건/시 발행이 아니고, AI2 생애주기와 분리한다. 이 문서를 쓰는 시점에는 3000을 관측하지 않았다.

## 관측으로 받은 기준

과제에 적힌 최근 1시간은 발견 435, 원본 425다. 24시간은 발견 7919, 원본 7802다. 루트 감사 13:41 기준선은 새 고유 383/시, 원본 문서 382/시다. 검색은 켜진 GitHub 신호 16개와 Show HN이다. 저장값 pagesPerTick 은 6, 최근 창은 3일, 검색 페이지는 100건이다. 이 세션은 그 숫자를 다시 재지 않았다.

## 숫자

검색 페이지. 예전 카탈로그는 10분마다 1틱이다. 저장값 6페이지면 시간당 36페이지다. 지금은 전용 `discovery` 줄에서 60초마다 1틱이다. 저장값 6이면 시간당 360페이지, 코드 상한 10이면 600페이지다. 둘 다 확인된 검색 신원 하나의 1,800보다 작다. 코드는 저장된 pagesPerTick 을 바꾸지 않는다.

입장 상한. `discover.maxNewPerHour` 기본값 3000은 기존 5분 창으로 나눈다. `floor(3000 × 300000 / 3600000) = 250`. 시드만 이 값을 `discoveryAdmission` 에 넘긴다. 원본 버퍼 호출은 인자를 그대로 두고, 건강한 큐의 남은 수는 예전처럼 무한이다. 대기 500건이 5분 이상이거나 1,000건이면 기존 압력 허용량(5분에 100건 근처)이 250보다 먼저 적용된다. 상한에 닿으면 그 틱은 검색을 더 하지 않고, 다음 60초 틱이 다시 읽는다. 중복 삽입은 몫을 줄이지 않는다.

홈페이지가 병목일 때의 원본 확보 상한은 `동시성 × 3600000 / 지연밀리초` 다. 동시성 8, 지연 10.5초는 시간당 2,742라 3000에 못 미친다. 그래서 동시성은 12다. 10.5초면 4,114, 14초면 3,085, 15초면 2,880이다. 15초 이상이면 홈페이지 지연이 3000을 막는 요인이다. `crawl-fetch` 는 전용 `fetch` 줄이고 예산은 120초다. 감독 잡 상한 180초 안에 있으며, 예산이 끝날 때까지 묶음을 이어 받아 줄을 쉬지 않게 한다. 이 식은 줄이 실제로 그 지연으로 가득 찰 때의 상한이지, 관측값이 아니다.

GitHub `api.github.com` 은 페치 한 번 안에서 여전히 직렬이다. getRepo 가 1.2초면 직렬만으로 시간당 3,000이고, 그보다 길거나 흔적 탐침이 대부분의 저장소에 붙으면 홈페이지 동시성 12로도 3000에 닿지 않는다. 직렬을 풀지 않는다. 1차·2차 한도 응답은 기존 쿨다운으로 틱을 미룬다.

getRepo 3,000회만 보면 코어 15,000/시보다 작다. 여기에 탐침·agent scan·별·README 요청이 붙으므로 전체 비용이 15,000 안에 드는지는 운영 관측이 필요하다. 한 버킷이 먼저 바닥나면 기존 쿨다운이 그 자격만 쉬게 하고, 코드가 한도를 무시하지 않는다.

## 적용

병합·배포 뒤 저장된 JSON 에 `maxNewPerHour` 가 없으면 읽기 기본값 3000이 바로 250/5분 상한이 된다. DB 쓰기는 없다. 루트는 검토된 정식 도구로만 `discover.maxNewPerHour` 와 `discover.pagesPerTick` 을 맞춘다. 지금 저장값이 6이면 그대로 두는 쪽이 이 계산과 같다. 10으로 올리는 것은 시간당 600페이지로, 여전히 검색 신원 하나 안이다. 심사 동시성, 발행 주기, 모델 용량, 역할 lease, 출처 검사, 중복 제거, origin 정책, 소스 백프레셔는 건드리지 않는다.

크롤러 프로세스의 DB 연결 상한은 4에서 8이다. 프로세스당 기본 연결 +4, M3 와 mini 가 각각 크롤러를 두면 상시 +8, rollout 겹치면 그 배가 카탈로그에 잡힌다. 호스트 예산이 켜져 있으면 이 8이 풀 상한이다. 페치 동시성 12는 풀보다 크다. HTTP 중에는 연결을 잡지 않고, 저장이 몰리면 기존 풀 대기만 한다.

루트가 14:01 KST에 읽은 실제 설정은 crawler-m3·crawler-mini 모두 `DB_POOL_MAX=4`, host budget 비활성이다. 환경변수가 코드 기본값을 덮으므로 두 crawler 앱의 이 값도 8로 맞춘 뒤 공식 배포 계획을 만들어야 한다. agent-scan consumer의 명시적 4는 유지한다. 같은 시각 DB 최대 연결은150(관리자 예약3), 전체 세션68이었다. 운영 반영 뒤 실제 풀과 세션 수를 다시 읽으며, 이 순간 관측을 장기 여유 보장으로 쓰지 않는다.

Show HN 30분 주기는 그대로다.
