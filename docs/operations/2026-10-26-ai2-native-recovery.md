## 복구 및 배포 검증

전환 전 남아 있던 Supa 검색 검증 `84d146b2…`와 MLX 1차 검수 `1337833c…`는 실제 원 실행자·중계·모델 프로세스의 종료를 확인한 뒤 해당 요청만 철회했다(audit 20091·20093). 사용량이나 모델 성공 결과를 만들어 넣지 않았다. 공유 서비스 여섯 개는 기존 소스·설정으로 모두 복원했다. 일회성 중단·철회·복원은 재실행하지 않았다.

웹 두 개와 모니터 하나는 실제 배포가 완료됐지만 기존 검증 스크립트는 실패했다. 원 실행의 실패 기록을 보존하고 다음 두 원인을 구분해 별도 읽기 전용 검증을 수행했다.

- 원격 기본 Python 3.9가 Docker 나노초 시각을 읽지 못해 모니터 수신 확인을 놓쳤다. 서버에 이미 설치된 Python 3.13에서 동일한 공식 파서를 실행하여 실제 두 수신처의 최신 DOWN 수신을 확인했다. 서비스나 서버 설정은 바꾸지 않았다.
- 새 웹 이미지에 상속된 Healthcheck가 추가되어 이전 컨테이너와의 엄격 비교가 실패했다. 서비스 명령·환경·마운트·spec은 보존됐고 해당 차이가 실제 새 이미지 설정과 정확히 같은지 별도 확인했다. 기존 guard 자체가 통과했다고 기록하지 않았다.

18개 앱의 현재 소스·이미지·설정·건강 상태 및 나머지 15개 앱의 유지 상태를 확인했다. 실제 텍스트 경보 네 개는 정상으로 바꾸어 기록하지 않았다. 별도 상시 관측 프로세스나 자동 복구는 추가하지 않았다. Oracle 범위는 감시·알림이다. 서브에이전트는 복구·검증 소스와 고정 증거를 읽기 전용으로 검토했고 P1/P2를 찾지 못했다.

## 남은 PR 제안 — 운영 영향 순서

아래는 새 PR 범위 제안이며 아직 PR을 생성하거나 수정 코드를 배포하지 않았다. 이번에 병합·배포한 PR은 [#664](https://github.com/JRVector9/nomorevibe/pull/664), [#665](https://github.com/JRVector9/nomorevibe/pull/665), [#666](https://github.com/JRVector9/nomorevibe/pull/666)이다.

1. **의도한 중단 중 작업 재시작 방지**: text 진행 감시가 capacity drain·수집 일시 중단을 고려하지 않아 `progressRestart=true`로 정상 종료하는 실제 기록을 확인했다. 원격 모델 실행이 남은 상태에서 로컬 일꾼만 재시작하면 미확정 요청으로 이어질 수 있다. 의도한 중단을 감시에 반영하고 프로세스 생존·lease 상실과 구분한다. 자동 모델 재시작이나 증거 없는 슬롯 해제는 추가하지 않는다.
2. **텍스트 번역 대기열 진행 회복**: reason 번역의 재시도마다 배치 구성과 work key가 바뀌는 현상을 확인했다(14요청·14 work key, 예약 만료 반복·실제 dispatch 없음). 이미 예약한 배치를 이어 처리하도록 고정하고 새 배치 생성과 구분한다. keywords·keyword-verify·product-translate·tagline-ko의 실제 `upstream_stalled` 경보도 남아 있다. product 번역의 `english_uncertain` 거절은 네트워크 실패가 아니라 출력 검증 실패로 구분해야 한다.
3. **배포 후 자동 검증 오류 수정**: Python 3.9에서도 Docker RFC3339Nano 시각을 정확히 읽고, 실제 대상 이미지에 선언된 Healthcheck 상속만 허용하도록 검증기를 고친다. 위조·누락 ACK, 명령·환경·마운트 변경은 계속 실패시킨다. 정상 배포를 실패로 오인해 중복 배포나 수동 확인을 유발하는 문제를 줄이는 범위다.

소개 검수 `product-intro-check/claude-cli/sonnet`은 기존 `no_contract` 보류가 남아 있다. 이번 open 명령은 이 경로 한 개의 보류를 명시적으로 확인하고 진행했다. 백업 복구·장기 관측 등 기존 미검증 운영 과제는 기존 PENDING 기록을 따른다.
