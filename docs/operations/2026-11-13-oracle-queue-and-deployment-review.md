# Oracle 대기열 확대와 일반 탐색·배포 차단 확인

2026-11-13 · 운영 읽기 전용 실측 05:08–05:12 UTC (14:08–14:12 KST)

## 결과

대기열 10,000 → 50,000건 확대를 격리 브랜치 `xaegis/4cd9ea6a-discovery`에 구현·검증했다. 운영에는 아직 적용하지 않았다. 일반 탐색 수정은 이미 main `25824182`(PR #934)에 있으나 운영 crawler는 `5b058e83`이며, 실제 소스 해시도 구버전과 일치했다. 따라서 일반 탐색의 운영 병목은 아직 해소되지 않았다.

## Oracle 대기열은 무엇인가

저장한 05:10:24 UTC의 실제 staging은 다음과 같았다.

| 판정 | 상태 | 수 |
|---|---|---:|
| 미판별 unknown | pending | 9,900 |
| 한국어 확인 yes | pending | 15 |
| 한국어 확인 yes | applied | 1,465 |
| 비한국어 no | excluded | 177 |

즉 당시 대기 9,915건이 모두 한국어 확인을 마친 것은 아니다. Oracle은 한국어 검색어·공유 검색 페이지의 한글 설명에서 **후보**를 찾은 뒤 설명·README의 한국어 내용을 확인한다. 한국어 확인 yes만 M3 공통 수집 큐에 전달하고 이후 AI 제작 근거·규칙 심사·소개 생성은 별개다. 한국어라는 판정은 제작자 국적이나 한국 소재 프로젝트임을 보증하지 않는다. applied 역시 공개 발행 수가 아니다.

조회 당시 검색 조건 3개는 모두 `staging_capacity_or_lease`였다. 이 오류 이름 자체는 용량·lease를 함께 나타내지만, 남은 공간이 85건인 반면 한 페이지는 최대 100건인 상태는 용량 제한과 일치한다. Oracle unit은 별도 조회에서 active/running, 시작 03:53:26 UTC, NRestarts=1이었다. 재시작 원인은 이번에 조사하지 않았다.

## 선택과 변경

유한한 5배 완충 공간을 확보하면서 기존 데이터·전송/심사 예산을 보존하는 **50,000건 상한**을 선택했다. 자동 무제한 확대나 판정 기준 변경은 하지 않았다.

- `KOREAN_STAGING_MAX_PENDING` 한 곳에서 직접 검색 적재·공유 페이지 재사용·운영 화면 집계 상한을 정의한다.
- 기존 advisory transaction lock 아래 공간을 확인한다. 부족하면 페이지/cursor를 확정하지 않는다. 동일 저장소는 새 공간 없이 재사용한다.
- 공유 페이지는 최대 100건 공간을 확보하고, 관리자 집계도 50,001건까지만 읽어 상한 초과를 표시한다.
- 화면에 한국어 판별 전 후보 포함과 50,000건 상한을 명시했다. 기존 판별/적용 이력·커서는 삭제하지 않는다.
- DB 마이그레이션·권한 확대가 없다. 실제 반영에는 Oracle 소비자의 코드 갱신도 필요하다. Dokploy 앱만 갱신해서는 Oracle 상한이 바뀌지 않는다.

상한 증가는 처리량 증가가 아니다. Oracle은 회차당 언어 확인 최대 5건, 다음 회차 전 15초 대기이며 검색·네트워크 시간도 소요된다. 미판별 유입이 확인 속도를 계속 넘으면 5만 건에도 다시 도달할 수 있다. 이번에는 동시성·API 한도·공통 큐 예산을 임의로 올리지 않았다.

## 일반 탐색 병목

운영 `crawl-seed`는 05:12 UTC에도 Claude 커밋 트레일러의 과거 페이지 2, `2026-10-24T15:13:11Z..15:13:26Z`에 있었다. 최신 탐색도 `2026-10-26T10:47:14Z..10:47:45Z`였다. 수집기 컨테이너의 seed.ts/github.ts/shared-discovery.ts SHA256은 모두 git `5b058e83`과 일치하고 main의 파일과 달랐다.

main의 기존 수정은 커밋 검색만 원문 수신 상한 2MiB → 8MiB, 저장용 요약 캐시는 2MiB 유지, 검색어별 독립 날짜/실패 진행과 백오프, 큰 응답의 범위 분할·미완료 보존, 최신 커서 통합 시 비활성 구간/부분 페이지 보존을 포함한다. 이번 브랜치는 이 수정본을 기반으로 하며 탐색 코드를 중복 수정하지 않았다. 관련 회귀와 실제 DB cursor 재개 검사를 다시 실행했다.

앞선 비교 보고의 동일 2,870,600B 응답·20회 모의 실행 결과는 `docs/operations/2026-11-13-discovery-comparison-review.md`에 있다. 이는 앞선 모의 실행의 근거이며 이번 운영 처리량으로 재표기하지 않는다. 이번에는 이미 통과한 관련 회귀를 현재 브랜치에서 재검증했다.

## 배포를 막는 요청

요청 `69781c87-fc49-40d6-af75-db39343102a7`은 검색 결과 검증 `product-search-verify`, 모델 supa, 소유자 m3-text의 **미종결 장부 기록**이다. 예약 실행이나 Oracle 검색 요청이 아니다.

- 전송 시각: 2026-11-13 00:04:45.742 UTC (09:04:45 KST).
- 상태: dispatched. 이 요청에 기록된 용량 이벤트는 queued → reserved → dispatch_started뿐이며, 조회된 terminal 이벤트는 없었다.
- 같은 boot `c861b385-c3cd-4592-af5e-a6ea7eb6beb6`가 현재 text 역할의 살아 있는 lease를 유지했다.
- `judgeOwnerGone`는 살아 있는 역할 lease가 있으면 `owner_holds_role_lease`로 거절한다. 이번에는 운영 상태를 바꾸는 회수 실행을 하지 않았다. 앞선 실행의 거절과 현재 소스·lease 근거를 대조했다.
- 접수는 OPEN이고 새 번역/검증 작업과 성공 시각이 갱신되고 있다. 서비스 전체 중단이 아니라 안전 교체를 위한 drain 관문의 차단이다. 이 미종결 기록이 실제 모델 엔진에서 5시간 연속 실행 중이라는 증거는 확보하지 않았다.

정상 결과를 얻었다고 가장하거나 행을 삭제/강제 정산해 관문을 우회해서는 안 된다. 종료 근거를 확보한 정식 복구가 필요하다.

- 관련 단위 9개 파일 **96건 통과**: 일반/최신 탐색·구간 보존·GitHub 수신 경계·Oracle 계약/상태/소비/적용/언어.

- Next typegen, 전체 TypeScript `tsc --noEmit --incremental false`, 변경 TS/TSX 6파일 ESLint, `git diff --check` 통과.
- 전체 unit/DB·build·브라우저·GitHub 필수 CI·실제 배포 후 처리량 검증은 실행하지 않았다. 단순 CLI 접수 성공을 운영 검증으로 기록하지 않는다.
- 운영 SQL 초기에 컬럼/타입 불일치로 읽기 2회 실패했고 올바른 request_id와 boot ID 형변환으로 재조회했다. 운영 쓰기는 없었다.

## 남은 승인과 실행 순서

현재 등록 프로젝트 범위는 **로컬 코드 수정·검증까지**이며 외부 게시·배포 승인을 포함하지 않는다. Coach 공유 체크아웃·진행 큐를 건드리지 않았다. 기존 `xaegis/4cd9ea6a` 브랜치도 보존하고 최신 main 기반 새 브랜치에서 작업했다. 사용자에게 필요한 것은 자격 정보 입력이나 SQL 실행이 아니라 별도 운영 변경 승인이다.

승인 범위 제안: 이 검토 브랜치의 PR 생성/필수 최신-base CI/병합, 미종결 요청 한 건의 제한 복구, 공식 절차에 따른 M3·mini 및 Oracle 코드 반영과 후속 측정.

1. 최신 운영/CI/다른 배포 여부와 미종결 요청을 재조회한다. 이미 해결됐다면 불필요한 복구를 생략한다.
2. 복구가 필요하면 접수를 DRAINING으로 전환해 다른 실제 진행 요청을 마친다. text 소유 프로세스와 요청별 종료 근거를 수집하고 정상 종료를 우선한다. 같은 boot가 역할을 유지한다는 이유로 회수 관문을 낮추지 않는다.
3. 명시적으로 승인된 제한 재시작이 필요한 경우 주·예비를 함께 고려해 옛 text boot의 실제 종료/후속 boot 근거를 확인한 뒤, 정식 owner-gone 도구가 허용할 때만 결과 미확정으로 전환한다. 모델 성공/토큰 사용량/terminal을 만들어 넣지 않는다. 추가 승인이나 근거가 필요하면 중단하고 OPEN 복구를 확인한다.
4. 새 최신 main과 필요한 필수 CI·이미지를 검증하고 `npm run deploy -- scope|plan|run`을 따른다. Oracle은 해당 native consumer의 별도 공식 반영 경로를 쓴다. 실패한 once 경로는 재사용하지 않는다.
5. 실측으로 새 릴리스·소스·접수 OPEN과 정상 서비스 확인 후, 동일 시간창에서 일반 탐색/Oracle 신규 유입, 검색어별 완료 날짜, invalid_response/큰 응답 오류, 미판별 증감, 원본 수집·규칙 심사 처리량을 구분해 비교한다. 이 확인 전에는 일반 탐색 해결 완료로 기록하지 않는다.
