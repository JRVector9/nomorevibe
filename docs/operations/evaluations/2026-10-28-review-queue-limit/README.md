# 검수 대기열 상한과 GitHub 탐색 분리

사용자 요청: 검수 대기열 기본 상한을 1,000,000건으로 늘리고 관리자에서 조절한다. 기존 검수 적체 시 1페이지 제한과 LLM 동시 한도의 관계를 확인한다.

선택: 고유 미완료 저장소 수를 기준으로 탐색 수용을 결정한다. 검색 페이지 수나 LLM 동시 실행 수를 대기열 용량으로 사용하지 않는다. 기존 데이터 삭제나 검수 정책 변경 없이 대기 작업을 보관할 수 있기 때문이다.

관리자 크롤 설정의 **수집 범위 → 검수 대기열 상한**에서 `discover.maxReviewBacklog`를 1~10,000,000 사이의 정수로 조절한다. 기본값은 1,000,000이며 기존 저장값에 필드가 없어도 새 코드가 읽을 때 기본값을 채운다. 옛 화면에서 필드를 보내지 않으면 기존 값을 보존한다. 저장 시 기존 관리자 인증, 설정 판 비교, 스키마 검증, 감사 기록을 이용한다. 작업은 다음 설정 조회부터 값을 적용한다.

미완료 저장소는 대소문자 구분 없이 합집합으로 센다.

- 별칭이 아닌 pending/fetching 탐색 큐 항목: 원본 수집 전 대기와 미래 재시도도 포함한다.
- 원본 문서가 있으나 후보가 아직 없는 항목.
- new/approved/needs_review 후보: 자동 검수·사람 검토·진행 중 검수를 포함한다.
- published/rejected 후보와 완료/실패/건너뜀 탐색 큐 항목은 다른 미완료 작업이 없는 경우 제외한다.

GitHub 탐색은 상한 미만에서 설정된 페이지 예산을 유지한다. 실제 신규 적재는 남은 큐 자리와 기존 5분 신규 수집 예산 중 작은 값을 사용한다. 상한 도달·큐 깊이 조회 시간 초과에서는 새로운 검색 호출 없이 기존 커서를 보존한다. 상한을 높이거나 기존 작업이 완료되면 이어서 탐색한다. GitHub 인증·API 쿼터·요청 실행 예산은 계속 적용한다.

선택적으로 켜는 source buffer도 같은 설정을 사용한다. 탐색 큐 자체가 가득 찼다는 이유로 기존 원본 수집을 중단하지 않으며, 이미 원본이 있는 항목의 갱신 경로를 보존한다. 크롤러 활동에는 대기 저장소 수·설정 상한을 표시하고 이를 회차별로 합산하지 않는다.

기존 500건+5분/1,000건 압력 정책은 LLM 동시 한도와 별개의 탐색 제한이었다. seed와 source buffer에서 이 정책 호출을 제거했다. `discovery-admission.ts`는 이전의 실행 가능 단계 측정·진단 코드로 남아 있으며 실제 신규 탐색 수용은 `review-backlog.ts`가 맡는다.

범위: 이 상한은 GitHub 탐색의 신규 적재 배정 기준이다. 다른 수집원·관리자 직접 등록을 모두 직렬화하는 DB 전체의 강제 행수 제약은 아니다. 동시에 다른 경로가 적재하면 다음 탐색 회차에서 증가분을 반영한다. DB에 100만 건을 실제 적재하는 부하 검사는 수행하지 않았다.

검증: 관련 회귀 111개, 크롤러 활동 34개, 활동 화면·집계 15개로 총 160개 통과. Next route typegen 후 전체 TypeScript 검사 통과. 변경 파일 ESLint 및 git diff --check 통과. 최초 TypeScript 검사는 격리 worktree에 Next 생성 PageProps가 없어 실패했고 typegen 후 재검사했다. 최초 회귀의 예전 압력 정책 기대값 2건은 새 동작에 맞춰 수정 후 통과했다. DB 전용 테스트 포트 55435에는 리스너가 없고 Docker 소켓 접근이 거부되어 DB 통합 검사는 실행하지 못했다. 고유 저장소 합산·재시도 포함·종료 시 자리 반환을 확인하는 롤백형 통합 검사 코드는 준비했다.

공개 PR 게시·병합·운영 배포 및 운영 설정 변경은 이 구현 단계에서 수행하지 않았다.
