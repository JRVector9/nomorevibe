# 근거 수집 복구와 생존 확인 처리량 개선안

2026-09-21 작성, 2026-09-22 재검토 보완. 기준 수치는 같은 폴더의 `README.md`와 `evidence.json`에 기록한 운영 측정이다. 이번 변경은 근거 수집의 로컬 코드 수정이다. 운영 배포·운영 DB 수정·생존 확인 설정 변경은 하지 않았다.

## 근거 수집: 반복 실패 수정

운영에서 확인한 `hraness/atet`, `hraness/hra`, `hraness/message-like-me`는 각각 스캔 행의 저장소 이름과 cursor 이름이 달랐다. 한 시간에 각 44회, 총 132회 예외가 발생했다. GitHub ID·commit SHA·탐지기·scope를 고유 키로 쓰는 upsert가 cursor만 갱신하고 저장소 이름을 갱신하지 않는 경로를 로컬 DB 테스트로 재현했다. 최초 운영 쓰기를 재생한 것은 아니다.

수정 내용:

1. 같은 불변 ID로 충돌하면 **기존 스캔의 repositoryKey·ID·관측 근거를 유지**하고 cursor의 이름을 저장된 이름에 맞춰 같은 upsert에서 일관되게 저장한다. GitHub ID·head·탐지기·scope가 모두 같은 충돌에서만 적용한다. 별칭의 cursor 안에 캐시된 커밋 분석 결과는 제거하고 커밋을 다시 조회·검증한다.
2. collector의 검증은 유지하고, 검증 실패를 `InvalidAgentScanCursorError`로 구분한다. refresh는 이 오류에 한해서 cursor 없이 한 번 재시작한다. 다른 네트워크·DB·프로그래밍 예외를 무한 재시도하거나 숨기지 않는다.
3. 재시작은 원래 작업 예산 안에서 공개 여부·GitHub ID·현재 head를 다시 조회한다. 다른 이름의 cursor에 현재 이름을 붙여 신뢰하지 않는다. 같은 이름이 다른 GitHub ID로 바뀌었다면 별도 스캔을 만든다.
4. 재조회 실패는 기존 저장 경로로 원인 코드와 재시도 시각을 남긴다. 일반 실패는 15분, GitHub 한도는 reset 시각을 따른다. 기존 완료 근거의 확인 시각은 성공 없이 갱신하지 않는다. 예산이 없으면 네트워크·저장을 하지 않고 다음 회차로 넘긴다.
5. 별칭으로 수집했다고 기존 주소까지 확인됐다고 보지 않는다. 충돌 시 기존 확인 시각을 보존하고 `alias_recheck_required`로 보류한다. 남은 파일이 없어도 재개 우선 대상에 포함해 기존 이름의 공개 여부·ID를 다시 확인한다. 이 보류는 refresh 반환과 작업 로그에도 전달돼 조기 재심사·제품 연결을 막는다.
6. 별칭 재확인과 API 한도·통신 실패가 겹쳐도 upstream 오류와 재시도 시각을 우선한다. 즉시 재확인 대상으로 바꿔 API 한도를 우회하지 않는다.

수동으로 문제 행만 지우는 안은 재발을 막지 못하고 근거를 잃을 수 있어 선택하지 않았다. 기존에 손상된 cursor의 이름을 무조건 바꾸는 안도 선택하지 않았다. 새 수집 결과를 저장할 때는 불변 ID의 일치를 DB 충돌 키로 확인한 뒤 재개 정보를 연결하며, 이후 원래 주소의 공개 여부·ID도 재확인한다. 전체 스키마를 별칭 테이블 중심으로 바꾸는 안은 추가 작업으로 남겼다. 현재 수정은 여러 별칭의 조회 캐시를 통합하지 않으므로, 옛 이름과 새 이름이 계속 함께 유입되면 불필요한 재조회가 남을 수 있다.

9월 21일 최초 수정은 충돌 시 저장소 이름 자체를 갱신했다. 22일 재검토에서 이것이 기존 이름의 제품·심사 조회를 끊는 부작용을 테스트로 재현했다. 위 방식으로 보완했으며 최초 수정안의 이름 갱신 동작은 최종 코드에 남아 있지 않다.

운영 반영 후 확인할 항목은 세 저장소의 `invalid agent scan cursor` 반복 소멸, 스캔 완료 또는 오류·미래 `next_attempt_at` 기록, 우선 재개 슬롯이 다음 저장소로 이동하는지다. 기존 수천 건의 partial이나 GitHub 한도 적체 전체가 이 수정만으로 없어지는 것은 아니다.

## 생존 확인: 먼저 배치 상한을 늘린다

관측된 대상은 16,845개 웹사이트다. 현재는 1분마다 최대 15건, 실제 900건/시간이다. 6시간 이내 전수 확인에는 평균 **2,808건/시간(분당 46.8건)**이 필요하다. 현재 계산상 한 바퀴는 18.7시간이며, 6시간 초과가 13,102개(77.8%)였다. maintenance 작업 시간 합은 16.5%였고 uptime 15건의 실행 시간은 중앙값 3.814초, p95 10.635초였다.

| 대안 | 계산상 처리 상한 | 이점 | 제약·선택 기준 |
| --- | ---: | --- | --- |
| **A. 1분마다 최대 60건** | **3,600건/시간**, 전수 4.68시간 | 가장 작은 변경. HTTP 동시 3개·origin별 직렬·DB 쓰기 직렬 유지 | 작업 예산 25초·느린 응답·다른 maintenance 작업 때문에 실제 상한은 낮아질 수 있음. 우선 적용 권장 |
| B. 30초마다 최대 30건 | 3,600건/시간, 전수 4.68시간 | 한 번에 maintenance를 점유하는 시간을 줄임 | scheduler/worker 조회·리스·선택 쿼리 빈도가 증가. 주기 요청은 합쳐지므로 실제 실행 횟수가 보장되지 않음 |
| C. 생존 확인 전용 워커 | 워커 예산·응답 시간에 따라 결정 | 썸네일·검색·랭킹 등 다른 작업과 분리 | 역할·DB 풀·리스·종료 절차 변경 필요. 동일 job 이름 워커를 복제하는 것만으로는 리스 때문에 병렬 처리되지 않음 |

3,600건/시간은 운영에서 확인한 개선 결과가 아니라 배치×주기 계산이다. 현재 15건의 p95에 단순히 4를 곱하거나, 동시성만 높여 전수 6시간을 보장한다고 주장할 수 없다. 모든 요청이 10초씩 걸리면 현재 동시성 3과 예산으로는 대략 한 회차 9건 수준까지 떨어진다. 본문·리다이렉트 처리도 있으므로 실제 완료 시간은 더 길어질 수 있다.

A의 구체적 적용 순서:

1. BATCH 15→60으로 조정하고, 오래된 확인 결과부터 선택한다. origin별 직렬, 제품별 최소 6시간, HTTP 동시 3개, DB 쓰기 1개를 유지한다. 동시성 확대는 먼저 하지 않는다.
2. 현재의 `hasBudget()`는 새 요청 시작만 제한한다. 남은 예산에 맞는 요청·본문·리다이렉트 기한을 전달하도록 보완해야 실제 총 실행 시간도 제어할 수 있다.
3. origin 하나의 긴 목록을 한 슬롯이 끝까지 점유하는 현재 구조는 origin별 라운드로빈으로 개선할 수 있다. 같은 origin에는 한 요청만 유지하면서 다른 origin의 오래된 대상에도 차례를 준다.
4. 적체가 충분한 동안 시간당 고유 확인 완료 3,000건 이상을 1차 검증 기준으로 삼는다. 이는 현재 6시간 필요량 2,808건보다 여유를 둔 기준이며, 대상 수가 늘면 `대상 수 ÷ 6`으로 다시 계산한다. 적체 해소 후에는 정상적으로 처리량이 낮아질 수 있다.
5. 1시간 동안 실제 처리량·예산 소진·다른 maintenance 잡 대기·DB 연결/락을 비교하고, 최소 6시간 동안 미확인·6시간 초과 수와 결과 나이 p95가 줄어드는지 본다. 전체 수요는 변하므로 상한 계산만으로 적체 해소 시각을 약속하지 않는다.
6. A가 예산에 자주 걸리면 B로 점유 시간을 분산하거나 C로 분리한다. 여러 워커로 나눌 때에는 origin 단위 분할/공유 제한과 대상 claim이 먼저 필요하다.

`HEAD`만으로 바꾸는 안은 일부 사이트의 응답 차이와 현재 함께 수행하는 본문 갱신 손실이 있으므로 우선안에서 제외한다. HTTP GET을 유지한 배치 확대부터 효과를 확인한다.

## 다음 병목의 우선순위

- 근거 갱신 때문에 승인 후보 90건의 재심사가 막힌 상태는 별도 우선순위 요청으로 푼다. 신규·부분 재개·발행 대기·일반 갱신에 처리 몫을 두고 오래 기다린 항목도 전진시킨다. 신선도 조건을 완화해서 통과시키지 않는다.
- 기존 감사 캠페인의 정책 불일치는 운영 절차로 해결한다. 이전 캠페인 기록을 보존하고 현재 정책의 감사로 전환한다. 이번에는 캠페인을 변경하지 않았다.
- stars/원본/근거의 GitHub 메타데이터 조회를 공유하고 공통 쿼터를 배분한 뒤 stars 배치를 늘린다. 현재 한도 대기가 있어 단순 동시성 확대의 효과가 제한된다.
