# GitHub 탐색 개선 전후 비교 및 보완

2026-11-13 · nomorevibe · 배포 없는 로컬 검증

## 결론

기존 개선의 응답 수용과 검색어별 독립 진행은 동일 입력 비교에서 확인됐다. 다만 최신 탐색의 과거 커서를 최근 커서로 통합하는 과정에서 **비활성 검색어의 미완료 구간 유실**과 **부분 페이지 덮어쓰기**를 재현해 수정했다. 추가로 두 재시도 목록을 합쳤을 때 128개를 넘으면 두 커서를 유지하게 했다.

**선택:** Claude 검색·8MiB 수신 상한·2MiB 캐시 상한·기존 적재 예산을 유지하고, 커서 통합은 기존 진행 기록 보존을 우선한다. 통합이 안전하지 않으면 이미 존재하는 두 커서를 계속 보관하는 방법이 변경 범위가 작고 기존 데이터를 보존하기 때문이다.

## 동일 입력 비교

| 시나리오 | 개선 전 | 기존 개선 | 보완 후 |
|---|---:|---:|---:|
| 20회 실행 중 실패 검색 요청 | 20 | 5 | 5 |
| 같은 실행 중 정상 검색 요청 | 0 | 26 | 26 |
| 정상 검색이 끝까지 본 날짜 | 없음 | 11-13 00:19 UTC | 동일 |
| 2,870,600바이트 정상 JSON 커밋 응답 | 거절 | 수용 | 수용 |
| 같은 크기의 저장소 검색 응답 | 거절 | 거절 | 거절 |

**이 수치는 운영 처리량이 아니다.** 두 검색어·회당 2페이지·가상 시계 1분 간격 20회의 모의 실행이다. 실패 검색은 계속 `invalid_response`를 반환하고, 정상 검색은 완전한 빈 페이지를 반환한다. 따라서 새 저장소 수나 실제 경과 시간 성능을 나타내지 않는다. 정상 검색은 10월 1일 시작 구간부터 독립적으로 따라잡았고, 실패 검색은 기존 개선의 1·2·4·8·15분 대기를 따랐다. 별도 HTTP 비교는 실제 Response 본문 읽기와 JSON 파싱을 통과시킨 합성 입력이다.

## 발견한 문제와 수정

1. 최신 커서 통합에서 이전 커서의 `incompleteWindows`를 이관하지 않아 꺼 둔 검색어의 미완료 범위가 사라졌다. 두 목록을 검색어·날짜 구간으로 중복 제거해 보존하도록 수정했다.
2. 이전·최근 커서에 같은 비활성 검색어가 있으면 얕은 states 병합으로 이전 부분 페이지가 최근 상태에 덮였다. 하나의 상태가 두 페이지를 대표할 수 없으므로 해당 검색어가 다시 실행될 때까지 양쪽 커서를 유지한다. 한쪽에만 있던 상태는 활성 커서의 실제 상태까지 포함해 이관한다.
3. 합친 미완료 목록이 128개를 넘으면 어느 범위도 버리지 않고 통합을 미룬다. 각 커서의 기존 상한은 유지한다.

추가 회귀 6건에서 기존 개선 코드가 **3건 실패**, 보완 코드가 **6건 모두 통과**했다. 실제 PostgreSQL에 jobs 커서를 넣고 다시 runJob으로 읽고 저장하는 추가 통합 2건도 기존 개선 코드에서는 **2건 모두 실패**, 보완 후 전체 통합 실행에서는 **모두 통과**했다. 실패 결과와 중간 검사 결과는 삭제하지 않았다. 비활성 신호를 다시 켜면 보존했던 1초 구간의 2페이지를 요청하는 것도 확인했다.

## 실제 검증

환경: Node.js 24.18.0, PostgreSQL 17.11, pgvector 0.8.6. 의존성은 기존 설치를 작업 전용 scratch로 복사해 사용했다. 테스트 DB는 새 전용 컨테이너 `nmv-discovery-audit-1cd4f557`의 `nomorevibe_test`이며 loopback 임의 포트를 사용했다. 기존 개발·테스트·운영 DB 및 .env.local은 변경하지 않았다.

- 관련 단위·회귀 **19개 파일 179건 통과**: 탐색·증거·최신/과거 예산·커밋 수신 상한·취소·GitHub 토큰/쿼터·공유 캐시 계약·분할·네트워크 읽기·Oracle 분리.
- 전용 DB 통합 **3개 파일 33건 통과**: crawl-seed 22건, 공유 탐색 9건, 진척 저장 2건. lease 경합·소유권 교체·최종 적재 한도·큰 응답의 요약 저장과 원문/이메일 제외·커서 직렬화 포함.
- Next route typegen 성공, 최종 전체 TypeScript 검사 및 변경된 TypeScript 3개 파일의 ESLint도 통과했다. validation.json에 결과를 기록했다.
- 기존 개선의 핵심 회귀 4개 파일 92건도 수정 전에 별도로 통과했다. 기존 검사 성공만으로 이번 보관 결함까지 검증된다고 볼 수 없었다.
- git diff --check 통과. 전체 unit/DB, 프로덕션 build, GitHub 필수 CI는 실행하지 않았다(저장소의 변경 범위 검증 정책 준수).

`comparison.json`에 비교 수치, `validation.json`에 실제 실행 결과를 보관했다. 원본 JSON·로그와 모의 입력/실행 코드는 작업 artifacts/scratch에 남겼다. 기존 테스트 DB는 건드리지 않았으며 이 작업 전용 컨테이너는 검증 후 중지했다.

## 한계와 다음 단계

push·PR·병합·외부 게시·배포·운영 커서/설정 변경은 하지 않았다. 실제 GitHub API, 유료 모델, 운영 서버에 호출하지 않았다. 그러므로 운영 신규 적재량·60분 처리량·메모리 개선과 장기 안정성은 이번 결과로 보증하지 않는다.

8MiB도 넘고 날짜를 더 나눌 수 없는 1초 구간은 기존 개선 정책대로 그대로 보존해 대기한다. disabled 상태가 양쪽 커서에 겹치거나 합친 목록이 상한을 넘으면 통합은 늦어지지만 활성 검색은 기존 예산으로 계속 실행한다. 새 DB 마이그레이션이나 커서 버전 변경은 없다. 기존 개선의 v3 커서에 대한 구버전 rollback 호환 주의는 그대로 유효하다.

다음은 이 브랜치의 코드 리뷰와 기존 개선 대비 follow-up 패치 검토다. 향후 별도 승인으로 운영 반영한다면 그때 필수 CI와 공식 절차를 수행하고, 같은 조건의 실제 60분 창에서 처리량·검색어별 완료 날짜·반복 실패·후속 적체를 비교해야 한다.
