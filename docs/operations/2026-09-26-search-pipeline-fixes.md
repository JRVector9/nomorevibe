## 재발 방지

프로필은 생성에 실제 사용한 입력의 해시와 함께 저장한다. 생성 입력이나 최신 심사 메모가 바뀌면 갱신 대상으로 표시한다. JS의 문자열 자르기·trim과 DB 변경 감지의 의미를 맞췄으며, 사용하지 않는 본문 뒷부분의 변경은 불필요한 재생성을 일으키지 않는다. 생성·검수 저장 시 현재 원본과 작업이 시작될 때의 프로필 버전을 다시 확인하므로 오래된 응답이 최신 데이터에 덮어쓰기되지 않는다.

생성 실패 시 기존 키워드와 기존 생성 해시를 함께 유지한다. 현재 해시만 덮어써 일치한 것처럼 처리하지 않는다. 검수 대상의 입력 해시가 달라졌다면 검수 대신 재생성으로 넘긴다. 갱신 대기·실패·재시도 한도와 backoff는 기존 작업 잠금 아래 처리한다.

운영에서 정상 모델 응답의 저장이 거절되던 별도 문제도 수정했다(PR194). Drizzle의 단일 테이블 조회가 외부 제품 ID를 한정되지 않은 id로 바꾸어 하위 쿼리가 감사행 ID를 비교했다. 제품과 감사행의 ID가 다른 회귀 테스트 3개로 모두 실패를 재현한 뒤 외부 products.id를 명시했다. 기존 테스트는 두 ID가 같아 이 문제를 놓쳤다.

이전 실패6건(ID1271·1829·4760·5366·5829·18759)은 실제 모델 생성·저장·검수까지 복구됐다. 복구 도중 마지막으로 남은 ID609는 JSON 구조와 판정 개수는 맞아도 모델이 키워드1개를 다른 이름으로 반환해 strict 검증에서 거부됐다. 잘못된 결과를 성공으로 저장하지 않았다. 같은 모델에15개 키워드를5개씩3묶음으로 실제 검수했고, 세 응답 모두 정확한 키워드·boolean·전체 판정 검증을 통과한 뒤 결과를 합쳐 현재 입력·프로필 버전·작업 잠금 검증 아래 정상 저장했다. 부분 성공은 저장하지 않았다. 이 건은 임시 복구 경로로 처리했으며 운영 검수 기준은 완화하지 않았다.

복구 기간에는 생성과 검수의 서로 다른 모델 호출을 병렬로 이어서 처리하도록 임시 실행기를 사용했다. 기존 job lease와 생성 동시2·검수 동시4, 호출 제한과 게이트웨이 backoff를 유지했다. 각 실행기는 최대4시간 또는 큐 소진 시 종료했고 만료 전에 소유한 실행기만 갱신했다. 07:41에 임시 실행기 프로세스가0개인 것을 확인했다. 정상 워커6개는 모두 healthy이고, 정상 생성·검수·근거 수집 작업은 최근 성공 기록과 오류0을 확인했다. 소개 검수의 사용자 중단 설정(not_before2100)은 유지했다.

병목은 생성 모델의 응답 지연이었다. 예를 들어 최근5분33건 생성·32건 검수처럼 처리량이 변동했다. 실제 호출 제한을 넘긴 시간 초과는 재시도하고, 틱의 남은 시간만 부족했던 호출은 실패 횟수를 소비하지 않고 다음 틱에 넘긴다(PR195). 처리량을 높이기 위해 검증 없이 모델 동시 호출 제한을 늘리지는 않았다.

이 수치는 최종 확인 시점의 결과다. 이후 새 수집이나 원본 변경으로 생기는 갱신 대기는 정상 워커가 자동 처리한다. 과거 복구 대상의 생성·검수는 모두 끝났으며, 남은 수동 복구 작업은 없다.
