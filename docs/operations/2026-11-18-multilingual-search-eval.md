# 2026-11-18 4개 언어 검색 평가와 중·일 검색어 번역 실험

[Draft PR #994](https://github.com/JRVector9/nomorevibe/pull/994) · 공개 제품 스냅숏 기준 커밋 `ebd63092` · 운영 변경 없음

## 무엇을 쟀나

같은 의도의 질의를 영어·한국어·중국어·일본어로 넣었을 때 검색 품질이 언어마다 얼마나 다른지 쟀다. 그리고 지금 한국어에만 하는 "검색어를 영어 낱말로 옮겨 함께 찾기"를 중국어·일본어에도 하면 어떻게 되는지 쟀다.

채택 기준(대표 지정): 어느 언어도 나빠지지 않고, 4개 언어 평균은 오를 것.

## 평가셋 — 4개 언어 240개 질의

- `scripts/experiments/multilingual-search-queries.json`
- `scripts/search-judged.ts`의 정답 질의 60개(영어 34·한국어 26)가 각각 한 묶음(key)이다. 묶음마다 나머지 세 언어판을 만들었다. 60묶음 × 4개 언어 = 240개 질의다.
- 네 언어판은 같은 의도라서 key의 채점을 그대로 쓴다(`scripts/search-judgments.json` 3,519건과 이번 추가 채점).
- 새 언어판은 Claude Opus 5.5가 직역이 아니라 그 언어 사용자가 실제로 칠 법한 검색어로 썼다. 원어민 검토는 받지 않았다. 중국어는 간체다.
- 같은 문자열이 겹친 곳이 있다. 영어 2곳(「coding agent cost tracking」, 「supply chain risk monitoring」), 한국어 1곳(「코딩 에이전트 비용 추적」)이다. 묶음마다 채점이 달라 그대로 두었다.
- 일본어판 60개 중 21개는 가나 없이 한자로만 되어 있다(예: 「薬 副作用 確認」, 「保育園 管理」).

**지금 코드의 언어 판별(`searchQuerySourceLocale`)로는 중국어판 60개와 일본어판 60개 중 번역 대상이 하나도 없다.**
- 중국어는 「软件·代码」 같은 정해진 12낱말이 있어야 번역한다. 평가셋의 자연스러운 중국어 검색어에는 그 낱말이 없다.
- 일본어는 가나가 있으면 일부러 건너뛴다. 한자로만 된 일본어는 판별하지 못한다.
- 이 제한은 10/13 i18n 작업(9e95dc37)에서 "kana·generic Han은 자동 번역하지 않는다"로 정한 것이다. 측정 근거는 남아 있지 않다.

## 실험안

모든 안이 운영 코드를 그대로 쓴다: `planSearch`(낱말 검색 계획), `listProductSlugs`·`countProducts`(낱말 검색), `nearestProductSlugs`(의미 검색, 코사인 0.5 이상 200개), RRF(k=60), 앞 30개 재정렬, `relevanceWindow`.
`current` 안은 질의마다 운영 `rankRelevance`와 순위·결과 수가 같은지 맞춰 보았다.

| 안 | 한국어 | 중·일 | 영어 |
|---|---|---|---|
| `cold` | 번역 캐시가 빈 운영. 정해 둔 확장만 쓰고, 0건이면 운영처럼 번역을 기다려 다시 찾는다 | 번역 없음 | 그대로 |
| `current` (기준) | 번역이 캐시에 있는 운영 — 번역 표현을 낱말 검색에 함께 넣는다 | 번역 없음(지금 운영) | 그대로 |
| `current-prodcache` | 번역을 운영 캐시(text_translations)에서만 읽는다 — 보정용 | 번역 없음 | 그대로 |
| `cjk` | current와 같다 | **한글 없이 한자·가나가 있으면 번역 표현을 낱말 검색에 함께 넣는다** | 그대로 |
| `cjk+vec` | 번역 표현을 임베딩한 세 번째 목록을 RRF로 섞는다 | 같음 | 그대로 |
| `cjk+rr` | 재정렬 질의를 「원문 / 번역」으로 바꾼다 | 같음 | 그대로 |
| `cjk+vec+rr` | 둘 다 | 둘 다 | 그대로 |

영어 질의는 어느 안에서도 바뀌지 않는다. 그래서 영어 점수는 모든 안에서 같다.

## 번역 — 대리 번역

- `scripts/experiments/multilingual-search-translations.json`
- 운영 검색어 번역 엔진(M3 gpt-oss-120b, 2칸)은 운영 웹 검색과 칸을 나눠 쓴다. 장부 밖 직접 호출은 운영 호출을 미확정(600초 정지)으로 만든 일이 있어(11/18 deepseek) 부르지 않았다.
- 대신 Claude Sonnet 서브에이전트 셋(한국어·중국어·일본어 따로)이 운영 지시문을 받고, 다른 언어판을 보지 않은 채 질의마다 한 줄로 답했다. 답은 운영 파서(`parseQueryTranslation`)를 거쳐 쓴다.
  - 한국어: 운영 지시문(QUERY_SYSTEM v2 + 용어표 힌트).
  - 중·일: 운영 중국어 지시문(v1)을 "Chinese or Japanese"로 넓힌 제안 지시문.
- `current-prodcache`가 대리 번역과 운영 캐시 번역의 차이를 잰다(원래 한국어 정답 질의 26개).

## 채점과 통계

- 모든 안·언어의 상위 10개 중 채점이 없는 질의·제품 쌍을 모아 불투명 ID로 섞고, Claude Sonnet 서브에이전트들이 어느 안·언어판에서 나왔는지 모르는 채로 0·1·2를 매겼다([채점 기준](../../scripts/experiments/multilingual-search-grading.md), README 실험과 같은 기준).
- 추가 채점은 `scripts/experiments/multilingual-search-judgments-extra.json`에 두고, 기존 `search-judgments.json`과 겹치지 않게 합친다(겹치면 실패).
- 주 지표는 nDCG@10이다(이득 2^g−1, 이상 순위는 key의 모든 채점). 대표 정답의 MRR·1위·10위 안, 영어판 상위 10과 겹치는 비율도 낸다.
- 구간은 질의 묶음을 단위로 10,000번 다시 뽑은 bootstrap 95% 백분위 구간이다(시드 고정). 기준(current)과의 차이는 같은 묶음끼리 짝을 지어 낸다. 「4개 언어 평균」은 묶음마다 네 언어 차이의 평균을 다시 뽑는다. 여러 안을 견준 다중 비교 보정은 하지 않았다.

## M3 부담

- M3 임베딩·재정렬은 한 번에 하나씩, 300ms 간격으로 불렀고, 응답은 파일에 캐시했다(다시 돌려도 M3를 부르지 않는다).
- 50번마다 검색어 하나를 재서 300ms를 넘으면 60초 쉬었다.
- 같은 시간에 README 실험이 v1·v1raw(README를 붙인 긴 문서)를 임베딩하면서 묶음 하나가 1.2~2.3초 걸렸다. 그동안 이 실험의 검색어 임베딩은 0.4~3초였고, 실행이 오래 쉬었다. 운영 웹 검색의 검색어 임베딩 제한은 500ms라서 그 시간 운영 검색이 의미 검색 없이 나갔을 수 있다. 진행 중에 보고함(문제)으로 알렸다.

### 요약

- **지금 중·일 검색은 영어보다 nDCG@10이 0.08~0.13 낮다.** 영어 0.763, 한국어 0.752, 중국어 0.680, 일본어 0.634.
- 결과가 10건 미만인 질의는 중국어 4개, 일본어 8개다. 일본어 「砥石 互換性 確認」는 0건이었다.
- **중·일 번역 추가(`cjk`)는 채택 기준을 만족한다.**
  - 영어·한국어는 순위가 하나도 바뀌지 않는다(같은 계획).
  - 중국어 +0.047 [0.020, 0.078], 좋아짐 31·나빠짐 17.
  - 일본어 +0.088 [0.046, 0.135], 좋아짐 37·나빠짐 14.
  - 4개 언어 평균 +0.034 [0.019, 0.050]. 대표 정답 MRR도 올랐다(중 0.365→0.370, 일 0.401→0.415).
  - 영어판 상위 10과 겹치는 비율이 중 0.50→0.60, 일 0.43→0.56으로 늘었다. 결과가 10건 미만인 질의는 0개가 됐다.
- 번역 벡터를 더하면(`cjk+vec`) 중 +0.010, 일 +0.008을 더 얻는다. 구간이 겹쳐 차이가 있다고 하기 어렵고, 한국어 순위가 조금 흔들린다(좋아짐 13·나빠짐 16).
- **재정렬 질의에 번역을 붙이면(`rr`) nDCG는 더 오른다.** `cjk+vec+rr`은 중 +0.075, 일 +0.120, 평균 +0.053이다.
  - 그러나 한국어 순위가 크게 흔들린다(좋아짐 31·나빠짐 22, +0.018 [−0.001, 0.038]).
  - 대표 정답 MRR은 내려간다(한 0.448→0.407, 일 0.415→0.393).
  - 바로 채택하지 않고 따로 더 잴 거리다.
- **보정:** 원래 한국어 정답 질의 26개 모두 운영 캐시 번역이 있었다. 대리 번역과 운영 캐시 번역의 nDCG 차이는 +0.003 [−0.013, 0.018]이다. 대리 번역이 운영 번역과 품질이 비슷하다는 근거다. 다만 중·일은 운영 모델로 재 보지 않았다.
- **곁가지 — 한국어 첫 검색:** 번역이 캐시에 없을 때(`cold`) 한국어 nDCG는 0.711로, 캐시가 있을 때(0.752)보다 0.041 [0.017, 0.069] 낮다. 10/07 측정(0.824 vs 0.832)보다 차이가 크다.

## 판단과 다음 단계

1. **`cjk`(중·일 검색어를 영어 낱말로 옮겨 낱말 검색에 함께 넣기)를 운영 반영 후보로 올린다.**
   - 한국어 경로와 같은 방식이고, 영어·한국어는 바뀌지 않는다.
   - 별도 PR이 필요하다.
     - `searchQuerySourceLocale`이 한글 없는 한자·가나 질의를 받게 한다.
     - 중·일 공용 지시문 판을 둔다(캐시 열쇠가 바뀐다).
     - 장부 wire의 `sourceLocale` 종류(`WebsearchQueryGatewayInput`)와 관련 시험을 넓힌다.
   - 비용: 처음 보는 중·일 검색어마다 번역 호출 1번(응답 뒤, 캐시 저장). M3 gpt-oss 2칸을 웹 검색과 나눠 쓴다.
2. **반영 전에 운영 번역 모델로 다시 잰다.** 이번 번역은 대리 번역이다. 장부를 거쳐 gpt-oss로 중·일 120개를 옮긴 뒤 이 하네스의 `cjk` 안을 다시 돌리면 된다(사람 허락 필요).
3. **첫 검색 문제:** 운영은 번역을 기다리지 않고 캐시에 있을 때만 쓴다(결과 0건일 때만 기다림). 그래서 처음 들어온 중·일 검색어는 지금과 같다. 결과가 적을 때(예: 10건 미만)도 기다릴지는 검색 기록에서 중·일 검색어가 얼마나 되풀이되는지 본 뒤 정한다(이번에는 기록을 보지 않았다).
4. **`rr`은 다음 실험으로 미룬다.** 재정렬에서 원문 점수와 번역 점수 중 큰 값을 쓰는 안, 중·일에만 적용하는 안을 같은 하네스로 잰다.
5. README 실험과 함께 켰을 때의 효과는 재지 않았다. 이번 추가 채점 1,308쌍은 같은 코퍼스라 README 실험도 쓸 수 있다.

## 한계

- 새 언어판(180개)은 Claude가 썼고 원어민 검토가 없다. 중국어는 간체만 있다.
- 번역은 대리 번역이다(한국어 보정에서는 운영 번역과 같은 수준). 중·일 운영 번역 품질은 재지 않았다.
- 추가 채점은 Claude Sonnet 서브에이전트가 블라인드로 했다. 사람 검수는 없다. 두 번째 차례의 두 채점자는 이유 칸을 일반 문구로 채웠다(ID별 등급은 직접 적음, 표본 확인 통과). 그 뒤 지시를 고쳐 항목마다 이유를 쓰게 했다.
- 질의 60묶음으로 여러 안을 견줬고 다중 비교 보정은 하지 않았다.
- 응답 없는 제품 빼기(product_health)가 빠진 코퍼스다. 검색 시간은 재지 않았다(M3가 README 실험으로 붐벼 의미가 없었다).
