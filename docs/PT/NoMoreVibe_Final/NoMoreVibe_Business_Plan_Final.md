## 1. 사업 요약과 최종 결정

### 1.1 한 문장으로 설명하는 서비스

**NoMoreVibe는 AI로 만든 제품을 소개하는 곳을 넘어, 적합한 사람이 제품을 써보고 개선에 필요한 피드백을 남기며, 그 피드백이 실제 업데이트로 연결되는 플랫폼이다.**

GitHub의 프로젝트 발견 기능은 유지하되, 핵심 가치는 “등록한 제품 수”가 아니라 “실제 사용자 반응을 받아 다음 버전을 만든 제품 수”에 둔다.

메이커에게는 **첫 사용자와 개선 방향**, 사용자에게는 **내 문제에 맞는 제품과 의견 반영 경험**, 에이전트 운영자에게는 **권한이 명확한 테스트 작업과 결과 제출 경로**를 제공한다.

### 1.2 핵심 순환 구조

```text
Radar에서 발견 / 메이커가 직접 등록
                  ↓
       관리 권한 확인 및 Launch
                  ↓
      적합한 사용자에게 테스트 제안
                  ↓
       사용 경험 / 에이전트 테스트
                  ↓
    출처·증거·품질이 구분된 Feedback
                  ↓
       메이커 검토 → 이슈 → 수정
                  ↓
         업데이트 공개 및 재테스트
                  ↓
     기여자에게 결과 알림과 참여 보상
```

### 1.3 최종 통합 방향

| 항목 | 권고안 | 이유 |
| --- | --- | --- |
| 서비스 정체성 | 제품 발견 + 첫 사용자 확보 + 피드백 기반 개선 | 단발성 홍보보다 반복 사용 이유를 만든다 |
| 홈 구조 | Launches와 Radar를 두 개의 주 영역으로 제공 | 현재 사용 가능한 제품과 자동 발견 자료를 혼동하지 않게 한다 |
| 제품 등록 | 기본 등록·관리 권한 인증·공개는 무료 | 남의 제품을 먼저 평가해야만 입장할 수 있는 장벽을 피한다 |
| 크레딧 | 적격 피드백 참여로 획득, 내 제품의 커뮤니티 피드백 요청에 사용 | 기여와 혜택을 연결하되 등록 자체를 인질로 삼지 않는다 |
| 피드백 출처 | User와 Agent를 서버 측 작성 주체 기준으로 분리 | 에이전트 결과를 사람의 사용 경험처럼 보이게 하지 않는다 |
| 실사용 확인 | 확인 수준과 근거를 표시 | 클릭·체류 시간만으로 “실제 사용”을 단정하지 않는다 |
| 보상 기준 | 사용 증거와 구체성, 관련성 | 호평 여부나 메이커의 선호에 따라 보상하지 않는다 |
| 수익화 | 유료 테스트 모집·관리, 반복 운영 도구, 별도 에이전트 실행 | 별점·추천·자연 노출 순위를 판매하지 않는다 |
| 핵심 지표 | 주간 적격 User Feedback을 받은 활성 제품 수 | 에이전트 물량으로 사업 성과가 부풀려지는 것을 막는다 |
| 화면 시안 | 미니멀 버전을 유지하고 상세 정보는 하위 화면으로 이동 | 기능이 늘어도 메인은 복잡해지지 않게 한다 |

### 1.4 이번 기획에서 하지 않는 것

모든 GitHub 저장소를 즉시 테스트 가능한 제품으로 간주하지 않는다. 공개 저장소라는 이유만으로 오픈소스 라이선스나 AI 제작 여부를 확정하지 않는다. 관리 권한 인증을 법적 소유권·저작권 보증으로 표현하지 않는다. Agent Feedback을 수요 검증, 결제 의사, 실제 고객 수의 대체 지표로 사용하지 않는다.

또한 화면 설계와 정책 문서가 완성되었다고 해서 서버, 결제, 인증, 테스트 에이전트까지 구현된 것으로 표현하지 않는다. 본 문서는 개발 기준이며 동작하는 서비스 코드 납품물은 아니다.

## 2. 해결하려는 문제와 핵심 고객

### 2.1 출발점

사용자의 사업 의도는 명확하다. **바이브 코딩으로 제품을 만든 사람이 쉽게 홍보하고, 사람들이 실제로 사용하면서 피드백하는 공간**을 만드는 것이다.

이 의도를 “프로젝트 링크 모음”이나 “인기투표 서비스”로 축소하지 않는 것이 중요하다. 링크를 등록하는 행위 이후에 사용자가 제품을 발견하고, 시도하고, 막힌 점을 공유하고, 개선 결과를 확인하는 과정까지 설계한다.

### 2.2 검증할 문제 가설

아래 항목은 인터뷰와 서비스 실험으로 확인해야 할 가설이다. 특정 경쟁사의 전체 사용자가 동일한 불만을 가진다는 의미는 아니다.

| 고객 | 문제 가설 | NoMoreVibe의 해결 방식 | 검증할 결과 |
| --- | --- | --- | --- |
| 개인 메이커 | 제품은 만들었지만 홍보할 곳과 첫 사용자가 없다 | 쉬운 등록, 관심사 기반 발견, 테스트 모집 | 등록 후 첫 적격 피드백까지 걸리는 시간 |
| 초기 창업자 | 조회·좋아요는 있지만 무엇을 고칠지 알기 어렵다 | 과제 중심 피드백, 불편·막힘·개선 요청 분리 | 피드백 기반 의사결정 및 수정 비율 |
| 작은 팔로어 기반의 메이커 | 기존 인맥과 초기 반응이 노출을 좌우한다고 느낀다 | 탐색용 노출 예산, 신규·저노출 제품 발견 슬롯 | 신규 제품에 배분되는 유효 노출과 피드백 |
| 일반 사용자 | 제품 소개만 보고는 내 문제에 맞는지 판단하기 어렵다 | 대상 사용자, 사용 준비물, 가격·가입 조건, 실제 사용 경험 표시 | 상세 → 테스트 시작 전환 |
| 테스터 | 긴 가입·설정 후에야 제품이 자신에게 안 맞는 걸 알게 된다 | 시작 전 과제·예상 부담·필수 조건 안내 | 테스트 중단 사유 및 낭비 시간 감소 |
| 피드백 작성자 | 의견을 남겨도 답변이나 개선 여부를 알 수 없다 | 답변·수정·배포·재테스트 알림 | 재참여율과 업데이트 확인율 |
| 에이전트 운영자 | 어디까지 테스트해도 되는지, 결과를 어떻게 제출할지 불명확하다 | 제품별 허용 범위, 표준 결과 형식, 실행 이력 | 유효한 자동 테스트 결과 비율 |

### 2.3 고객 우선순위

**1차 고객은 이미 배포 가능한 웹 제품을 가진 개인 메이커와 소규모 팀**이다. 시작부터 모든 앱·라이브러리·하드웨어·기업 제품을 동일한 테스트 흐름으로 수용하지 않는다.

초기 범위는 웹 브라우저에서 사용 가능한 생산성 도구, 디자인 도구, 콘텐츠 도구 등으로 좁히는 것이 좋다. 이는 추천 범위이며, 실제 제품 공급과 테스터 관심사에 따라 조정한다.

**2차 고객은 특정 분야에 관심 있는 초기 사용자와 테스터**다. 메이커끼리만 상호 평가하는 구조로는 실제 고객 수요를 충분히 확인할 수 없으므로, 제품의 목표 고객과 일치하는 비메이커 사용자 비중을 별도로 관리한다.

**3차 고객은 반복적인 제품 검증이 필요한 팀과 에이전트 운영자**다. 이 고객군의 유료 기능은 초기 커뮤니티 운영이 안정된 후 확대한다.

### 2.4 사용자에게 주는 약속

메이커에게는 “홍보를 위해 무조건 많은 팔로어가 필요하지 않다. 제품을 소개하고, 적합한 사람의 구체적인 의견을 받을 수 있다.”고 말한다.

테스터에게는 “어떤 제품을 왜 사용해볼지 먼저 알 수 있고, 막혔다는 피드백도 정당한 기여로 인정되며, 이후 무엇이 바뀌었는지 확인할 수 있다.”고 말한다.

이때 **사용자 수·매출·긍정적 평가를 보장하지 않는다.** 보장 가능한 것은 명시된 운영 범위와 검토 기준, 미충족 시 처리 방식이다.

## 3. 서비스 목표와 성과 지표

### 3.1 서비스 목표

NoMoreVibe의 목표는 제품 수집량 확대 자체가 아니다. 좋은 제품이 묻히지 않고, 처음 만난 사용자의 경험을 통해 실제로 개선될 수 있게 하는 것이다.

이를 위해 제품 발견, 적합한 테스트 매칭, 신뢰 가능한 피드백, 수정 추적, 재방문이라는 다섯 기능을 연결한다.

### 3.2 핵심 성과 지표

**North Star Metric: 주간 적격 User Feedback을 1건 이상 받은 활성 제품 수**

```text
주간 핵심 지표 =
해당 주에 적격으로 판정된 비소유자 User Feedback이 1건 이상 발생한
서로 다른 활성 Launch 제품의 수
```

동일인이 반복 제출한 내용, 자기 제품 평가, 에이전트 결과, 취소·부정 판정된 피드백은 제외한다. “활성”은 공개 상태이며 이용 경로가 유효하고, 해당 기간 테스트를 수용하는 제품으로 정의한다.

단일 지표의 한계를 보완하기 위해 **28일 내 서로 다른 적합 사용자 3명 이상의 적격 피드백을 받은 제품 비율**을 함께 본다. 3명은 초기 운영 가정이며 제품 유형에 따라 조정한다.

### 3.3 보조 지표와 해석

| 지표 | 정의 | 주의점 |
| --- | --- | --- |
| 첫 피드백 도달 시간 | Launch 활성화부터 첫 적격 User Feedback까지 | 전체 평균보다 중앙값·상위 지연 구간을 함께 본다 |
| 테스트 시작률 | 테스트 시작 세션 / 제품 상세 방문 세션 | 외부 링크 클릭을 사용 완료로 집계하지 않는다 |
| 사용 확인 수준 분포 | 자기진술·증거 검토·제품 이벤트 확인의 비율 | 강한 증거가 많아도 완전한 진실 보장은 아니다 |
| 적격 피드백 비율 | 품질 심사 통과 건 / 최종 심사 완료 건 | 긍정적 리뷰 비율과 다르다 |
| 목표 고객 일치율 | 명시한 대상 조건에 맞는 테스터의 비율 | 메이커끼리의 평가와 실제 타깃 고객 평가를 구분한다 |
| 메이커 응답률 | 정해진 기간 내 실질적 답변이 있는 피드백 비율 | 형식적 “감사합니다” 자동 응답은 별도 표시한다 |
| 개선 연결률 | 이슈·수정·출시 중 하나와 연결된 적격 피드백 비율 | 의견을 모두 채택할 필요는 없다 |
| 수정 재확인율 | 수정 주장 후 테스터가 재확인한 항목 비율 | 메이커의 완료 표시와 구분한다 |
| 테스터 재참여율 | 첫 적격 피드백 후 다시 참여한 사용자 비율 | 보상만 노린 반복과 자연 재참여를 분석한다 |
| 유료 캠페인 공헌이익 | 매출에서 해당 캠페인의 변동비를 차감한 금액 | 매출 증가를 곧 수익성으로 보지 않는다 |

**Agent 지표는 별도 영역**으로 관리한다. 실행 수, 재현 가능한 발견 수, 중복 제거 후 유효 이슈 수, 재테스트 통과율, 유효 발견 1건당 비용이 핵심이다.

### 3.4 파일럿 운영 목표 예시

파일럿은 활성 제품 20~30개와 초대형 테스터 풀을 대상으로 시작하는 방안을 제안한다. “7일 이내 첫 적격 User Feedback”, “미응답 제품 감소”, “실제 수정 사례 확보”를 검증한다. 이 숫자는 실적이나 성장 예측이 아니라 운영 범위를 정하기 위한 가정이다.

<a id="sec-04"></a>
## 4. 서비스 구조: Radar와 Launches

### 4.1 두 영역의 역할

| 구분 | Radar | Launches |
| --- | --- | --- |
| 핵심 목적 | 아직 등록하지 않은 프로젝트를 발견한다 | 메이커가 운영하며 피드백을 받는 제품을 만난다 |
| 등록 방식 | 수집 파이프라인·운영자 큐레이션·제보 | 메이커 직접 등록 또는 인증된 Claim |
| 관리 주체 | 미확인 또는 확인 중일 수 있다 | 관리 권한이 확인된 메이커·팀 |
| 사용자 행동 | 상세 보기, 저장, 소스 열기, 관리 권한 인증 신청 | 제품 사용, 테스트 참여, 피드백, 업데이트 구독 |
| 주요 메타데이터 | 발견 출처, 최근 확인 시각, 저장소 정보, 이용 경로 | 대상 사용자, 제품 설명, 피드백 요청, 최근 개선 |
| 기본 지표 | 출처가 있는 GitHub 데이터 등 | 사람 피드백, 에이전트 결과, 개선 연결 |
| 주의점 | 자동 발견은 추천·안전·품질 보증이 아니다 | 인증은 사업 성과·법적 소유권 보증이 아니다 |

### 4.2 Radar는 “주인 없는 제품”이 아니다

표현은 **“아직 메이커가 연결되지 않은 제품”** 또는 **“자동 발견된 프로젝트”**로 통일한다. 기존 제품의 저작권이나 운영권이 비어 있다는 의미를 주면 안 된다.

누구나 타인의 제품을 Claim할 수 있는 구조가 아니라, **해당 제품의 관리 권한을 입증한 주체만 Claim**할 수 있다. 일반 사용자는 제품을 저장하거나 제작자에게 NoMoreVibe 참여 링크를 공유할 수 있다.

### 4.3 발견 출처와 현재 운영 상태를 분리한다

Radar에서 찾은 제품이 Claim되었다고 해서 출처를 지우거나 새로운 제품 ID를 만들지 않는다.

```text
product_id: 유지
origin: github_discovery | web_discovery | maker_submission
claim_status: unclaimed | pending | verified | disputed | revoked
publication_status: draft | listed | launched | paused | archived
```

이 값들은 구현용 예시다. **발견 경로**, **관리 권한 상태**, **공개 상태**는 서로 다른 필드로 다룬다는 원칙이 핵심이다. Claim된 제품은 Launches에 노출하되, 원래 Radar 링크는 동일 제품으로 연결한다.

### 4.4 제품 유형을 구분한다

웹 앱, 모바일 앱, 개발 도구, 설치형 오픈소스, 라이브러리는 이용 방법이 다르다. 상세에서 “브라우저 바로 사용”, “회원가입 필요”, “설치 필요”, “API 키 필요”, “유료 사용 필요”를 구분한다.

GitHub 별이 없는 웹 제품에는 `0 stars`를 만들어 넣지 않는다. 데이터가 없으면 해당 지표를 숨기거나 “해당 없음”으로 표시한다. AI 제작 여부도 메이커 자기신고, 저장소 설명 기반 추정, 미확인을 구분한다.

### 4.5 공개 데이터 운영

프로젝트 설명의 출처와 마지막 확인 시각을 유지한다. 소스 코드 공개 여부와 라이선스를 구분하고, 발견한 코드·이미지를 무조건 재배포하지 않는다. 삭제·수정 요청 경로, 중복 병합 절차, 위험 링크 신고를 제공한다.

## 5. 차별화 전략과 사용자 가치

### 5.1 경쟁보다 해결할 일을 선명하게 정의한다

Product Hunt·Uneed와의 차이를 “상대 서비스에는 피드백이 없다”로 설명하지 않는다. 비교의 핵심은 **NoMoreVibe가 무엇을 중심 행동과 성과로 설계하는가**다.

| 비교 관점 | 제품 소개·런칭 중심 경험을 바라보는 관점 | NoMoreVibe의 설계 선택 |
| --- | --- | --- |
| 성공의 단위 | 등록, 노출, 반응, 런칭 이벤트 | 적합한 사용자의 경험과 후속 개선 |
| 참여 행동 | 살펴보기, 반응하기, 댓글 쓰기 | 명확한 과제를 시도하고 구체적인 결과 남기기 |
| 제품의 생애 | 출시 시점의 관심 | 첫 공개부터 수정·재테스트까지 |
| 피드백 출처 | 다양한 댓글·평가 | User / Agent 및 관련 주체 표시 |
| 신뢰 표현 | 인기도와 소개 정보 | 증거 수준·확인 방법·후속 상태 |
| 과금 대상 | 다양한 홍보·운영 상품 가능 | 테스트 모집·관리와 반복 운영 도구를 우선 |

위 표는 경쟁사의 최신 기능을 배타적으로 판정한 기능표가 아니라, NoMoreVibe의 제품 설계 기준이다.

### 5.2 사용자 불만을 실제 기능으로 바꾸기

**“좋아요는 많은데 사용자는 없다.”**<br>
좋아요와 외부 클릭을 핵심 지표에서 제외한다. 테스트 시작, 확인 수준, 피드백 완료를 단계별로 보여준다.

**“좋다는 말만 있고 고칠 것을 모르겠다.”**<br>
무엇을 하려고 했는지, 어디에서 막혔는지, 어떤 결과가 나왔는지를 묻는다. 막힘 보고도 정상적인 완료 유형으로 인정한다.

**“내 의견을 아무도 읽지 않는다.”**<br>
접수·검토·보류·수정·배포·재확인 상태를 보여준다. 메이커는 채택하지 않은 이유도 남길 수 있다.

**“제품을 소개하려면 남의 제품부터 억지로 평가해야 한다.”**<br>
등록과 기본 공개는 무료로 두고, 피드백 교환 프로그램을 선택적으로 참여하게 한다.

**“무료 테스트라더니 결제·API 키·긴 설정을 요구한다.”**<br>
테스트 전에 준비물과 비용을 안내한다. 유료 미션은 메이커가 테스트 계정이나 필요한 사용량을 제공하는 구조를 우선한다.

**“에이전트가 사람인 척 리뷰를 쓴다.”**<br>
작성 인증 경로와 실행 출처를 데이터 모델에서 분리한다. AI가 실제 테스트를 수행했다면 사람이 제출 버튼을 눌러도 Agent Feedback이다.

### 5.3 장기적으로 축적할 자산

차별화 자산은 단순한 프로젝트 목록이나 피드백 양이 아니다. **어떤 사용자 조건에서, 어떤 버전과 과제를 시도했고, 무엇이 막혔으며, 무엇을 수정했을 때 문제가 줄었는지**를 연결한 기록이다.

이 기록은 제품 추천, 테스트 매칭, 재현 가능한 에이전트 평가, 개선 우선순위 정리에 활용할 수 있다. 다만 개인의 민감한 사용 행동을 과도하게 수집하는 방향으로 확장하지 않는다.

## 6. 제품 관리 권한 인증 및 Claim 정책

### 6.1 인증이 증명하는 범위

서비스에서 사용할 배지는 **“관리 권한 확인”**을 기본으로 한다. “법적 소유자 인증”이라는 표현은 사용하지 않는다.

GitHub 저장소나 도메인을 관리할 수 있다는 사실은 해당 자원에 대한 현재 통제의 증거다. 법적 소유권, 상표권, 원저작자 지위, 팀 내부의 게시 권한까지 자동으로 보증하지 않는다. 사용자는 게시·관리 권한이 있다는 확인에 동의하고, 분쟁 시 별도 절차를 따른다.

### 6.2 권고 인증 수단

| 수단 | 확인 대상 | 사용 방식 | 단독으로 보증하지 않는 것 |
| --- | --- | --- | --- |
| GitHub 기반 권한 확인 | 연결된 특정 저장소에 대한 적정 관리 권한 | 로그인 후 서버에서 저장소 권한을 확인하고 제품과 연결 | 로그인 성공만으로 제품 소유자가 되지는 않음 |
| 도메인 DNS Challenge | 특정 도메인의 DNS 제어 | 제품·계정에 귀속된 일회성 TXT Challenge | 법적 소유권·저작권 |
| 고정 경로 파일 Challenge | 특정 서비스 경로에 파일을 게시할 수 있는 권한 | 지정된 검증 파일을 안전하게 조회 | 같은 공유 도메인 아래 다른 사용자의 서비스 권한 |
| 업무 이메일 확인 | 해당 이메일의 수신 가능 여부 | 보조 신호 또는 수동 심사 자료 | 메일 수신만으로 저장소·제품 관리 권한 |
| 수동 심사 | 자동 수단으로 증명하기 어려운 관계 | 운영 자료와 기존 검증 주체의 확인 | 무제한·영구적인 소유권 보증 |

구체적인 GitHub 앱 권한과 API 선택은 구현 시 공식 문서에 맞춰 검증한다. 불필요한 코드 쓰기 권한이나 모든 저장소 접근을 요구하지 않는 최소 권한 원칙을 적용한다.

### 6.3 인증 흐름

```text
제품 URL 또는 저장소 URL 입력
    → 기존 제품 중복 확인
    → 로그인
    → 적절한 검증 수단 선택
    → 제품·계정에 귀속된 Challenge 발급
    → 서버에서 검증
    → 권한 충돌 확인
    → 관리 멤버십 생성
    → 등록 초안 검토
    → Launch 공개
```

검증 토큰은 예측 불가능하고 짧은 유효기간을 가지며 재사용되지 않도록 설계한다. 정확한 도메인·제품·계정에 묶고, 단순 URL 입력이나 외부 링크 첨부만으로 통과시키지 않는다.

### 6.4 예외와 공격 시나리오

| 상황 | 처리 원칙 |
| --- | --- |
| 다른 프로젝트를 Fork한 저장소 | Fork의 관리 권한만 확인한다. 원본 제품의 관리자로 승격하지 않는다 |
| 팀원이 제품을 등록 | 제품별 역할을 부여하고 팀 내부 권한을 확인할 수 있게 한다 |
| 공유 호스팅 도메인 | 상위 도메인 전체가 아니라 해당 배포 경로·프로젝트와 연결된 권한을 검토한다 |
| 동일 제품에 두 번째 Claim | 기존 관리자 알림과 검토 절차를 거치고 자동 탈취·이전을 차단한다 |
| 저장소와 서비스 도메인이 불일치 | 연결 관계를 추가 확인하거나 수동 심사한다 |
| 도메인 만료·저장소 이전 | 변경 이벤트와 민감 작업 시 재검증한다 |
| 계정 탈취 의심 | 편집·결제·관리자 변경 권한을 일시 제한하고 복구 절차를 진행한다 |
| 저작권·상표권 분쟁 | 서비스 내 관리 권한과 법적 권리 판단을 분리하고 신고·조정 절차로 처리한다 |

제품 권한은 `Owner / Admin / Editor / Viewer` 등으로 분리한다. 여기서 Owner는 서비스 내부 최고 관리자 역할 명칭이며 법적 소유권 확인을 뜻하지 않는다는 점을 문서와 UI에 명확히 한다.

### 6.5 사용자에게 보여줄 문구

> 이 인증은 연결된 저장소 또는 도메인에 대한 관리 권한을 확인합니다. 제품의 법적 소유권이나 저작권을 보증하지 않습니다.

인증이 거절되면 이유와 다음 행동을 안내한다. “실패했습니다”만 표시하지 말고 `권한 부족`, `Challenge 미발견`, `토큰 만료`, `기존 관리자 확인 필요`, `수동 심사 중`을 구분한다.

## 7. User Feedback과 Agent Feedback

### 7.1 두 종류를 구분하는 기준

| 구분 | User Feedback | Agent Feedback |
| --- | --- | --- |
| 실제 경험 주체 | 사람이 직접 제품을 사용·시도함 | AI 에이전트가 제품을 탐색·실행·분석함 |
| 강점 | 이해도, 사용 맥락, 불편, 선호, 재사용 의향 | 반복 점검, 재현 단계, 오류 증거, 동일 과제 재실행 |
| 한계 | 표본 편향·주관성·불완전한 기억 | 도구·모델·환경에 따른 편향, 실제 수요를 대변하지 못함 |
| 기본 필드 | 시도한 과제, 실제 결과, 막힘, 개선 의견 | 실행 주체, 실행 환경, 과제, 단계, 결과, 증거 |
| 보상 | 적격 커뮤니티 미션에 참여한 경우 보상 가능 | 사람용 기여 크레딧 자동 발급 없음 |
| 공개 지표 | 적격 사용자 수·사람 피드백 수 | 실행 수·발견 수·재현 결과 |

### 7.2 작성자 선택 버튼만으로 구분하면 안 된다

로그인 사용자가 UI에서 `User`를 선택했다는 이유만으로 사람이 직접 사용했다고 확정하지 않는다. 반대로 모든 AI 보조 문장을 자동으로 Agent로 분류해서도 안 된다.

판정 기준은 **누가 경험을 수행했는가**다.

| 사례 | 분류 |
| --- | --- |
| 사람이 사용한 뒤 맞춤법·문장 정리를 AI에 맡김 | User Feedback + 선택적 AI 작성 보조 표시 |
| 에이전트가 사용하고 사람이 결과를 복사해 제출 | Agent Feedback |
| 사람이 사용하지 않고 소개문만 보고 AI로 리뷰 생성 | 사용 경험 리뷰로 인정하지 않음 |
| 메이커 본인의 에이전트가 자기 제품 테스트 | Agent Feedback + Maker-run 표시 |
| 사람이 남긴 피드백을 AI가 요약 | AI Summary. 새로운 피드백 건수로 집계하지 않음 |

자동 API 경로는 작성 주체를 서버에서 Agent로 고정하고, 임의로 `source_type=user`를 선언할 수 없게 한다. 브라우저 폼을 통한 허위 자기신고를 완전히 막을 수는 없으므로 사용 증거·심사·이의제기를 결합한다. **AI 문장 탐지기만으로 사람 여부를 판정하지 않는다.**

### 7.3 추가 출처 라벨

피드백 출처 외에 독립된 라벨을 지원한다.

- 관계: `독립 참여 / 메이커 본인 / 팀원 / 이해관계 신고`
- 보상: `자발적 참여 / 크레딧 보상 / 유료 테스트`
- 확인 수준: `자기진술 / 증거 검토 / 제품 이벤트 확인`
- 에이전트 실행 주체: `Maker-run / Platform-run / Third-party-run`

`Third-party-run`은 외부 운영자가 실행했다는 뜻일 뿐 완전한 독립성 보증은 아니다. 일반 목록에는 핵심 라벨만 보여주고 상세에서 나머지를 펼친다.

### 7.4 사람 피드백 기본 질문

처음에는 질문 세 개로 시작한다.

1. **무엇을 하려고 했나요?**
2. **실제로 어떤 결과가 나왔고, 어디에서 막혔나요?**
3. **한 가지만 바꾼다면 무엇을 바꾸겠나요?**

좋았던 점, 사용 환경, 스크린샷, 재사용 의향은 선택 또는 미션별 질문으로 둔다. 별점은 필수가 아니다. 결제 의향도 “있음 / 없음 / 아직 판단 어려움”을 제공하고, 실제 구매와 구분한다.

### 7.5 에이전트 결과 기본 구조

```text
제품 / 버전 / 대상 URL
실행 주체와 에이전트 식별자
실행 시각과 환경
권한이 부여된 과제와 범위
시도한 단계
관찰 결과
성공 / 실패 / 차단 / 판단 불가
증거 링크 및 민감정보 처리 상태
재현 단계와 재실행 결과
관련 피드백·이슈 식별자
```

증거가 없는 README 요약이나 소개문 분석은 `Overview analysis` 등으로 별도 표시한다. 브라우저 실행 로그가 없는데 “직접 테스트 완료”로 보여주지 않는다.

### 7.6 제품 개선 상태

```text
접수 → 검토 중 → 계획됨 → 작업 중 → 수정 배포 → 재확인 완료
                ↘ 보류 / 채택하지 않음 / 중복 연결
```

메이커가 “수정 배포”를 표시해도 자동으로 “문제 해결 확인”이 되지 않는다. 사용자 재확인 또는 에이전트 재실행 결과가 연결되면 후속 확인 상태를 추가한다.

## 8. 실사용 확인과 피드백 품질 검토

### 8.1 무엇을 알 수 있고 무엇을 알 수 없는가

**NoMoreVibe에서 외부 제품 링크를 눌렀다는 사실만으로, 외부 서비스에서 회원가입하거나 핵심 기능을 사용했다고 알 수는 없다.**

돌아오기까지의 시간 역시 실제 사용 시간과 동일하지 않다. 클릭, 대기 시간, 체크박스, 스크린샷 하나를 묶었다고 100% 사용을 입증하는 것도 아니다. 이를 과장하지 않는 것이 신뢰 정책의 출발점이다.

### 8.2 확인 수준을 단계적으로 표시

| 수준 | 확보하는 신호 | UI 표현 | 보상 판정에서의 활용 |
| --- | --- | --- | --- |
| L0 | 상세 열람·외부 링크 클릭 | 방문 또는 테스트 시작 | 이것만으로 보상하지 않음 |
| L1 | 사용자의 과제 결과 자기진술 | 사용 경험 자기진술 | 공개 가능. 추가 검토 전 보상 확정 안 함 |
| L2 | 관련 증거와 구체적인 경험을 플랫폼이 검토 | 증거 검토됨 | 표준 미션의 적격 판정 후보 |
| L3 | 연동된 제품의 핵심 이벤트가 해당 테스트와 연결 | 제품 이벤트 확인됨 | 품질·이해관계·이상 패턴 검토와 결합 |
| 추가 확인 | 재현 또는 독립 재테스트 | 재현 확인 / 수정 재확인 | 이슈 신뢰와 개선 결과에 활용 |

증거의 강도와 피드백의 유용성은 별도 축이다. 이벤트가 확인된 “좋아요” 한 줄은 보상 기준을 충족하지 않을 수 있고, 실패 과정이 명확한 상세 피드백은 핵심 기능을 완료하지 못했어도 적격일 수 있다.

### 8.3 제품 연동이 없는 MVP

테스트를 시작할 때 미션 ID와 세션 ID를 생성한다. 사용자는 과제와 필요한 준비물을 확인하고 외부 제품을 연다. 돌아온 뒤 시도한 과정과 결과, 필요한 증거를 제출한다.

운영자는 과제 관련성, 구체성, 증거 일치 여부를 검토한다. 애매한 내용은 보완 요청하고, 이를 “완전한 실사용 증명”이 아니라 **“제출 증거를 검토한 피드백”**이라고 표현한다.

MVP에서는 정교한 0~100점 신뢰 점수를 공개하기보다 확인 상태와 근거를 표시한다. 캘리브레이션되지 않은 점수는 객관적인 확률처럼 오해될 수 있다.

### 8.4 제품 연동이 있는 경우

메이커가 선택적으로 제품의 서버 또는 SDK를 연동하면 미션과 관련된 최소한의 이벤트를 받을 수 있다.

```text
NoMoreVibe: 일회성 테스트 세션 생성
    → 사용자 동의 후 제품으로 이동
    → 제품에서 핵심 과제 수행
    → 제품 서버가 세션 ID와 허용된 이벤트를 제출
    → NoMoreVibe가 서명·시각·중복·제품 일치 여부 확인
    → 피드백에 이벤트 확인 상태 연결
```

브라우저 이벤트는 조작 가능한 신호로 취급한다. 서버 간 서명된 콜백도 제품 운영자가 참여자를 실제로 사용하게 했는지까지 독립적으로 보증하지 않으므로, 자기 제품 평가와 담합·반복 패턴 검토가 필요하다.

세션 토큰은 짧은 유효기간, 대상 제품 제한, 재전송 방지, 중복 처리 키를 갖는다. 이메일·원문 문서·결제정보를 URL 쿼리나 이벤트 본문에 담지 않는다. 로그인 인증 코드나 일회용 비밀번호를 실사용 증거로 요구하지 않는다.

### 8.5 적격 피드백 판정 기준

| 기준 | 확인 질문 |
| --- | --- |
| 관련성 | 해당 제품과 요청된 과제에 관한 경험인가? |
| 구체성 | 행동·화면·결과 또는 막힌 지점을 이해할 수 있는가? |
| 증거 일치 | 제출한 자료가 주장과 모순되지 않는가? |
| 신규성 | 기존 내용을 그대로 복제한 것이 아닌가? |
| 이해관계 | 자기 제품·팀·관련 계정 여부를 확인했는가? |
| 안전·정책 | 개인정보 노출, 공격, 홍보성 스팸이 없는가? |

문장 길이, 긍정적 감정, 별점, 메이커의 채택 여부는 보상 기준의 대체물이 아니다. “찾을 수 없었다”, “가입할 수 없었다”, “설명과 달랐다”도 구체적 근거가 있으면 가치 있는 피드백이다.

### 8.6 공개 상태와 보상 상태를 분리

```text
콘텐츠 상태: 초안 → 제출 → 공개 / 보완 요청 / 숨김 / 삭제
심사 상태: 미검토 → 검토 중 → 적격 / 부적격 → 이의제기 → 확정
보상 상태: 미대상 / 대기 → 적립 → 회수 또는 정정
개선 상태: 접수 → 검토 → 수정 배포 → 재확인
```

메이커가 비판적인 피드백을 마음에 들어 하지 않는다는 이유만으로 보상이나 공개를 막을 수 없다. 플랫폼 정책 위반을 신고할 수는 있지만 적격 판정은 플랫폼의 기준으로 결정한다.

### 8.7 반복 악용 대응

동일 문구의 대량 제출, 매우 짧은 반복 흐름, 같은 소수 계정끼리만 보상 교환, 자기 제품의 우회 평가, 증거 재사용을 이상 신호로 본다. 단, 동일 IP나 기기만으로 부정을 확정하지 않는다. 학교·회사·가족 등 정상적인 공유 환경이 있을 수 있기 때문이다.

의심 신호는 검토 우선순위를 정하는 데 사용하고, 제재에는 사유·증거·이의제기 경로를 제공한다.

## 9. 크레딧 및 평판 정책

### 9.1 사용자의 질문에 대한 최종 답

**남의 제품을 실제로 평가하면서 시작하는 것은 좋은 참여 경로지만, 내 제품을 등록하기 위한 강제 조건으로 만들지는 않는다.**

다른 제품을 평가한 사람은 기여 크레딧을 얻고, 그 크레딧으로 자신의 제품에 대한 피드백을 요청할 수 있다. 따라서 자연스러운 흐름은 다음과 같다.

```text
제품을 둘러본다
    → 내 관심사에 맞는 미션을 수행한다
    → 구체적인 피드백이 적격으로 인정된다
    → 기여 크레딧을 얻는다
    → 내 제품을 무료로 등록한다
    → 크레딧으로 내 제품의 테스트 미션을 연다
```

등록을 먼저 하고, 이후 크레딧을 모아 테스트를 요청해도 된다. 사용자를 억지로 상호 칭찬하게 하는 구조가 아니라 **공동 테스트 자원에 기여하고 활용하는 구조**다.

### 9.2 초기 정책: 돈과 기여 포인트를 분리한다

| 단위 | 의미 | 획득 | 사용 | 초기 출시 여부 |
| --- | --- | --- | --- | --- |
| 기여 크레딧 `C` | 커뮤니티 테스트 기여에 대한 내부 포인트 | 적격 User Feedback 미션 완료 | 커뮤니티 피드백 요청 | MVP에 도입 |
| 현금 결제 | 유료 테스트 모집·관리 서비스 요금 | 캠페인·구독 구매 | 명시된 유료 상품 | 유료 파일럿부터 |
| 에이전트 실행량 | 실행 비용과 제한을 관리하는 별도 단위 | 별도 구매 또는 구독 포함량 | Agent Run | 후속 단계 |
| 평판 | 참여 이력과 신뢰를 보여주는 비금전 정보 | 실제 적격 활동과 검토 결과 | 매칭 참고·프로필 표시 | 기본 이력부터 도입 |

**초기에는 기여 크레딧을 현금으로 판매하거나 현금으로 교환하지 않는다.** 구매형 크레딧이 필요해지면 유료 잔액과 무료 포인트의 장부·유효기간·환불 규칙을 분리한 뒤 도입한다. 이는 초반 원가와 보상 정책을 단순화하기 위한 권고다.

### 9.3 기여 크레딧의 기준값

다음 수치는 정책을 일관되게 설명하기 위한 **파일럿 기본값**이다. 운영 결과를 보고 정책 버전과 적용 시점을 공개하며 조정한다.

| 행동 | 크레딧 | 조건 |
| --- | ---: | --- |
| 제품 등록·관리 권한 확인·기본 공개 | 0C | 등록은 무료 |
| 표준 User Feedback 미션의 적격 완료 | +10C | 보상 미션으로 사전 예약된 건, 자기 제품 제외 |
| 사용자 1명의 적격 피드백 요청 | -15C | 요청 시 예약, 적격 완료 시 차감 |
| 가입·외부 링크 클릭·단순 체류 | 0C | 활동량만으로 발행하지 않음 |
| 긍정적인 별점·좋아요·메이커의 칭찬 | 0C | 감정이나 호평에 보상하지 않음 |
| 일반 자유 댓글 | 0C | 공개 의견 작성과 보상 미션은 별개 |
| Agent Feedback 제출 | 0C | 사람용 크레딧을 자동 발행하지 않음 |
| 친구 초대 | MVP에서는 0C | 다계정 유입을 부추기는 즉시 보상 제외 |
| 버그 수정 재확인 | 별도 미션이 열린 경우만 | 같은 건으로 반복 보상하지 않음 |

**두 건의 적격 피드백으로 20C를 얻으면, 내 제품에 1명의 피드백을 요청하고 5C가 남는다.** 요청 비용 15C와 기여 보상 10C의 차이 5C는 소각한다. 이는 현금 수익이 아니라 무료 포인트의 공급량을 조절하는 장치다.

기여 크레딧은 평판 점수와 다르다. 크레딧을 많이 썼다고 신뢰도가 낮아지지 않고, 크레딧을 많이 갖고 있다고 리뷰가 더 진실한 것도 아니다.

### 9.4 무제한 지급을 막는 수요 연결

아무 제품에나 리뷰를 쓰면 포인트가 생기는 구조는 피한다. **보상을 주는 피드백은 요청자의 예산이 예약되어 있거나, 플랫폼이 명시적으로 후원한 미션에 한정**한다.

```text
메이커가 3명 요청: 45C 예약
    → 각 슬롯에 테스터 참여
    → 2건 적격 완료: 30C 차감
        └ 테스터 두 명에게 각각 10C 지급, 합계 10C 소각
    → 1건 미매칭·기한 종료: 15C 예약 해제
```

자발적 피드백은 자유롭게 남길 수 있지만, 사전 미션 예산이 없으면 자동 보상이 발생하지 않는다. 이 조건은 작성 전에 표시한다.

### 9.5 초기 보상 공급

콜드스타트에서는 요청자에게 포인트가 없기 때문에 후원 미션이 필요하다. 운영자가 선별한 제품에 한정된 예산을 배정하고, 실제 피드백이 적격으로 인정될 때만 포인트를 발행한다.

전체 후원 한도와 계정별 참여 한도를 운영 장부에 기록한다. 예를 들어 파일럿 후원 한도를 3,000C로 잡는 실험을 할 수 있으나, 이는 자동으로 지급하는 가입 보너스가 아니다. 실제 수요와 검토 가능 인력을 기준으로 설정한다.

### 9.6 중복·상호 평가 제한

기본적으로 `사용자 × 제품 × 테스트 캠페인` 단위의 적격 보상은 한 번만 지급한다. 새 버전의 다른 과제나 재테스트 미션은 별도 승인된 경우 참여할 수 있다.

직접적인 “너 나 평가해주면 나도 해줄게” 약속이나 우호적 리뷰 조건부 교환은 금지한다. 한 커뮤니티 안에서 서로의 제품을 테스트한 사실만으로 자동 제재하지는 않으며, 반복된 관계·과제 수행·내용·보상 집중을 함께 검토한다.

### 9.7 크레딧 상태와 정산

| 상태 | 사용자에게 보이는 의미 |
| --- | --- |
| 사용 가능 | 현재 요청에 사용할 수 있는 잔액 |
| 예약 중 | 열린 미션에 묶여 있지만 아직 차감되지 않은 잔액 |
| 적립 대기 | 피드백 제출 후 심사 중인 예상 적립량 |
| 적립 완료 | 적격 확정 후 장부에 반영된 보상 |
| 사용 완료 | 적격 결과가 제공되어 확정 차감된 금액 |
| 예약 해제 | 미매칭·취소·기한 종료로 돌아온 금액 |
| 정정·회수 | 중복·오류·부정 확정에 따른 조정 |

장부는 덮어쓰지 않고 거래 이벤트를 추가하는 방식으로 설계한다. 심사나 결제 웹훅이 중복 수신되어도 같은 보상이 두 번 지급되지 않도록 한다.

실사용 증거가 불충분하면 보완 요청을 할 수 있다. 단순히 부정적인 의견이거나 메이커가 채택하지 않았다는 이유로 적립을 거절하지 않는다.

### 9.8 취소·유효기간·환금 원칙

무료 기여 크레딧은 MVP에서 계정이 활성 상태인 동안 만료시키지 않는 단순 정책을 권고한다. 정책 변경 시 사전 안내하고 이미 확보한 잔액을 소급 소멸시키지 않는다.

기여 크레딧의 현금 출금·개인 간 양도는 제공하지 않는다. 유료 캠페인의 취소·미이행 환급은 현금 상품의 별도 계약과 규정에 따른다. 무료 포인트 회수와 유료 결제 환급을 같은 용어로 처리하지 않는다.

부정 적립을 사용한 뒤 회수가 필요하면 장부에 사유를 남기고 보상 기능을 제한하거나 이후 적립에서 정산할 수 있다. 이를 현금 채무로 전환하지 않는다.

### 9.9 평판 설계

처음부터 게임형 레벨·랭킹을 전면에 내세우기보다 적격 피드백 수, 참여 분야, 재확인 기여, 이의제기 처리 이력을 보여준다.

평판을 돈으로 살 수 없게 한다. 신고 횟수만으로 평판을 낮추지 않고 확정된 위반을 반영한다. 신규 사용자가 과거 이력이 없다는 이유로 계속 미션을 받지 못하는 문제를 막기 위해 신규 참여 슬롯을 확보한다.

### 10.3 유료 Sprint가 파는 것

Sprint는 단순 댓글 수가 아니라 **정해진 대상·과제·기간에 맞는 테스트 결과를 수집하는 운영 서비스**다.

시작 전 대상 사용자, 과제, 시간 부담, 테스트 계정, 보상, 공개 범위, 결과물, 적격 기준, 미충족 시 처리 방식을 명시한다. “전문가”, “독립 사용자”, “10명 확보” 같은 표현은 실제 모집·검증 수준에 맞게 사용한다.

유료 테스트 참여자는 보상 사실을 공개한다. 긍정적 의견을 내야 보상받는 조건은 허용하지 않는다. 참가자에게 지급하는 현금 보상은 커뮤니티 기여 크레딧과 별도 장부로 관리하며 이중 보상 여부는 사전에 정한다.

### 10.4 단위 경제성 예시

아래 계산은 가격 결정 방법을 설명하기 위한 가정이며 실제 원가가 아니다.

| 가정 항목 | 예시 |
| --- | ---: |
| 적격 사용자 테스트 | 10명 |
| 1명당 보상 | $5 |
| 참가자 보상 합계 | $50 |
| 모집·검토 운영비 | $20 |
| 인프라·실행 변동비 | $5 |
| 결제비용 가정 | 매출의 3% + $0.30 |
| 목표 공헌이익률 | 매출의 30% |

```text
판매가격 P - (50 + 20 + 5 + 0.30 + 0.03P) = 0.30P
0.67P = 75.30
P ≈ $112.39
```

이 가정에서는 $49 판매 시 약 $27.77의 캠페인 변동 손실이 난다. $119 판매 시 공헌이익은 약 $40.13, 공헌이익률은 약 33.7%다.

이 계산에는 고정 인건비, 사용자 획득비, 세금, 환불, 재모집 비용 등이 전부 반영된 것은 아니다. 따라서 `$119`도 확정 가격이 아니라, **목표 결과를 보장하려면 단순 노출 상품과 다른 원가 계산이 필요하다**는 예시다.

### 10.5 무료 커뮤니티와 유료 Sprint의 구분

| 구분 | 커뮤니티 요청 | 유료 Sprint |

| 결과 해석 | 관심 있는 초기 사용자 표본 | 모집 조건을 충족한 테스트 표본 |

### 10.6 매출 우선순위

초기에는 대규모 구독 플랜이나 크레딧 팩을 동시에 출시하지 않는다. 먼저 수동 Assisted Sprint로 실제 지불 의사를 확인하고, 반복되는 운영 부담을 Maker Pro 기능으로 전환한다.

광고 상품은 나중에 도입하되 자연 노출과 시각적으로 분리한다. 결제 여부를 신뢰 점수·피드백 적격 판정·자연 추천 순위에 직접 넣지 않는다.

## 11. 핵심 사용자 시나리오

### 11.1 시나리오 A — 처음 온 사람이 제품을 사용하고 의견을 남긴다

```text
홈 → Launches → 제품 상세 → 테스트 시작
    → 준비물·과제 확인 → 외부 제품 사용
    → 완료 또는 막힘 보고 → 피드백 제출
    → 심사 상태 확인 → 결과 알림 → 업데이트 재방문
```

상세 탐색까지는 로그인하지 않아도 된다. 저장, 보상 미션 참여, 피드백 제출 등의 시점에 로그인한다. 테스트 전 “회원가입 필요”, “카드 불필요”, “샘플 데이터 제공” 같은 조건을 보여준다.

과제 수행에 실패하면 성공한 척 체크하도록 유도하지 않는다. `완료`, `일부 완료`, `시도했지만 막힘`, `제품 접근 불가` 중 실제 결과를 선택한다.

### 11.2 시나리오 B — 메이커가 먼저 기여한 뒤 자신의 제품에 피드백을 요청한다

```text
미션 탐색 → 타 제품의 적격 미션 2건 완료 → 20C 적립
    → 내 제품 무료 등록 및 관리 권한 확인
    → 15C로 사용자 1명 요청 → 5C 유지
    → 적격 결과 확인 → 답변 → 수정 또는 보류 사유 작성
```

“제품 등록 자격을 얻었다”가 아니라 “내 제품에 피드백을 요청할 자원을 얻었다”로 설명한다.

### 11.3 시나리오 C — Radar에서 자신의 제품을 발견한다

```text
Radar → 제품 상세 → ‘이 제품을 관리하시나요?’
    → 로그인 → 저장소·도메인 관리 권한 확인
    → 기존 제품 정보 확인 및 수정
    → 테스트 조건 설정 → Launch 공개
```

기존 URL·저장·피드백·발견 출처는 유지한다. 관리 권한이 없으면 신청을 완료할 수 없고, 대신 제작자에게 참여 링크를 공유하는 경로를 제공한다.

### 11.4 시나리오 D — 신규 제품을 직접 등록한다

```text
Launch your product → URL 입력 → 중복·기본 정보 확인
    → 관리 권한 확인 → 설명·카테고리·이용 조건 입력
    → 피드백 요청 및 에이전트 허용 범위 설정
    → 미리보기 → 공개
```

기본정보는 자동 채움을 제공할 수 있지만 반드시 수정·확인할 수 있게 한다. AI 요약을 그대로 사실로 확정하지 않는다. 초안 자동 저장, 재진입, 인증 보류 상태를 지원한다.

### 11.5 시나리오 E — 에이전트가 테스트한다

```text
메이커가 Agent Test 허용 범위 설정
    → 운영자·사용자가 Agent Run 요청
    → 예산·도메인·금지 행동 확인
    → 제한된 환경에서 실행
    → 증거가 연결된 Agent Feedback 제출
    → 메이커 검토 → 수정 → 같은 과제 재실행
```

미허용 도메인 이동, 결제, 계정 삭제, 실제 고객 데이터 변경 등은 기본적으로 차단한다. 외부 페이지가 에이전트에게 새로운 지시를 내리더라도 테스트 권한으로 취급하지 않는다.

### 11.6 시나리오 F — 피드백이 수정으로 이어진다

```text
피드백 열람 → 관련 이슈 연결 또는 생성
    → 작업 중 → 배포 버전 연결
    → 피드백 작성자에게 알림
    → 사용자·에이전트 재테스트
    → 해결 확인 또는 재오픈
```

GitHub 이슈를 닫았다는 이유만으로 제품 배포가 완료되었다고 추정하지 않는다. 이슈 상태, 릴리스 연결, 실제 수정 확인을 나누어 표시한다.

### 11.7 시나리오 G — 크레딧 적립이 거절되거나 Claim이 분쟁 상태다

거절 사유, 관련 기준, 필요한 보완 자료, 이의제기 기한을 보여준다. 일반 오류와 부정 의심을 같은 문구로 처리하지 않는다.

피드백 보상 분쟁은 메이커 혼자 결론 내리지 못하게 한다. Claim 분쟁에서는 기존 접근 권한을 즉시 상대방에게 넘기지 않고 민감한 변경을 보류한다.

### 12.2 공통 디자인 원칙

사용자가 좋다고 평가한 두 번째 미니멀 시안을 기본으로 한다. 흰 배경과 진한 네이비 텍스트를 중심으로 하고, 파란색은 선택·주요 행동, 초록색은 사람 피드백 상태, 보라색은 에이전트 출처를 보조하는 데만 사용한다.

일반 본문은 16px 이상을 기본값으로 제안한다. 데스크톱 콘텐츠 폭은 약 1,200px 내외로 제한하고, 좁은 화면에서는 한 열로 재배치한다. 전체 페이지에 카드를 중첩하거나 모든 정보에 테두리를 두지 않는다.

색만으로 User / Agent를 구분하지 않고 텍스트와 아이콘을 함께 사용한다. 주요 버튼은 화면마다 1개를 중심으로 두고, 보조 행동은 링크 또는 약한 버튼으로 제공한다.

긴 설명, 검증 근거, 집계 방법, 정책 상세는 확장 영역이나 별도 화면으로 이동한다. 메인에 기능의 존재를 모두 보여줄 필요는 없다.

### 12.3 메인에서 제거하거나 줄일 요소

대형 KPI 카드 4~5개, 상시 뉴스 패널, 복잡한 점수판, 여러 유료 배너, 사용자·에이전트 지표의 중복 노출은 기본 메인에서 제외한다.

실제 검증된 운영 지표가 충분히 쌓이기 전에는 수치 영역 자체를 숨긴다. GitHub 자동 발견 건수를 “활성 사용자 제품 수”처럼 보여주지 않는다.

### 12.4 공통 상태

모든 데이터 화면은 `로딩`, `빈 상태`, `오류`, `권한 없음`, `일부 데이터 없음`, `오래된 데이터`, `검토 중`을 지원한다.

폼은 키보드 탐색, 입력 오류 위치, 저장 상태, 제출 중 중복 클릭 차단, 첨부 실패 복구를 제공한다. 모바일에서는 긴 필터를 펼침 패널로 넣고 주요 행동을 화면 하단에서 찾기 쉽게 한다.

### 13.2 P01 — 홈

**목적:** 처음 온 사람이 “제품을 써볼지, 내 제품을 올릴지” 즉시 선택하게 한다.

```text
[NoMoreVibe]  Launches  Radar              검색      로그인 / 내 제품

                 Ship it. Get real users.
          만든 제품을 공개하고, 써본 사람의 피드백으로 개선하세요.

               [제품 등록하기]   [제품 둘러보기]

    Launches                            Radar
    메이커가 공개한 제품                 자동 발견한 프로젝트
    제품 3개                            프로젝트 3개
    [전체 보기]                         [전체 보기]

    지금 피드백을 기다리는 제품      2~3개만 표시

    다른 제품을 써보고, 내 제품의 피드백을 받아보세요. [참여 방법]

    Footer: Credits · Pricing · Trust · Contact
```

홈의 제품 한 행은 아이콘, 이름, 한 줄 설명, 카테고리 1~2개, 핵심 행동으로 구성한다. `Needs feedback`은 별도 복잡한 보드가 아니라 제품 상태나 짧은 목록으로 표현한다.

기본 메인에 User / Agent 수치를 모두 늘어놓지 않는다. 상세에서 각각 확인하도록 하고, 필요한 경우 `User 12 · Agent 3`처럼 간결하게 표시한다. 초기에는 예시 수치 대신 실제 목록만 보여준다.

### 13.3 P02 — Launches 목록

**목적:** 자신의 문제와 관심사에 맞는 제품을 고르게 한다.

기본값은 넓은 카드 여러 개보다 간결한 목록형을 권고한다. 필터는 `전체`, `피드백 모집 중`, `최근 공개`, `최근 개선`을 먼저 제공하고, 카테고리·이용 방식·가격 조건은 추가 필터에 둔다.

제품 행에는 이름, 한 줄 설명, 대상 사용자 또는 카테고리, 테스트 조건, 최근 변화 중 필요한 정보만 넣는다. 주 행동은 `사용해보기` 또는 `자세히 보기`다. 사용자가 미션 참여 의사를 표현하지 않았는데 외부 이동만으로 보상 예약을 생성하지 않는다.

정렬은 `추천`, `최근 공개`, `최근 업데이트`를 제공한다. 추천에는 사용자 관심사와 제품 접근 가능 여부, 신규 제품 탐색 노출을 고려하고, 에이전트 결과 수나 결제 여부를 인기도로 합산하지 않는다.

빈 상태에는 필터 초기화와 다른 제품 보기를 제공한다. 일시 중지·이용 불가 제품은 상태를 표시하고 테스트 예약을 막는다.

### 13.4 P03 — Radar 목록

**목적:** GitHub·웹에서 발견한 프로젝트를 가볍게 탐색한다.

상단에는 “자동으로 발견한 프로젝트입니다. 메이커 등록·안전성·품질이 확인된 목록은 아닙니다.”라는 짧은 안내를 제공한다.

기본 행 구성은 아이콘, 이름, 한 줄 설명, 출처, 카테고리, 최근 확인 정보다. GitHub 별은 저장소가 연결되고 데이터가 있을 때만 보조 정보로 노출한다. 기본 행동은 `보기`, `소스 열기`, `저장`이다.

`Claim`을 모든 방문자에게 가장 강한 버튼으로 반복하지 않는다. 일반 방문자는 제품 발견이 목적이므로, 상세나 보조 메뉴에 **“이 제품을 관리하시나요?”**를 둔다. 메이커가 연결된 제품은 `메이커 참여` 라벨과 Launch 상세로 연결한다.

추가 필터는 프로젝트 유형, 사용 방법, 카테고리, 발견 시점이다. “오픈소스” 필터는 라이선스 확인 자료가 있는 항목에 적용하고 공개 저장소 전체를 자동 포함하지 않는다.

### 13.5 P04 — 제품 상세: Testing Hub

**목적:** 설명을 읽고 끝나는 페이지가 아니라 사용과 개선의 연결점이 되게 한다.

상단에는 제품명, 설명, 관리 주체, 이용 조건, `사용해보기` 버튼을 둔다. 메이커가 검증되지 않았다면 그 상태를 명시한다. `피드백 남기기`는 보조 행동으로 제공한다.

탭은 `소개`, `피드백`, `업데이트`를 기본으로 한다. 피드백 내부에서 `User Feedback`과 `Agent Feedback`을 구분하고, 총합 하나를 “사용자 평가 수”로 표시하지 않는다.

**소개 탭:** 누구를 위한 제품인지, 해결하는 문제, 주요 기능, 가격·가입·설치 조건, 스크린샷, 메이커가 원하는 피드백 과제.

**User Feedback 탭:** 실제 경험 설명, 확인 수준, 보상 여부, 작성자와 제품의 관계, 메이커 답변, 후속 상태.

**Agent Feedback 탭:** 실행 주체, 버전, 과제, 증거, 성공·실패·판단 불가, 재실행 결과. 단순 소개문 분석은 실제 실행 결과와 분리한다.

**업데이트 탭:** 배포 시각, 변경 내용, 연결된 피드백, 수정 주장과 재확인 상태.

재사용 의향 비율을 표시한다면 표본 수와 응답 기준을 함께 보여준다. 소수 표본에서는 백분율 대신 `응답 3명 중 2명` 등 원자료 중심으로 표시하는 방식을 검토한다.

### 13.6 P05 — 제품 등록

**목적:** 짧은 단계로 정확한 제품 페이지를 만들고, 관리 권한을 확인한다.

| 단계 | 필수 또는 조건부 항목 | 선택 항목 | 주요 검증 |
| --- | --- | --- | --- |
| 1. 제품 연결 | 제품 URL 또는 사용 가능한 배포 경로 | 저장소 URL | 유효한 URL, 중복 제품, 안전한 조회 |
| 2. 기본 정보 | 제품명, 한 줄 설명, 카테고리, 대상 사용자 | 상세 설명, 제작 방식, 스택 | 길이 제한, 과장·금지 콘텐츠 |
| 3. 관리 권한 | 검증 방식과 Challenge 수행 | 보조 증빙 | 정확한 대상 권한, 충돌 여부 |
| 4. 사용 조건 | 가입·설치·비용·계정 필요 여부 | 샘플 계정, 미디어 | 테스트에 필요한 실제 준비물 |
| 5. 피드백 설정 | User Feedback 수용, 원하는 과제 | Agent 실행 허용 범위 | 자동 실행은 별도 명시 동의 |
| 6. 검토·공개 | 게시 권한 확인, 미리보기 | 이미지·추가 링크 | 미인증·중복·위험 상태 제한 |

화면상으로는 단계 1~2와 4~5를 묶어 **3~4단계의 짧은 흐름**으로 표현할 수 있다. 정책상 필요한 항목과 화면 단계 수를 동일시하지 않는다.

로고와 스크린샷은 없으면 기본 아이콘으로 시작할 수 있게 한다. GitHub 저장소가 없는 비공개 코드 서비스도 도메인·배포 권한을 확인해 등록할 수 있다. 등록 시 크레딧 결제는 요구하지 않는다.

오른쪽에는 간단한 카드 미리보기를 제공하되, 모바일에서는 제출 직전 미리보기로 이동한다. 모든 단계에서 초안을 저장한다.

### 13.7 P06 — Claim

기존 제품명, 정규 URL, 수집 출처를 읽기 쉬운 요약으로 제공한다. 이미 다른 계정이 관리 중이면 일반 인증 버튼 대신 `팀 초대 요청`, `권한 분쟁 신고`를 보여준다.

인증 결과는 `확인됨`, `재시도 필요`, `권한 부족`, `검토 중`, `분쟁으로 보류`로 구분한다. 확인된 경우에도 초안 검토를 거쳐 Launch로 공개하며, 기존 제품 기록을 복사해 새 제품으로 만들지 않는다.

### 13.8 P07 — 테스트 시작

미션 제목, 대상 사용자 조건, 준비물, 예상 부담, 과제 1~3개, 보상 여부, 사용 증거 기준을 한 화면에 보여준다.

`예상 5분` 같은 시간은 해당 미션의 메이커 입력 또는 검증된 안내로 표시하며, NoMoreVibe가 모든 제품의 소요 시간을 측정했다고 표현하지 않는다.

보상 미션이라면 참여 조건 확인 후 슬롯을 예약한다. 예약 만료·이탈 정책을 보여주고, 제출 후 플랫폼 심사가 오래 걸린다는 이유로 이미 제출한 슬롯이 자동 소멸하지 않게 한다.

### 13.9 P08 — 피드백 작성

상단에는 제품과 미션의 짧은 요약을 고정한다. 폼은 실제 결과, 구체적인 경험, 우선 개선점에 집중한다. 증거 첨부에는 개인정보 가림 안내를 제공한다.

기본 완료 선택지는 `완료`, `일부 완료`, `막힘`, `접근 불가`다. 실패를 선택하면 재현 과정과 오류 증거를 보완하도록 질문을 바꾼다.

피드백 출처는 세션과 인증 주체를 기준으로 설정한다. 사람이 문장 정리에 AI를 사용했는지와 AI가 실제 테스트를 했는지는 별개의 질문이다.

제출 전에 공개될 정보, 적립 조건, 검토 상태를 확인하게 한다. 제출 후에는 완료 페이지에서 **“심사 중 +10C”**처럼 확정 전임을 표시한다.

### 13.10 P09 — 피드백 상세

원문, 출처, 증거 수준, 관련 제품 버전, 관계·보상 라벨, 검토 상태, 메이커 답변, 연결된 이슈·업데이트를 표시한다.

첨부 증거를 누구나 보게 할지, 메이커·운영자만 보게 할지 구분한다. 개인정보나 민감한 오류 증거는 공개 원문과 분리할 수 있다.

메이커 행동은 `답변`, `이슈 연결`, `검토 중`, `수정 배포 연결`, `정책 위반 신고`다. 적격 심사 결과를 메이커가 임의로 수정하는 버튼은 제공하지 않는다.

### 13.11 P10 — 피드백 미션 목록

사용자 관심사와 사용 가능한 환경에 맞는 미션을 보여준다. 제품명, 과제, 준비물, 보상 `+10C`, 남은 슬롯, 보상 기준을 기본 정보로 한다.

자기 제품·소속 팀의 보상 미션은 참여 불가로 처리한다. 이미 예약 중인 미션, 동일 캠페인 참여 이력이 있는 미션, 필요한 환경이 맞지 않는 미션은 이유를 표시한다.

비메이커 일반 사용자에게 크레딧은 직접적인 가치가 약할 수 있다. 이들에게는 관심 제품, 제한 없는 무료 체험, 개선 기여, 선택적 유료 테스트 기회 등 실제 참여 이유를 제공해야 한다.

### 13.12 P11 — 빌더 대시보드

처음 화면은 복잡한 칸반보다 **해야 할 일 목록**을 중심으로 한다. `답변 필요`, `새 User Feedback`, `새 Agent Feedback`, `재확인 대기`를 우선 보여준다.

기본 영역은 제품 선택, 피드백 목록, 상태 필터, 우측 상세 패널이다. 칸반은 선택 보기로 제공한다. User와 Agent를 같은 작업함에서 볼 수 있지만 출처 라벨과 필터는 유지한다.

사용자 수와 에이전트 실행 수를 합쳐 하나의 KPI로 보여주지 않는다. 크레딧 잔액과 캠페인 예약량은 필요할 때만 보조 영역에 표시한다.

### 13.13 P12 — 업데이트 작성

배포 버전, 변경 내용, 관련 피드백, 관련 이슈·커밋·릴리스, 재테스트 요청 여부를 입력한다. 연결된 피드백 작성자에게 알림을 보낼지 확인한다.

상태 명칭은 `수정 배포됨`과 `재확인 완료`를 구분한다. 단순 커밋 생성이나 GitHub 이슈 종료만으로 배포 완료를 자동 표시하지 않는다.

### 13.14 P13 — 내 크레딧

**필요한 화면 구성:**

```text
Credits
기여하면, 내 제품에 피드백을 받을 수 있습니다.

사용 가능      예약 중       적립 대기
    35C          30C            10C
           ※ 위 잔액은 화면 설명용 예시

[미션 참여하기]   [내 제품 피드백 요청]

내역
유형          제품/미션           상태        증감
피드백 보상    Example A          적립 완료   +10C
피드백 요청    My Product         예약 중     15C 예약
미션 만료      My Product         예약 해제   15C 해제

[크레딧 정책] [심사 중 내역] [이의제기]
```

예시 잔액을 실서비스 기본값으로 하드코딩하지 않는다. 거래 유형, 전후 잔액, 예약 식별자, 관련 미션, 정책 버전, 시각을 조회할 수 있게 한다.

### 13.15 P14 — 크레딧 정책

화면 첫 줄은 **“제품 등록은 무료입니다. 크레딧은 피드백 요청에 사용합니다.”**로 한다.

세 개의 설명 블록으로 `적격 피드백 +10C`, `피드백 1명 요청 15C`, `심사 후 적립·완료 시 차감`을 보여준다. 하단에서 자기 제품 평가 제외, 호평 보상 금지, 미매칭 예약 해제, 비환금·비양도, 이의제기 규칙을 펼쳐볼 수 있게 한다.

단순 클릭이나 가입 보상, Agent Feedback 자동 보상은 포함하지 않는다. 모든 수치에 현재 정책 버전과 적용일을 연결한다.

### 13.16 P15 — 캠페인 만들기

첫 단계에서 **커뮤니티 요청**과 **유료 Assisted Sprint**를 구분한다. 같은 폼에서 포인트와 달러를 환산해 섞지 않는다.

공통 입력은 제품, 대상, 과제, 모집 수, 기간, 준비물, 피드백 공개 범위다. 사람 수와 에이전트 실행 수는 별도 필드로 제공한다.

커뮤니티형 요약은 `요청 3명 × 15C = 45C 예약`처럼 계산한다. 유료형은 참가자 보상, 운영 범위, 예상 총액, 세금·환급 조건을 보여준다. 확정되지 않은 모집 결과를 “보장”이라고 표시하지 않는다.

### 13.17 P16 — 캠페인 결과

예약, 참여, 제출, 적격, 보완, 취소, 미충족 슬롯을 나누어 보여준다. User와 Agent 결과는 별도 탭으로 제공하고 AI 요약은 원본 피드백을 참조하도록 한다.

요약에는 긍정적인 내용뿐 아니라 막힘, 실패, 비채택 의견도 포함한다. 샘플 수와 대상 조건을 함께 표시하고 통계적으로 대표하는 시장조사처럼 표현하지 않는다.

### 13.18 P17 — Agent Runs

제품별 허용 도메인, 실행 환경, 테스트 계정, 금지 행동, 비용 한도, 실행 횟수, 결과 공개 범위를 설정한다. 실행 버튼 앞에 권한·예산 요약을 보여준다.

실행 목록은 `대기`, `실행 중`, `완료`, `차단`, `오류`, `취소`, `판단 불가`를 구분한다. 실제로 실행한 도구·환경·관찰 결과와 소개문 분석을 혼합하지 않는다.

### 13.19 P18~P21 — 요금·개인 활동·신뢰·운영

**요금제·청구:** 무료와 유료의 차이, 이용량, 갱신·해지, 청구서, 환급 상태를 제공한다. 유료 가입으로 기본 검토의 신뢰 기준이 느슨해지지 않는다.

**내 활동·알림:** 참여 미션, 적립, 메이커 답변, 수정 배포, 재테스트 요청을 보여준다. 프로필의 활동 공개 범위를 설정할 수 있게 한다.

**신뢰·이의제기:** 인증 의미, 증거 수준, 보상 기준, 신고 정책, 처리 진행 상태를 공개한다.

**운영 콘솔:** 원본 증거와 신청 내역, 규칙 버전, 검토자, 결정 사유, 재검토 이력을 남긴다. 고위험 권한 변경과 보상 정정은 감사 로그를 필수로 한다.

## 14. 데이터 모델·API·연동 설계

### 14.1 기술 구성의 범위

기존 서비스 기술 스택을 먼저 확인하고 그 안에서 구현한다. 아래는 특정 프레임워크 버전이나 현재 코드 구조를 가정하지 않은 논리 설계다.

관계형 데이터베이스는 제품·권한·미션·장부의 정합성을 담당하고, 작업 큐는 수집·검증·알림·에이전트 실행을 분리한다. 첨부 파일은 비공개 접근 제어가 가능한 객체 스토리지에 보관한다. 외부 URL 조회와 에이전트 실행은 일반 API 서버와 분리된 제한 환경에서 처리한다.

### 14.2 핵심 엔터티

| 엔터티 | 핵심 필드·역할 |

| `users` | 로그인 주체, 프로필, 상태, 알림 설정 |

| `payments` / `refunds` | 현금 상품의 결제와 환급. 무료 크레딧과 분리 |

### 14.3 데이터 모델의 중요한 제약

피드백에는 `source_type`, `relationship`, `incentive_type`, `evidence_level`을 각각 둔다. 하나의 `verified=true` 필드로 모든 신뢰를 표현하지 않는다.

제품별 멤버십을 확인한 서버만 관리자 기능을 허용한다. 인증 결과와 현재 권한이 서로 어긋나면 재검증하거나 민감 기능을 제한한다.

크레딧 거래는 정수 단위로 관리하고, 예약·차감·보상 지급은 트랜잭션으로 묶는다. 장부 합계와 표시 잔액을 검증하며, 정정은 기존 기록 수정이 아닌 반대·조정 거래로 기록한다.

### 14.5 반드시 필요한 정합성 규칙

동일 피드백에 대한 보상은 한 번만 지급한다. 캠페인 슬롯 수보다 많은 참여자가 동시에 확정되지 않게 한다. 사용 가능한 잔액보다 큰 예약을 생성하지 않는다.

에이전트가 사람 피드백 API를 호출해 보상받을 수 없게 한다. 제품 소유자가 자신에게 유리하도록 심사 결과를 바꿀 수 없게 한다. 외부 서비스 이벤트가 중복 수신되어도 테스트와 보상 수가 증가하지 않게 한다.

알림 발송 실패 때문에 핵심 거래가 취소되거나 반대로 거래 실패 상태에서 보상 알림이 나가지 않도록 후속 작업을 분리한다.

### 14.6 GitHub·개발 에이전트 연동

제품 등록의 마찰을 줄이기 위해 `/nomorevibe launch`, `/nomorevibe feedback`, `/nomorevibe update` 같은 명령 흐름을 제공하는 방안을 유지한다. 이는 **연동 기능 제안**이며 현재 구현 사실을 재확인한 것은 아니다.

등록 시 저장소 정보를 읽어 초안을 만들고, 게시 전 사람이 확인한다. 피드백 가져오기는 제품 관리자 권한을 확인하고, 외부 문장을 명령이 아닌 비신뢰 입력으로 취급한다. 업데이트 공개는 연결할 배포와 피드백을 명시적으로 선택한다.

GitHub 이슈 생성과 릴리스 연결은 별도 동의를 받는다. 이슈를 닫거나 커밋이 올라왔다는 사실과 사용자가 겪은 문제가 해결되었다는 사실을 동일시하지 않는다.

### 14.7 첨부·증거 보관

원본 스크린샷과 실행 로그는 접근 제어된 객체 스토리지에 보관하고 제한된 시간의 접근 링크를 제공한다. 파일 종류·크기·악성 콘텐츠를 검토하며, 공개에 부적절한 민감정보를 삭제하거나 가릴 수 있게 한다.

MVP는 PNG·JPG 같은 제한된 이미지 형식을 우선 지원하고, SVG·HTML·실행 파일 등은 별도 안전 처리 전까지 증거 첨부로 허용하지 않는 방안을 권고한다.

<a id="sec-15"></a>
## 15. 운영·신뢰·보안 정책

### 15.1 제품과 참여자의 안전

악성 링크, 피싱, 불법 콘텐츠, 위장 제품, 결제 유도 사기를 신고할 수 있게 한다. 자동 수집 제품은 안전성 검증 완료로 표시하지 않는다. 테스트 모집 전에는 최소한 이용 가능 경로와 준비물, 위험한 권한 요구 여부를 점검한다.

메이커는 테스트용 계정과 샘플 데이터를 제공하는 방식을 우선 사용한다. 테스터가 개인 금융·의료·법률 문서 등 민감한 자료를 업로드해야만 보상받게 만드는 미션은 초기 운영 범위에서 제외한다.

### 15.2 과도한 추적을 피한다

방문 경로, 미션 ID, 필요한 핵심 이벤트처럼 목적에 직접 필요한 정보만 수집한다. 외부 제품의 모든 클릭, 입력 내용, 화면 녹화를 기본 수집하지 않는다.

화면 녹화나 확장 프로그램은 향후 별도 동의가 있는 선택 기능으로 검토한다. 기본 기능 이용이나 일반 피드백 작성을 위해 강제 설치하게 하지 않는다. 증거의 공개 범위, 보관 기간, 삭제 요청 경로를 서비스 정책에 명시한다.

구체적인 개인정보 처리, 국제 이전, 결제·환급·현금 보상 운영 요건은 실제 출시 국가와 결제 구조를 기준으로 별도 법률·정책 검토를 진행한다. 이 문서는 해당 법률 준수를 확정하는 의견서가 아니다.

### 15.3 외부 URL 검증 보안

제품 URL·검증 파일을 서버가 가져올 때 내부 IP, 클라우드 메타데이터 주소, 제한된 포트, 위험한 리다이렉트 등으로 접근하지 않도록 설계한다. 최초 입력뿐 아니라 리다이렉트와 DNS 해석 결과도 검증한다.

메타데이터 수집·도메인 검증·브라우저 실행을 일반 서비스 내부망과 분리한다. 사용자가 제공한 HTML·README·스크린샷은 비신뢰 데이터로 처리한다.

### 15.4 에이전트 실행의 경계

자동 테스트는 제품 관리자의 동의와 작업 범위가 있는 경우에만 진행한다. Radar에 발견되었다는 이유만으로 계정 생성, 대량 요청, 결제, 데이터 변경을 수행하지 않는다.

실행 가능한 도메인, 로그인 계정, 테스트 데이터, 허용 행동, 금지 행동, 비용·시간 한도를 정한다. 결제·삭제·실제 고객 데이터 변경·외부 메시지 발송 등은 기본적으로 차단한다.

웹페이지나 피드백 본문에 “비밀 키를 보내라”, “다른 사이트로 이동하라” 같은 지시가 있더라도 테스트 권한으로 간주하지 않는다. 실행 로그와 외부 전송을 제한하고 비밀정보가 증거에 노출되지 않게 한다.

### 15.5 품질 검토와 이의제기

자동 분류는 중복·스팸·우선 검토 항목을 찾는 보조 수단으로 사용한다. 초기에는 운영자가 적격 보상 결정을 확인하고, 명확한 규칙과 오류율이 확보된 영역부터 자동화한다.

검토 사유는 선택 코드와 설명을 함께 남긴다. 이의제기 시 최초 판정의 근거와 추가 증거를 확인할 수 있게 한다. 보상 분쟁의 최종 결정권을 피평가자인 메이커에게만 주지 않는다.

### 15.6 콘텐츠와 보상은 분리한다

정책을 위반하지 않은 비판적 의견은 플랫폼의 중요한 자산이다. 보상 대상이 아니라는 이유만으로 일반 의견을 삭제하지 않고, 운영 정책에 따라 공개·비공개·미확인 표시를 결정한다.

반대로 보상 심사를 통과했다고 해서 개인정보나 위험한 내용이 자동으로 공개되는 것도 아니다. 콘텐츠 안전과 보상 적격은 별도 검토한다.

### 15.7 운영 역할

| 역할 | 주요 책임 |
| --- | --- |
| 제품 운영 | 메이커 온보딩, 과제 설계, 매칭, 미응답 제품 관리 |
| 신뢰·품질 검토 | Claim, 증거, 적격 판정, 신고·이의제기 |
| 개발·인프라 | 권한·장부·연동·작업 큐·실행 환경 안정성 |
| 커뮤니티 운영 | 관심사별 참여 모집, 기여자 유지, 운영 공지 |
| 유료 캠페인 운영 | 대상 확인, 모집, 보상, 결과물, 환급 |

초기에는 한 사람이 여러 역할을 수행할 수 있지만, 민감한 보상 정정과 권한 분쟁의 근거·이력을 남겨 역할이 나뉘어도 이어받을 수 있게 한다.

## 16. 출시 전략과 초기 네트워크 형성

### 16.1 많은 제품보다 응답하는 메이커를 확보한다

초기에는 수천 개의 자동 수집 제품을 전면에 늘어놓기보다, 실제로 피드백에 답하고 제품을 수정할 의사가 있는 소수 메이커를 확보한다.

참여 조건은 테스트 가능한 이용 경로, 명확한 대상 사용자, 과제 1~3개, 피드백에 답할 담당자다. 제품이 덜 완성되었다는 이유만으로 배제하기보다 사용자가 무엇을 테스트하는지 알 수 있게 한다.

### 16.2 파일럿의 단위

권고 파일럿은 특정 관심사 또는 카테고리에서 **메이커 20~30개 제품, 제한된 테스트 기간, 수동 매칭·심사**로 구성한다. 테스터 수는 모집 가능한 풀과 실제 참여율을 보고 조정한다.

메이커끼리의 교차 테스트를 시작점으로 삼되, 목표 고객과 일치하는 비메이커 사용자도 포함한다. “개발자가 개발자를 위해 만든 제품” 외의 시장에서는 이 구분이 특히 중요하다.

### 16.3 초기 참여 유인

| 대상 | 참여 이유 | 주의점 |
| --- | --- | --- |
| 메이커 | 첫 구체적 피드백, 개선 사례, 커뮤니티 요청 크레딧 | 등록을 강제로 교환 활동과 묶지 않음 |
| 관심 분야 사용자 | 새로운 도구, 사용 조건이 투명한 체험, 의견 반영 | 크레딧만으로 일반 사용자가 계속 참여할 거라 가정하지 않음 |
| 전문 테스터 | 명확한 과제와 선택적 유료 테스트 | 전문가 자격·독립성 과장 금지 |
| 에이전트 운영자 | 표준화된 테스트·재실행 경로 | 실제 사용자 역할 대체 금지 |

### 16.4 유입 경로

메이커 등록 도구, 제품에 삽입하는 피드백 배지, 개선 결과 공유 카드, 관심사별 커뮤니티, 기존 프로젝트의 제작자에게 보내는 선별된 참여 안내를 활용할 수 있다.

자동 수집한 연락처로 무차별 대량 홍보를 보내는 방식은 피한다. 제작자가 자발적으로 자신의 제품을 연결하고 기존 피드백을 가져갈 수 있게 한다.

### 16.5 가장 좋은 홍보 콘텐츠

“이번 주 1위 제품”만 반복하기보다 **“이 피드백으로 이 부분이 바뀌었다”**는 실제 개선 사례를 소개한다.

```text
사용자가 겪은 문제
    → 구체적인 피드백
    → 메이커가 선택한 해결책
    → 변경된 버전
    → 재테스트 결과
```

사례 공개는 메이커·기여자의 공개 범위와 첨부 증거의 개인정보를 확인한 뒤 진행한다. 개선 사례를 만들기 위해 긍정적 결과만 선택적으로 강요하지 않는다.

## 17. 개발 우선순위와 단계별 검증

### 17.1 단계 0 — 운영 가능한 문제 정의

기존 코드·데이터 모델·수집 권한·제품 상태를 점검한다. 자동 발견 제품과 메이커 제출 제품을 구분하고, 현재 지표가 무엇을 실제로 의미하는지 확인한다.

동시에 메이커 인터뷰와 소규모 수동 테스트를 통해 과제 작성, 증거 제출, 적격 판정, 답변·수정의 부담을 확인한다.

**통과 조건:** 어떤 고객이 어떤 테스트 결과에 가치를 느끼는지 설명할 수 있고, 실제 수동 운영 사례가 확보되어야 한다.

### 17.2 단계 1 — 사람이 사용하는 MVP

포함 범위는 미니멀 홈, Launches / Radar, 제품 등록·Claim, 기본 상세, 과제 기반 피드백, 수동 품질 검토, 기여 크레딧 장부, 빌더 답변·업데이트, 기본 알림이다.

Agent Feedback은 출처가 구분된 데이터 구조와 표시 방식을 먼저 준비하되, 완전 자율 실행·브라우저 검증 시스템까지 한 번에 개발하지 않는다.

**통과 조건:** 관리 권한 분쟁·중복 보상·미션 미완료·증거 부족 같은 예외를 수동으로 처리할 수 있고, 첫 사용부터 개선 알림까지 최소 한 번 연결되어야 한다.

### 17.3 단계 2 — 사용 증거와 반복 개선

제품 이벤트 연동, 선택적 GitHub 이슈·릴리스 연결, 적합 사용자 매칭, 재테스트 미션, 내 활동과 개선 이력, 운영 자동화를 추가한다.

**통과 조건:** 강한 증거가 피드백 품질과 운영비에 실제로 도움이 되는지 확인한다. 설치·연동 마찰이 참여를 과도하게 낮추지 않아야 한다.

### 17.4 단계 3 — 유료 Sprint와 운영 구독

수동 Assisted Sprint로 모집과 원가를 검증하고, 반복되는 메이커 작업을 Maker Pro에 포함한다. 청구·환급·유료 보상 공개를 구현한다.

**통과 조건:** 유료 고객이 결과에 가치를 느끼고 반복 구매할 이유가 있으며, 모집·보상·검토 비용을 포함해 지속 가능한 단위 경제성을 확인한다.

### 17.5 단계 4 — 에이전트 테스트와 팀 확장

제품별 허용 범위, 격리된 실행, 표준 결과, 재현·재테스트, 별도 실행 비용, 팀 권한, 비공개 테스트를 제공한다.

**통과 조건:** 자동 실행이 사람 피드백의 대체물로 오해되지 않고, 보안 경계와 실행 예산, 증거 품질이 통제되어야 한다.

### 17.6 초기에는 미루는 기능

복잡한 신뢰 점수, 화려한 레벨 시스템, 글로벌 순위 경쟁, 다단계 크레딧 상품, 무제한 에이전트 실행, 대규모 뉴스 허브, 자체 화면 녹화 확장 프로그램은 후순위로 둔다.

기능의 수가 아니라 **등록 → 사용 → 피드백 → 수정 → 재방문**이 작동하는지를 우선한다.

### 18.2 우선 실험

초기 표본이 작은 실험은 방향 탐색으로 해석한다. 인과 효과나 시장 전체 수요를 과장하지 않는다.

## 19. 리스크·의사결정·출시 체크리스트

### 19.1 주요 리스크

| 리스크 | 조기 신호 | 대응 |
| --- | --- | --- |
| 메이커만 있고 테스터가 없음 | 요청 대기 증가, 첫 피드백 지연 | 카테고리 축소, 미션 부담 감소, 후원 예산, 타깃 사용자 모집 |
| 포인트를 노린 저품질 참여 | 반복 문장, 증거 재사용, 좁은 상호 관계 | 수요 기반 보상, 예약 한도, 품질 검토, 이의제기 |
| 비판적 피드백이 보상에서 불리함 | 부정 의견의 높은 거절률 | 판정 기준 공개, 메이커와 심사 권한 분리 |
| 잘못된 Claim | 기존 관리자 신고, 도메인·저장소 불일치 | 검증 범위 명시, 충돌 심사, 재검증 |
| Agent 결과가 사용자 지표를 오염 | 실행량 증가만으로 인기 상승 | 출처별 지표·추천 신호 분리 |
| 유료 테스트의 원가 초과 | 재모집·검토 시간 증가 | 대상·과제별 가격, 수동 견적, 모집 약속 제한 |
| 크레딧 공급 과잉 | 요청 수보다 적립량만 증가 | 예산 연결 미션, 차감·소각, 후원 발행 한도 |
| 제품이 피드백에 응답하지 않음 | 장기 미응답·미수정 누적 | 응답 상태 공개, 모집 중지, 활성 제품 기준 |
| 과도한 검증 마찰 | 테스트 시작 후 높은 이탈 | 최소 증거, 선택적 연동, 막힘 보고 인정 |
| 개인정보·실행 보안 문제 | 증거에 비밀정보 노출, 허용 범위 이탈 | 최소 수집, 비공개 저장, 격리 실행, 권한·예산 제한 |

### 19.2 현재 문서에서 기준으로 삼는 결정

`Radar / Launches 분리`, `User / Agent 분리`, `등록 무료`, `관리 권한 확인`, `실사용 확인 수준 표시`, `출처별 지표`, `피드백-수정 연결`, `호평 비보상`은 구현 기준으로 권고한다.

`+10C / -15C`, 후원 예산, 요금제, 유료 Sprint 수량과 가격, 상세 보관 기간, 부정 탐지 임계값, 목표 고객의 세부 범위는 파일럿에서 검증할 설정값이다.

### 19.3 출시 전 확인 사항

- [ ] Radar 수집 출처와 실제 메이커 제품이 구분되어 있다.
- [ ] 제품 등록은 크레딧 소모 없이 가능하다.
- [ ] URL을 입력하거나 GitHub 로그인만 했다고 관리 권한이 부여되지 않는다.
- [ ] 기존 관리자의 제품을 다른 계정이 자동 탈취할 수 없다.
- [ ] 방문, 테스트 시작, 사용 확인, 적격 피드백을 구분한다.
- [ ] 막힘·접근 실패도 증거가 충분하면 적격 피드백이 될 수 있다.
- [ ] Agent 결과는 사람용 보상과 사람 사용자 수에 포함되지 않는다.
- [ ] 보상 미션에 예약 예산이 있으며 중복 지급이 불가능하다.
- [ ] 미충족 미션은 크레딧 예약 해제가 가능하다.
- [ ] 비판적 리뷰 때문에 메이커가 보상을 막을 수 없다.
- [ ] 크레딧 장부와 현금 결제 장부가 분리되어 있다.
- [ ] 수정 배포와 실제 해결 재확인을 구분한다.
- [ ] 신고·이의제기·개인정보 삭제 요청 경로가 있다.
- [ ] 모바일·키보드 사용·빈 상태·오류 상태를 확인했다.
- [ ] 화면의 예시 수치·임의 확률·과거 날짜가 운영 화면에 남아 있지 않다.
- [ ] 에이전트가 외부 입력을 권한으로 오인하거나 허용 범위를 벗어나지 않는다.

## 20. 이미지 시안과 적용 가이드

### 20.1 시안 활용 원칙

아래 이미지는 본 대화에서 생성된 **원본 방향 시안**이다. 이미지 안의 문구·가격·수치가 최종 정책과 다를 수 있으므로 개발 기준은 본문을 따른다. 이미지를 새롭게 수정하거나 동작하는 화면으로 구현한 것은 아니다.

홈은 가장 단순한 버전의 여백과 구성에 맞춘다. 기존에 복잡하게 제시된 사업·기능 인포그래픽은 설명 참고용으로 사용하고, 실제 서비스 메인에 그대로 옮기지 않는다.

각 이미지의 상대 경로는 통합 ZIP 안에서 동작한다.

## 22. 최종 결론

NoMoreVibe는 “AI로 만든 제품이 많이 모인 곳”에서 출발하지만, 성공하려면 **제품이 실제 사용을 만나고 개선되는 곳**이 되어야 한다.

이를 위한 출발점은 복잡한 점수판이나 큰 상품 구성이 아니다. **미니멀한 발견 화면, 쉬운 무료 등록, 분명한 관리 권한 확인, 사람이 시도한 경험과 에이전트 결과의 구분, 구체적인 피드백, 공정한 참여 보상, 수정 결과의 공개**다.

메이커에게는 “누가 써봤고 무엇을 고치면 되는가”가 남아야 한다. 사용자에게는 “내가 남긴 의견이 읽혔고 무엇이 달라졌는가”가 남아야 한다. 에이전트에게는 “어떤 범위에서 어떤 과제를 실행했고 어떤 증거가 있는가”가 남아야 한다.

**사업의 핵심 거래는 노출이나 칭찬을 파는 것이 아니라, 제품의 다음 결정을 더 잘 내릴 수 있도록 돕는 것이다.**

### 문서와 산출물의 범위

이 패키지는 사업·서비스 기획 MD, 원본 이미지 시안 19종, 이미지 목록 및 검수 정보로 구성되어 있다. 서버 코드, 실제 결제 연동, API 구현, 실행 가능한 웹 프로토타입은 포함하지 않는다.

### 자료 기준

- 본 대화에서 사용자가 설명한 사업 목적과 디자인 선호.
- 본 대화의 NoMoreVibe 사업·서비스·신뢰·보상 관련 제안.
- 본 대화에서 생성된 이미지 시안 중 본 문서에 연결한 19종.
- 가격·크레딧·수량·파일럿 범위는 별도 표기한 설계 가정. 실제 운영 데이터나 외부 조사로 확인된 시장 수치가 아님.
