# 전수 점검과 수정 계획 (2026-11-21)

소유자 요청: 레이턴시가 걸리는 구간, 로직 오류, 수집 오류, 비효율적 코드, 표준에서 벗어난 개발, 동시 접속 처리, 비동기가 아닌 곳을 전부 검토하고 **수정 계획**을 올린다. 리팩토링으로 효율화할 수 있는 구조 변경도 제안한다.

이 PR 은 **문서만** 담는다(배포 대상 0개). 코드는 아래 작업 묶음마다 따로 PR 로 고친다.

- 발견 159건 — P0 1 · P1 34 · P2 66 · P3 58. 중복을 묶어 **작업 묶음 46개**로 정리했다.

## 1. 결론

1. **주 DB 가 느린 까닭은 두 가지 구조다.** 0.5초 넘는 문장이 하루 약 8만 건(합계 약 34시간)인데,
   약 65% 는 「할 일이 있나」를 상태 표가 아니라 **이력 전체를 매번 다시 훑어** 구하는 조회이고, 약 31% 는 **한 행의 잠금을 기다리는 시간**이다(모델 장부의 전역 한 행이 29.5%).
2. **작은 수정 아홉 개(1단계)로 그 절반 가까이를 걷어낼 수 있다(추정).** 조건식 한 줄(357ms → 0.06ms, 직접 실측), 빠진 인덱스, 미룬 잡이 5초마다 다시 도는 것, 같은 진행 집계를 여섯 프로세스가 따로 세는 것. 1단계가 겨누는 문장이 합계의 57% 이고, 호출 수를 일정대로 되돌리는 것만으로 그 대부분이 준다.
3. **시한이 있는 문제가 하나 있다.** 사유 번역 진행 집계가 지금 6.5~6.8초인데 원천 행이 6일에 20% 씩 늘어 **약 3주 뒤 10초 상한을 넘는다.** 넘으면 감시가 계속 「unknown」이 되고 배포 관문이 막힌다(W1-5).
4. **안전 문제 하나를 먼저 고친다.** 메이커 소유 확인이 기대는 저장소 id 근거가 재수집·갱신 때 덮여 사라진다. 소유자 규칙(「아이디 근거 사라지지 않도록」)에 어긋난다(W0-1).
5. **수집은 「일시 장애」와 「영구 실패」를 구분하지 못한다.** 봇 차단 응답(401·403·429)으로 후보 1,344건이 「접속 불가」로 자동 거부됐고, 일시 오류 4번으로 frontier 약 1,690건이 되살릴 길 없이 멈췄다(W1-8 · W4-1).
6. **구조는 재작성하지 않는다.** 마이크로서비스·메시지 브로커·워커 양쪽 동시 가동은 이 규모에 과하다. 바꿀 구조는 넷이다 — 유지되는 대기열, 장부 잠금 쪼개기, 진행 집계 한 번만 계산, 배포 범위를 런타임 경계로 판정(6절·9단계).

## 3. 묶음별 계획

발견 ID 는 `areas/` 문서의 항목이다. 같은 문제를 여러 구역이 짚은 경우 여기서 하나로 묶었다.

### 0단계 — 전제와 안전

#### W0-1 저장소 id 근거를 덧붙이기만 하는 표로 보존 (M)
- 묶은 발견: DOM-01 (DOM-07 은 이 표를 읽어 GitHub 호출을 줄인다)
- 문제: 소유 확인은 「전에 본 저장소 id 가 지금과 다르면 거절」에 기대는데, 근거 세 곳이 모두 마지막 값만 남기거나 7일 뒤 지워진다. `saveFetchedDocument` 는 같은 행의 옛 id 와 달라도 비교 없이 덮는다(직접 확인).
- 고칠 것:
  1. 새 표 `repository_identity_anchors`(저장소 이름 소문자 · GitHub 저장소 id · node id · 주인 id · 출처 · 처음/마지막 본 시각, `(이름, id)` 유일). 지우지 않고 보관 정리 잡에서도 뺀다.
  2. 마이그레이션 직후 세 출처(수집 원본 · 사실 수집 · 남아 있는 스타 관측)로 백필한다 — 더 잃기 전에 이것부터 배포한다.
  3. 수집·사실 수집·스타 관측·소유 확인이 id 를 볼 때마다 이 표에 넣는다.
  4. id 가 바뀌면 원본·사실을 덮지 않고 사람 검토로 보낸다. 소유 확인은 이 표만 읽는다.
- 검증: 같은 이름에 다른 id 로 다시 수집 → 원본 유지 · 근거 2개 · 소유 확인 `repo_replaced` 인 통합 테스트. 백필 뒤 저장소 수 대조.
- 배포: 마이그레이션 + 백필(3.5GB 표를 읽으므로 묶음으로, 창 밖) → crawler · maintenance · web.
- 상세 경로는 공개 저장소라 싣지 않았다(비공개 메모).

#### W0-2 문장 단위 관측 (S, 운영 설정 — 소유자 승인)
- 묶은 발견: DB-13 · CAP-15 · DB-12
- 문제: `pg_stat_statements` 가 없어 0.5초 미만 문장과 하루 1만 건의 statement timeout 이 어느 문장인지 모른다. 잠금을 누가 쥐었는지도 남지 않는다.
- 고칠 것: `log_lock_waits=on`(reload 만), `track_io_timing=on`, `pg_stat_statements`(shared_preload_libraries 라 **주 DB 재시작 필요** — 전환 창). 장부 트랜잭션에 경로 표식(`application_name`)을 붙인다.
- 효과: 아래 모든 묶음의 전후를 문장 단위로 잴 수 있다. 이 계획의 PLAUSIBLE 항목 대부분이 이것으로 확정된다.

#### W0-3 온라인 인덱스 경로 (S)
- 묶은 발견: DB-17
- 문제: drizzle 마이그레이터는 밀린 마이그레이션을 한 트랜잭션으로 돌려 `CREATE INDEX CONCURRENTLY` 를 쓸 수 없다. 이 계획의 인덱스들은 수백 MB~GB 표에 걸린다.
- 고칠 것: 트랜잭션 밖에서 `CREATE/DROP INDEX CONCURRENTLY` 를 돌리는 운영 도구(짧은 `lock_timeout`, 실패 시 INVALID 인덱스 정리) + 뒤따르는 마이그레이션은 `IF NOT EXISTS` 로 기록만. 절차를 배포 문서에 더한다.

#### W0-4 로그·오류 기록 최소분 (S)
- 묶은 발견: STD-01 · STD-02
- 문제: 공통 로거가 drizzle 오류의 message(SQL 전문과 입력값)를 그대로 남기고 정작 SQLSTATE 는 버린다. 역할 워커·scheduler·감시 등 진입점 13곳은 최상위 오류를 한 줄 문구로 바꿔 버려 크래시 루프의 원인이 로그에 없다.
- 고칠 것: 로거의 Error 처리를 이미 있는 `dbErrorFields` 규칙(SQLSTATE·이름·잘린 메시지)으로 통일. 진입점 공통 `reportFatal`.
- 배포: 일반 배포(공통 worker 이미지 전부).

### 1단계 — 작은 PR, 큰 효과

#### W1-1 장부 상태 조건을 인덱스를 타는 꼴로 (S)
- 묶은 발견: REVIEW-04 · CAP-09 · DB-04
- 문제: 2차 심사의 낡은 표 정리가 `coalesce(state,'') NOT IN ('waiting','withdrawn','settled')` 로 2.5GB 장부 전체를 읽는다. 힌트마다, 후보마다(틱당 최대 80번).
- 고칠 것: `state IN ('reserved','dispatched')`. `state` 는 NOT NULL + CHECK 6값이고 미확정(indeterminate)은 보호 판정에 쓰이지 않으므로(`capacityBlocksStaleReconcile`) 결과가 같다.
- 효과(직접 실측, 복제본): 357ms · 84,708 버퍼 → **0.06ms · 57 버퍼**. 읽는 행도 613 → 8 이라 후보×장부 쌍마다 도는 LIKE·정규식이 함께 준다. 대상 문장은 하루 10,293초.
- 검증: `tests/integration/ai2-stale-reconcile.test.ts`, 복제본 EXPLAIN.
- 배포: 일반 배포(reviewer). 인덱스 추가 없음.

### 2단계 — 모델 장부의 전역 잠금

모든 LLM 호출이 `model_capacity_control` 한 행을 잠근다. 0.5초 넘게 기다린 것만 하루 35,141번 · 36,184초다. 잠금 자체가 아니라 **잠근 채 하는 일**과 **필요 없는 잠금 강도**가 문제다.

#### W2-1 정산·취소·읽기는 약한 잠금으로 (M)
- 묶은 발견: CAP-01 · CAP-04 · ARCH-03(PR1)
- 문제: 점유를 **줄이기만** 하는 전이 24곳(정산·취소·미확정 표시)과 정책만 읽는 도메인 트랜잭션 12곳 이상이 예약 부여와 같은 강도로 control 을 잡는다.
- 고칠 것: 잠금을 넷으로 나눈다 — 예약 부여 `FOR NO KEY UPDATE`, 정산·취소·보냄·정책 읽기 `FOR KEY SHARE`, 정책·모드 쓰기와 DR seal 만 `FOR UPDATE`, 관측은 잠금 없음. KEY SHARE 는 NO KEY UPDATE 와 충돌하지 않는다.
- 전제: control 에 쓰는 모든 경로가 `UPDATE` 전에 명시적 `SELECT … FOR UPDATE` 를 잡아야 한다. DR seal 이 지금은 잠금 없이 바로 `UPDATE` 하므로 그것부터 고친다.
- 효과: control 잠금 대기의 44~80% 감소(추정). 폭이 넓은 까닭은 대기 가운데 예약 부여와 보냄·정산의 비율을 잰 자료가 없어서다 — W0-2 로 먼저 잰다.
- 배포: 장부 경로라 DRAIN 창. 옛 코드와 새 코드가 섞이는 동안의 잠금 호환을 PR 에서 증명한다.

#### W2-2 전역 잠금을 쥔 채 하는 도메인 일 줄이기 (M)
- 묶은 발견: CAP-02 · CAP-03 · REVIEW-06 · DB-07 · REVIEW-13
- 문제: 보냄(dispatch) 트랜잭션 11종이 control 을 쥔 채 후보·문서·시도·잡·역할 행 잠금과 수십 문장을 돈다. 도메인 행 하나의 대기가 전체 정지로 커진다. 구체적으로 — 1차 심사 claim 은 잠금을 쥔 채 **두 번째 DB 연결**을 열어 장비 상태를 계산한다(풀이 차면 5초 자기 교착 위험). 사유 번역 보냄은 잠금 아래에서 심사 기록 전체를 본문 비교로 훑는다. 공식 사이트 근거 claim 은 잠금 아래에서 큰 조인을 최대 3번 한다.
- 고칠 것: W2-1 의 KEY SHARE 로 대부분 풀린다. 더해 — claim 재확인은 같은 연결(executor)로 하거나 잠금 밖 힌트를 넘겨받는다. 원문 확인은 잠금 전으로 옮기거나 id 조회로(W3-2).
- 배포: DRAIN 창 권고.

#### W2-3 장부 조회 인덱스 · 판정 식 (S, 전제 W0-3)
- 묶은 발견: CAP-05 · CAP-12 · DB-06 · CAP-14 · CAP-10
- 문제: 51만 행 장부를 5.6일에 176만 번 통째로 훑었다. 장비 판정의 `busy` 셋째 가지는 상태 조건 없이 시각만 걸어 어떤 인덱스도 못 탄다(입장과 모든 장비 상태 관측에서). 열린 4상태 `IN` 목록은 부분 인덱스 술어를 함의하지 못한다.
- 고칠 것: 셋째 가지를 상태별 범위 조건으로. 열린 상태 부분 인덱스 하나. `job_readback_idx` 는 부분 인덱스로 다시 만든다. 주원인이 이 가지인지는 EXPLAIN 으로 먼저 확인(PLAUSIBLE).

#### W2-4 예약 대기 폴링 · 만료 청소 · 회수 (M)
- 묶은 발견: CAP-07 · CAP-08 · CAP-13 · CAP-11
- 문제: 1차 심사의 예약 대기자가 500ms 마다 전체 입장 트랜잭션으로 다시 묻는다 — 칸이 모자랄수록 폴링이 늘고, 칸을 풀 정산은 그 뒤에 줄 선다. 입장 한 번이 잠금 아래에서 20~30번 왕복한다.

#### W2-5 장비 단위 직렬화 · 저장소 모듈 분할 (L)
- 묶은 발견: ARCH-03(PR2 이후) · ARCH-07 · STD-07

### 3단계 — 이력에서 유도하지 않는 대기열

공통 원칙(ARCH-04): **상태가 바뀌는 순간 대기열 표(또는 표지 칸 + 부분 인덱스)를 채우고, 무거운 술어는 고르기가 아니라 잠근 뒤의 검증에만 쓴다.** 놓친 것을 잡는 대조기가 15분~1시간에 한 번 전체를 본다. 묶음마다 옛 경로와 새 경로를 플래그로 나란히 두고 결과를 비교한 뒤 바꾼다.

#### W3-1 발행 대기열 (M)
- 묶은 발견: REVIEW-02 · CRAWL-01 · DB-01

#### W3-2 사유 번역 원천 표 (M)

- 문제: 번역할 사유 목록을 매번 심사 기록 36만 + 2차 심사 20만 행에서 다시 만든다. 진행률·대기열·묶음 확인이 모두 그렇다.

#### W3-3 판정 대기열 · 발굴 입장 계산 (M)

#### W3-4 2차 심사 정비 · 위임 고르기 (M)
- 묶은 발견: REVIEW-05 · REVIEW-09 · DB-08

#### W3-5 후처리 「다시 볼 때」 대기열 표준 (M)

### 4단계 — 수집 견고성

#### W4-1 일시 오류와 영구 실패 구분 · 되살리기 (M)
- 묶은 발견: CRAWL-05 · CRAWL-06 · CRAWL-07 · CRAWL-12 · CRAWL-15 · CRAWL-17
- 문제: 일시 오류 4번(약 3시간 35분)이면 frontier 가 영구 `failed` 가 되고, 이미 받은 GitHub 메타도 버려 후보가 생기지 않는다. 되살리는 경로가 없다(약 1,690건). 우리 쪽 네트워크·DNS 가 끊겨도 구분하지 못해 대기열 전체가 시도 횟수를 태운다. 실패 원인 코드를 버려 「fetch failed」 433건을 분류할 수 없다.
- 고칠 것: 소진 때도 원본과 실패 흔적을 저장해 판정이 사유를 남기게. 일시 오류 계열은 긴 꼬리 재시도(12시간 · 3일 · 7일). 한 묶음에서 여러 origin 이 연속 실패하면 「우리 쪽 장애」로 보고 시도를 돌려준다. `cause.code` · TLS 오류를 기록하고 인증서 오류는 영구로. charset 판별, 메타 리프레시 실패 시 껍데기 유지, 잡 취소 신호 전달.
- 배포: 일반 배포(crawler). 기존 failed 의 일회성 복귀는 새 수집보다 낮은 우선순위로(5절).

#### W4-2 재발견 재검토 · 발굴원 일관성 (S~M)

### 5단계 — 공개 웹과 사용자 경로

원 서버는 캐시 MISS 에서도 TTFB 0.17~0.38초다. 문제는 속도보다 **공개 요청이 가장 붐비는 주 DB 에 묶여 있다**는 것이다. PgBouncer 의 풀은 (DB, 계정)마다 하나라서, 운영 문서대로 같은 앱 계정으로 붙는 웹과 워커는 서버 연결 40개를 나눠 쓴다. 잠금을 기다리는 워커 트랜잭션도 그 연결 하나를 쥔다(`evidence/orchestrator-checks.md` — 설정 파일에서 읽은 값이고, 풀 사용량 자체는 재지 못했다).

#### W5-1 공개 요청의 주 DB 쓰기 줄이기 (M)
- 묶은 발견: WEB-02 · WEB-08 · WEB-01 · WEB-12 · DOM-09 · OPS-22
- 문제: 공개 화면·API 요청이 처리 전에 주 DB 에 rate-limit UPSERT 를 직렬로 보낸다 — 엣지 MISS 화면 1개, 상세 API 4개, 상세 한 번 보기에 합쳐 10~23문장. 기한이 없어 주 DB 가 밀리면 공개 요청이 함께 매달린다. 상세 렌더는 익명 GET 에서도 주 DB 에 `products` 행 잠금 트랜잭션을 연다. `/go` 는 이동 전에 주 DB 문장 5개를 기다린다.
- 고칠 것: 한도 저장을 Valkey 로(이미 있는 `CrawlBurstStore` 인터페이스, Lua 한 번 · 150ms 기한 · 실패하면 열어 둠). IPv6 는 /64 로 접는다. 상세의 바인딩 판정은 복제본 읽기 + 30초 캐시. `/go` 기록은 응답 뒤로. `/api/health` 는 직전 결과를 잠깐 담는다.
- 효과: 동시 접속 목표(5,000명)에서 주 DB 쓰기 초당 약 2,500문장(추정)을 0 에 가깝게.
- 배포: 일반 배포(웹). 전환 순간 한 창의 카운트가 비는 것은 허용.

#### W5-2 공개 집계를 스냅숏·공유 캐시로 (M)
- 묶은 발견: WEB-03 · WEB-04 · WEB-14 · DOM-02 · DB-18 · WEB-10 · ARCH-13
- 문제: 홈 집계를 웹 프로세스마다 1분에 한 번 따로 계산한다(제품마다 lateral 두 번). 공개 개수는 만료 순간 겹친 요청이 웹마다 전체 표를 다시 센다. 상세 부가 API 는 순위 하나를 얻으려고 화제판 전체를 주 DB 에서 다시 계산한다.
- 고칠 것: 홈 집계는 Valkey 공유 + `products.repo_born_at` 칸. 「목록에 실림」을 칸과 부분 인덱스로. 화제 순위는 캐시된 판에서 찾는다. 번역 읽기는 요청 단위 캐시. 공개 화면 렌더링 전략 자체는 재작성하지 않는다(CDN 이 그 역할을 한다).

#### W5-3 복제본 전환 기준 · 복제본으로 갈 읽기 (S)
- 묶은 발견: WEB-05 · RUN-08 · WEB-09
- 문제: 복제본 **풀 대기 초과**를 「복제본 다운」으로 보고 30초 동안 모든 공개 읽기를 주 DB 로 돌린다. 실패한 읽기는 주 DB 에서 처음부터 다시 돈다 — 붐빌 때 더 붐비게 만드는 연쇄다.
- 고칠 것: 풀 대기 초과는 「바쁨」으로 따로 분류해 그 요청만 처리하고 쿨다운을 걸지 않는다. 연결 오류만 30초 쿨다운. 검색어 해석 · 홈 소식 · 피드 등 주 DB 로 가는 공개 읽기를 복제본으로.

#### W5-4 요청 안의 무거운 일 떼어 내기 (M)
- 묶은 발견: WEB-06 · WEB-13 · WEB-15 · DOM-03 · DOM-07 · DOM-12 · WEB-11
- 문제: README 전문 API 가 요청마다 **수집용** GitHub 토큰으로 API 를 두 번 부르고 최대 8초 기다린다. 등록은 OG 그림 받기(최대 약 60초)를 기다린 뒤에야 수정 키를 돌려준다. 스타 버튼 GET 이 볼 때마다 GitHub API 와 주 DB 쓰기를 일으킨다. 공유 카드 PNG 와 메이커 미디어 워터마크를 요청 때 웹 이벤트 루프에서 만든다. 검색의 임베딩·재정렬 호출에 동시 상한과 차단기가 없다.
- 고칠 것: 잡이 미리 만들어 저장소(MinIO · DB)에 두고 요청은 읽기만. 등록은 썸네일 잡에 맡긴다. 검색은 프로세스별 세마포어와 단계별 차단기.

#### W5-5 메이커 쓰기 경로 (M)
- 묶은 발견: DOM-04 · DOM-05 · DOM-06 · DOM-08 · DOM-10 · DOM-11
- 문제: 수정 키 발급이 멱등이 아니고 다시 받을 길이 없다 — 응답 하나를 놓치면 그 제품은 영영 고칠 수 없다. 메이커 등록은 저장소 중복을 보지 않는다(수집 발행은 막는다). 확인되지 않은 repo_url 이 메이커 알림·귀속에 쓰인다. 로그인 한도의 계수 순서.

- 배포: 멱등 표 마이그레이션. 메이커 스킬(`skill/`)도 함께 갱신(옛 스킬은 그대로 동작).

### 7단계 — 실행기와 DB 운영

#### W7-1 연결 예산 · 시간 제한 (M)
- 묶은 발견: RUN-09 · RUN-10 · STD-06
- 사실(직접 확인): 앱 계정의 DB 설정은 `statement_timeout=120s · lock_timeout=5s · idle_in_transaction=120s` 한 벌이고, PgBouncer 모드의 모든 프로세스가 이것을 쓴다. 웹에도 120초다. 연결 예산(앱별 풀 합 ≤ PgBouncer 40 ≤ DB 150)을 검사하는 코드는 없다.
- 고칠 것: 부팅 때 실제 값을 읽어 기대와 다르면 경고(뒤에 거부). 역할별 DB 계정(웹은 5초 · 1초)으로 나누거나 트랜잭션 래퍼가 `SET LOCAL` 을 넣는다. 배포 plan 이 연결 예산 합을 검사한다. 역할 부모 프로세스의 풀은 작게.

#### W7-2 줄(lane) poll · heartbeat · 시계 (M)
- 묶은 발견: RUN-11 · RUN-12 · RUN-13
- 고칠 것: 줄 32개가 5초마다 따로 내는 문장을 프로세스당 poll 하나로. heartbeat 한 번 실패를 틱 상실로 보지 않는다(0행이거나 60초 무성공일 때만). 관측 시각은 DB 시계로 쓴다.

#### W7-3 autovacuum · HOT · 시간대 (S~M)
- 묶은 발견: DB-15 · DB-11 · DB-16 · STD-04 · CAP-14
- 문제: 큰 뜨거운 표가 autovacuum 기본값(20%)이라 죽은 행이 9~18% 쌓인다. `products` 갱신의 HOT 비율이 0.3% 다. 시각 칸이 시간대 없는 것과 있는 것으로 섞여 있다(154 대 163). drizzle 로 읽는 형 있는 칸은 UTC 로 읽히지만(2차 검증), DB 세션 시간대는 앱 계정에 고정돼 있지 않고(서버 기본값이 UTC 라 지금은 맞는다 — 직접 확인) 날 문자열을 직접 파싱하는 곳이 몇 군데 남아 있다.
- 고칠 것: 표별 `autovacuum_vacuum_scale_factor=0.02`. 앱 계정에 `timezone='UTC'` 를 고정하고 워커 preflight 가 확인한다(Oracle 소비자 계정은 이미 그렇다). 새 칸은 timestamptz 만. `products` 의 fillfactor 와 넓은 칸 분리는 W9-3.

### 8단계 — 개발 표준

#### W8-1 오류 분류 · 트랜잭션 안 오류 삼킴 (S~M)
- 묶은 발견: STD-03 · STD-10 · STD-16
- 문제: 트랜잭션 안의 읽기 실패를 savepoint 없이 `.catch` 로 넘기려 한다(`pipeline-control-repository`). 의도한 「모름으로 둔다」는 동작하지 않고 — 드라이버가 오류를 다시 던진다 — 실행 경로에서는 실제 원인이 25P02 로 가려진다(2차 검증에서 「관문이 꺼진다」는 반증됨). SQLSTATE 를 찾는 도우미가 9벌 이상 제각각이고, 오류 분류가 메시지 문자열에 기댄다. floating promise 를 잡는 lint 가 없다.
- 고칠 것: savepoint 로 감싼다. `sqlState()` · `isLockBusy()` 한 벌. `no-floating-promises` 를 경고부터.

#### W8-2 설정 한 입구 · 하드코딩 제거 (M)
- 묶은 발견: STD-05 · STD-11 · STD-15
- 문제: 소유자 규칙(「모델·주소는 관리자 설정으로만 — 하드코딩·env 금지」)과 달리 기본 등록부에 엔진 주소와 모델 이름 10개가 들어 있고, env 하나(`MODEL_REGISTRY_CONFIG`)는 관리자 저장값을 이긴다(다른 env 는 관리자 값이 없을 때만 쓰는 대체값 — 2차 검증). 추론 강도 선택지를 모델 이름으로 정해 새 모델은 고를 수 없다. 10-30 에 없앤 게이트웨이의 잔재가 98개 파일에 남아 있고 기본 provider 가 아직 그 이름이다. `.env.example` 에 운영 변수 약 40개가 없다.
- 고칠 것: `lib/config/env.ts`(zod) 한 입구와 그 스키마로 `.env.example` 검사. 기본 등록부의 주소·모델을 비우고 관리자 값만. provider 이름 정리는 장부 CHECK 에 걸려 있어 W8-3 과 같은 창.

#### W8-3 스키마 기준 · 생성 CHECK SQL (M~L)
- 묶은 발견: STD-07 · STD-08
- 문제: drizzle snapshot 이 0052 에서 멈춰 TS 스키마와 DB 가 어긋나 있다. 생성한 CHECK SQL(한 줄 33만 자)이 TS 소스 문자열로 들어 있다.
- 고칠 것: 마이그레이션한 DB 와 TS 스키마를 비교하는 통합 테스트(허용 목록만 통과). CHECK 는 #772 의 트리거 함수 시안과 함께.

#### W8-4 포매터 · lint · CI · 워커 이미지 (M)
- 묶은 발견: STD-12 · STD-13 · STD-14 · STD-09 · ARCH-12
- 고칠 것: 포매터를 새·수정 파일부터. 워커는 미리 묶은 JS 로 실행하고(지금은 운영에서 tsx) 쓰지 않는 next 약 300MB 를 뺀다. CI 는 `node_modules` 캐시(실행당 `npm ci` 12번)와 `tests` 전용 프로필. 효과 없는 `revalidatePath` 5곳 정리.

### 9단계 — 구조

#### W9-1 배포 범위를 런타임 경계로 판정 (PR1 S, 전체 M)
- 묶은 발견: ARCH-05
- 문제: worker·monitor 이미지에는 `app/`·`components/` 가 들어가지 않는데, 화면 TSX 를 바꿔도 18개 앱 전체 배포 + DRAIN 창이다. 최근 병합 100개 중 19개는 이미지 내용과 import 그래프로 웹 전용임을 증명할 수 있는데 지금 분류기는 1개만 그렇게 본다.
- 고칠 것: 분류기가 이미지에 들어가는 경로와 import 그래프로 판정한다.
- 효과: 해당 배포 한 번에 7~24분과 DRAIN 이 준다(11-06 배포 문서의 시간에 근거한 추정). 여러 PR 을 묶어 배포하는 날은 절약이 0 이다.

#### W9-2 모듈 경계 (L, 점진)
- 묶은 발견: ARCH-06
- 문제: 공개 상세 페이지가 번역 모듈을 거쳐 3,392줄 장부 저장소까지 닿는다. 공개 웹이 닿는 `lib` 569개 파일 중 455개가 워커와 공유된다.
- 고칠 것: 동작을 바꾸지 않는 이동부터 — 도메인 모듈을 읽기/쓰기로 나누고, 공용 기반을 `lib/platform` 으로, 마지막에 경계 lint 로 강제.

#### W9-3 뜨거운 행과 차가운 이력 분리 (L)
- 묶은 발견: ARCH-08 · DB-11
- 고칠 것: 잡이 자주 고치는 칸을 `products` 옆 표로 뗀다. 파티셔닝은 권하지 않는다.

#### W9-4 측정용 replay 장치 퇴역 (M, 소유자 결정)
- 묶은 발견: ARCH-11
- 사실: 운영 경로 61개 파일에 199개 분기로 남아 있고 통합 CI 시간의 약 1/5 을 쓴다. 계속 쓸지 정한다.

## 4. 이번 점검에서 이미 조치한 것

## 6. 하지 않기로 권하는 것

- **마이크로서비스 · 메시지 브로커 · LISTEN/NOTIFY 우선 도입**(ARCH-10). 제품 11만 · 하루 LLM 호출 수만 건 규모에는 Postgres 대기열 표 + `FOR UPDATE SKIP LOCKED` 로 충분하다. PgBouncer transaction 모드에서는 LISTEN 도 못 쓴다.
- **M3·mini 워커를 양쪽이 나눠 일하게(active-active)**(ARCH-09). 지금의 lease 구조를 싸게 만드는 편이 낫다(W1-6).
- **장부를 Valkey 토큰 버킷이나 낙관적 버전으로**(W2-5). 도메인 쓰기와의 원자성을 잃는다.
- **공개 화면 렌더링 전략 재작성**(ARCH-13). CDN 이 이미 그 역할을 한다. 목록 정렬 키만 미리 계산한다.
- **큰 표 파티셔닝**(W9-3). 보관 정리(#967)와 칸 분리로 충분하다.

## 7. 점검 방법 · 검증 · 한계

- **방법**: 운영 실측을 먼저 받고(느린 문장 23시간치 · 표/인덱스 통계 · 잡 상태 · 수집 분포), 코드를 10개 구역으로 나눠 병렬로 읽었다. 각 발견은 「실측이 가리키는 문장 → 그 SQL 을 만드는 코드 → 호출 빈도」 순서로 추적했다.
- **검증**: ① 구역 문서의 `경로:줄` 인용과 인용 코드를 전수 기계 대조했다(956곳, 불일치 0). ② 상위 항목은 오케스트레이터가 코드와 운영 DB 로 직접 다시 확인했다(`evidence/orchestrator-checks.md`). ③ 다섯 구역(공개 웹 · 운영 화면 · DB 쿼리 · 표준 · 구조)은 별도 검증자가 상위 항목을 반증 시도했다. 통째로 틀린 항목은 없었고, 세 건(STD-03 · STD-04 · STD-05)은 일부가 반증돼 제목에 「부분 반증」을 달았으며, 열 건은 등급을 내렸다(OPS-01 P0→P1 등). 고친 내용은 각 구역 문서 끝의 「검증 기록 (2차)」에 있다.
- **한계**:
  - 코드는 읽기만 했다. 테스트·빌드는 돌리지 않았고 수정안은 구현 전 설계다.
  - 0.5초 미만 문장은 실측에 없다. 「효과」 수치 중 직접 잰 것은 W1-1 · W1-5 뿐이고 나머지는 구조에서 나온 추정이다. 구역 문서의 「확신도: PLAUSIBLE」 항목은 적힌 확인(대개 EXPLAIN)을 먼저 한다.
  - 보지 못한 범위는 각 구역 문서의 「범위 밖·못 본 것」에 있다(관리자 화면 약 300개 파일 중 무거운 10여 개, Python 운영 도구의 내용, Cloudflare 설정 등).
  - 공개 저장소이므로 악용 절차가 될 서술 4건(DOM-01 · DOM-06 · DOM-08 · WEB-08)은 문제와 수정 방안만 싣고 상세는 비공개 메모로 뺐다.
- **이미 열린 PR 과의 관계**: #1000(공개 API 세션 · 더 보기 전체 수) · #999(키워드 생성 재시도) · #986 · #985 · #984 · #983 · #959 범위는 다시 제안하지 않았다.
