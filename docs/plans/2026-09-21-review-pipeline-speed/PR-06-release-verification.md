# PR-06 — 전체 경로 회귀 검증과 배포 판정

제안 브랜치: `test/review-speed-release-verification` · 선행: PR-01~05 · 상태: 미구현.

## 목적과 수정 범위

각 PR의 단위 동작이 맞아도 전체 파이프라인의 상태 전이·재시도·발행은 달라질 수 있다. **고정된 외부 응답으로 이전/개선 흐름을 비교하고, 개선되는 것은 시간·작업 요청뿐인지 검증한다.**

- 신규 `tests/integration/review-pipeline-equivalence.test.ts`, `tests/integration/review-pipeline-races.test.ts`.
- 신규 fixture: `tests/fixtures/review-pipeline-speed/`. 실제 API 키나 운영 사용자 데이터를 넣지 않는다.
- 신규 `scripts/verify-review-pipeline-speed.ts`: 로컬 전용 모의 파이프라인 실행/보고. 입력 schema와 loopback 전용 test DB를 명시적으로 검증한다.
- PR-01 보고 도구와 `docs/operations/review-pipeline-speed-runbook.md` (신규).
- 필요 시 운영 화면의 기존 서비스 역할 표시 E2E 보강. 새로운 판별 필드 UI는 추가하지 않는다.

## 고정 응답 비교

기존 `af50608` 기준 입력·모델/분류 응답을 fixture로 저장하고, 논리 후보 단위의 최종 상태·이유 코드·제품 identity·category·필수 승인표를 비교한다. 실제 LLM을 두 번 호출한 답변 일치를 동등성 테스트로 사용하지 않는다.

동등해야 하는 값: 각 후보의 승인/거절/보류와 근거, 보존한 원문, 입력/policy/source identity, 카테고리, 최종 발행된 저장소/URL 집합, 관리자 결정 보존, 정상 완료 경로의 논리 표/제품 중복 없음.

비교에서 제외하는 값: 정상적인 완료 순서·시각·job request version·로그량·DB 일련번호. ID는 논리적인 candidate/source/model slot으로 대응시킨다. 실행 중 원본·정책이 변한 race fixture에서는 동일한 과거 결과가 아니라 **최신 원본 재검증 및 부적격 발행 차단**을 검사한다. PR-04가 고치는 늦은 텍스트 결과 덮어쓰기는 기존 잘못된 동작을 재현한 뒤 차단되어야 한다. 이 차이는 정상 처리의 동등성 대상에서 제외하고 별도 안전 회귀로 기록한다.

## LAYA 비개입 검증

운영 entrypoint의 dependency graph에 LAYA client가 없어야 한다. LAYA 환경 변수가 없거나 잘못되어도 원래 모델 호출/원문/대상/정렬/발행 경로가 같아야 한다. 테스트에서는 예상한 기존 모델 endpoint 외 외부 통신을 차단하여 숨은 LAYA 호출이 없음을 확인한다. 평가 JSON/CSV는 앱 번들에서 import하지 않는다. 기존 오프라인 평가 파일에만 임의 LAYA 결과를 넣어도 운영 fixture 출력이 변하지 않아야 한다.

## 배포 순서와 성공 판정

1. 각 PR은 해당 회귀 검증 후 개별 검토/병합. 관문·정책 변경이나 LAYA runtime import가 있으면 병합 중단.
2. PR-01 기준선 수집 → PR-02 연결 → PR-03 큐 처리 → PR-04 늦은 텍스트 결과 보호 → PR-05 역할 이동 순서로 배포하고, 단계마다 상태·source hash·실제 커밋을 기록한다. 오래된 RELEASE_TAG만으로 배포 완료를 판단하지 않는다.
3. 배포마다 새 자동 심사 최소 100건 및 30분을 모두 충족하는 관측. 유입이 적으면 시간을 늘린다. 기존 후보를 검증 목적으로 억지로 재심사하거나 발행하지 않는다.
4. 실제 제품 중복/승인 관문 우회/오래된 원본 승인/관리자 덮어쓰기 **한 건이라도 발견하면 진행 중단·해당 PR 롤백**. 원인 확인 없이 잘못된 제품을 일괄 삭제하는 자동 복구는 하지 않는다.
5. 입력 규모·새 수집/재심사·큐 깊이·gateway 상황이 비슷한 구간에서 stage wait p50/p95, 새 처리 건수, 외부 요청 수, timeout/429를 비교한다. 샘플이 부족하면 성능 판정 보류로 기록한다.
6. 운영 중 timeout/429/invalid_output 실패율이 비슷한 기준선보다 2%p 이상 증가하거나 2차 대기 p95가 20% 이상 악화하면 원인을 조사하고 PR-03을 우선 되돌린다. 이는 정확도 임계값이 아니라 부하 악화의 운영 중단 기준이다. 원인이 외부 서버인지 구분하여 기록한다.
7. PR-05 후 실제 text worker healthy, publisher가 텍스트 작업을 실행하지 않는 로그, 텍스트 backlog 감소를 함께 확인한다. 전체 시스템에서 판별 경로가 동일한지 읽기 전용 표본 검증한다.

단계별 속도 개선과 안전 조건을 모두 만족해야 완료다. 모델을 바꾸거나 검수를 생략해서 얻은 빠른 수치를 이 작업의 성과로 보고하지 않는다.

## 롤백·최종 보고

변경의 역순으로 코드/역할을 되돌리고 DB의 심사·발행 이력은 보존한다. 전체 잡 요청을 삭제하거나 규칙 버전을 올려 재심사를 강제로 발생시키지 않는다. 최종 보고에는 실제 커밋, 배포 대상별 상태, 실행한 테스트, 전후 표본 수/지연/오류율, LAYA 운영 호출 0, 중복/잘못된 관문 통과 검사 결과와 미해결 항목을 기록한다. `docs/CODEX_HANDOFF.md`도 갱신한다.
